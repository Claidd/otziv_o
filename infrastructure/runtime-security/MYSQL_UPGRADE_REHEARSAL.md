# MySQL 9.0 → 9.7.3 local upgrade rehearsal

This opt-in harness reads **only** the sanitized `otziv-prod-local-mysql-1` source, then works on its own Docker network, named data volume and fixture accounts. It does not change Compose, the production pin, the source database, application code or the separate rollback fixture. No ports are published; the network is `--internal`.

The [official upgrade matrix](https://dev.mysql.com/doc/refman/9.7/en/upgrade-paths.html) supports an Innovation release to its next LTS by an in-place upgrade. MySQL 9.0 → 9.7 is that path. The [9.7.3 release note](https://dev.mysql.com/doc/relnotes/mysql/9.7/en/news-9-7-3.html) identifies it as the Docker-only Critical Security Patch Update. The candidate is pinned to `container-registry.oracle.com/mysql/community-server@sha256:bf955135c21e2c1c153417407fbbbb8efa786f487781b1fb6baaf7aba17d4340`, with amd64 image configuration `sha256:3fa754b144aeb7be887e6c614522aa06a2bbcd8ac2f3b67414884fa79000cdab`. Its actual binaries report mysqld **9.7.3** and MySQL Shell **26.7.1**; a tag alone is not accepted as proof.

## Run

Use local Docker and Node 22+. Prevent source DDL until `DUMP_CAPTURED`; ordinary transactional DML is compatible with the single-transaction capture. The operator must finish the approved offline migration/performer maintenance before declaring `SOURCE_READY`. The first captured rehearsal source was schema **1.10.300**; the independent hardened-image follow-up captures **1.10.306**. Do not pass this flag while source maintenance or another migration is running.

```powershell
node infrastructure/runtime-security/mysql-upgrade-rehearsal.mjs capture E:/private/mysql-upgrade-run --source-ready
# Source may resume only after DUMP_CAPTURED; subsequent work never reconnects to it.
node infrastructure/runtime-security/mysql-upgrade-rehearsal.mjs rehearse E:/private/mysql-upgrade-run --app-env-file E:/private/prod-local.env --app-image otziv-app:finalization-shutdown-proof
node --test infrastructure/runtime-security/mysql-upgrade-rehearsal.test.mjs
```

For the reviewed missing-definer fixture and additional hardened-runtime proof, use a **new capture directory**, then append `--prepare-reviewed-view-definer --hardened-image otziv-mysql:9.7.3-proof --retain-after-pass` to the rehearsal command. This opt-in definer preparation uses the same exact metadata/locked SELECT-only checks described below before the first checker, without recreating the already diagnosed original failure. The hardened tag resolves to an immutable local image ID recorded before execution. The upstream image remains the separate full Upgrade Checker artifact; the hardened runtime can omit MySQL Shell while retaining the server and client binaries.

The capture directory must not exist. On Windows its inherited ACL is removed and only the current user SID and SYSTEM receive access; on Unix its mode is 0700. `mysqldump --single-transaction --quick` streams binary bytes directly through gzip to a private file, including routines, triggers, events and hex blobs. No PowerShell text transcoding, credentials or user rows enter stdout. The capture records size/SHA256, source image/version and the Flyway-history hash. It is a local sanitized application-schema dump, **not** a replacement for the paired recovery archive.

The second command is exclusive and will refuse an existing `rehearsal.claim`. It creates a 1.5 GiB/2 CPU MySQL 9.0 clone and restores the captured bytes. The real application image migrates the 1.10.300 capture to 1.10.306, or validates an already-1.10.306 capture, passes authenticated database startup/Flyway/Hibernate validation and reaches `/actuator/health`. The app has a 2 GiB/2 CPU limit. Local env-file credentials never enter process arguments or evidence; database credentials are replaced with ephemeral fixture values. External send/registration/dispatch/backup flags are disabled, independently of the internal network fence. This health proof does not test live Keycloak authentication.

There is one explicit fixture-preparation recovery option, `--resume-app-preparation`. It is accepted only for an app-startup failure on the still-9.0 clone **before any checker or target-server attempt**. It preserves the failed result, verifies the unchanged app image/configuration, stopped resources, ownership labels and internal network, and starts the same existing 9.0 volume. It does not reimport or replace data. This exists to correct missing Compose-provided disabled integration placeholders when using a raw local env file. It cannot resume or bypass a failed Upgrade Checker or failed 9.7 upgrade.

The observed application image originally used `sh -c java ...`, which left Java behind a shell PID1. Its real `docker stop --time 120` ended with forced exit137 while health remained UP. That failure is retained. The corrected image `sha256:0b5307c31fc60e744bebf22b65495a7111bb775b066fcf3517d918fe874ae470` changes only the entrypoint to `exec java`; the resume guard verifies identical RootFS and every other image configuration field. Java PID1 may exit143 after SIGTERM: accept that only with no OOM/forced kill and completed graceful shutdown before the deadline. MySQL must exit0. Do not use an exit-code wrapper to conceal forced termination.

One separately reviewed correction is available through `--resume-view-definer-preparation`. The application-schema dump omits MySQL system users. On the observed clone, two unchanged `SQL SECURITY DEFINER` views (`analytics_payment_source` and `analytics_salary_source`) referred to the missing `hunt@%` database account; `CHECK TABLE` labelled those views `Corrupt`. The original full checker RED and direct diagnostic output are retained. This option accepts only those exact two errors before any target server has started, checks the actual view metadata and absence of that account, and creates a **locked** synthetic definer with **SELECT only** on the clone schema. No production password or login is introduced; view definitions are hashed before/after and must remain unchanged. The entire mandatory checker then runs again without exclusions. This is a correction of the incomplete fixture account inventory, not a general repair or a means to ignore actual corruption. Any other checker or target-upgrade failure still stops the run.

The app is stopped before the checker or comparison snapshots. The [official Upgrade Checker](https://dev.mysql.com/doc/mysql-shell/9.7/en/mysql-shell-utilities-upgrade.html) runs against the still-running 9.0 clone, using the candidate's bundled Shell and explicit target `9.7.3`, with the clone's complete option file. There are no check exclusions. A nonzero error count, empty/incomplete checks, wrong version, parser failure or failed process stops the run **before** the target server opens the volume. Warnings and manual checks remain evidence requiring review; the harness does not redefine them as zero risk.

After a successful checker, `innodb_fast_shutdown=0` and a clean MySQL exit are mandatory. Only then is the **same named volume** attached to the exact 9.7.3 image. The Oracle image uses UID27 by default, while the source image uses UID999. The harness explicitly retains UID999 using Oracle's non-root entrypoint support; a dedicated UID999 tmpfs supplies writable runtime files. It does not recursively rewrite database ownership or silently initialize another data directory. The generated option file retains existing nonstandard-FK compatibility, keeps database events off for the fixture, and is hashed in the result.

## Evidence and failure behavior

`rehearsal.json` records exact image identities, actual server version, checker outcomes and assertions. Private companion files contain:

- all application base-table row counts and the exact Flyway version/checksum history;
- extended data checksums for selected business and durable-queue tables;
- synthetic JSON-function results and counts/validity/aggregate CRC checks for every actual JSON column;
- native lead/performer queue selection SQL, its hash and successful `FOR UPDATE SKIP LOCKED` execution followed by rollback;
- app health, protected startup/server logs and resource limits.

Before/after row counts, history, representative checksums and JSON results must match before the target app starts. The real app then starts on 9.7.3 and passes health again. Queue probes verify SQL compatibility; they are neither a delivery attempt nor a throughput benchmark. Source MySQL users/grants are deliberately not copied, so this run proves the current JDBC client with isolated caching-SHA2 fixture accounts, not every production account policy.

With `--hardened-image`, an exclusive `upstream-rehearsal.json` freezes the upstream result before the additional phase. After a clean upstream stop, the hardened server opens the **same volume**, repeats the full integrity comparison and app health, and then undergoes a clean stop/start with another full integrity comparison. The app must run as Java PID1, finish before the shutdown deadline, and log completed Spring graceful shutdown, JPA closure and completion of every observed Hikari pool shutdown. Exit143 alone is insufficient. The new follow-up never rewrites the original upstream-only result directory.

Any checker/upgrade failure is retained with the phase and stopped owned resources. There is no `--upgrade=FORCE`, ignored error, grant bypass, new-volume fallback or automatic downgrade. Successful cleanup checks exact ownership labels and paths, then removes only this run's containers/network/volume and its protected dump/fixture credential file. Original failure evidence is not rewritten as a successful run.

`--retain-after-pass` deliberately leaves the owned containers stopped and retains the volume, network, protected dump and fixture credentials for an agreed follow-up. They remain private and are listed in the result. Subsequent cleanup requires checking those exact ownership labels and resolved paths; this flag does not grant access to unrelated fixtures.

There is **no supported binary downgrade of this 9.7 data directory to 9.0**. The [official downgrade matrix](https://dev.mysql.com/doc/refman/9.7/en/downgrading.html) does not provide in-place LTS→earlier Innovation rollback. Keep a verified pre-upgrade backup paired with its app/configuration/secrets and restore that pair when rollback is required. This rehearsal's disposable dump is deleted on success and is not that operational backup. Production activation still requires a fresh backup/restore decision, actual account/configuration review and the candidate's separate vulnerability scan; this script grants no release approval.
