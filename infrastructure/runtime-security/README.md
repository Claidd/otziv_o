# Runtime security and CI evidence

The quality workflow builds the actual backend, web, worker, WhatsApp, Docker-observer and monitoring-publisher Dockerfiles, checks their runtime boundaries and preserves vulnerability reports. Local commands require Node 22.12+ and a local Docker context; remote Docker contexts are rejected. Nothing here starts the application Compose stack, restores production data, logs into WhatsApp or sends provider messages.

```sh
node --test infrastructure/runtime-security/*.test.mjs infrastructure/docker-observer/*.test.js
docker build -t otziv-worker-ci -f backend/external-review-worker/Dockerfile backend/external-review-worker
docker build -t otziv-whatsapp-ci -f Dockerfile.whatsapp .
docker build -t otziv-observer-ci infrastructure/docker-observer
node infrastructure/runtime-security/container-smoke.mjs worker otziv-worker-ci
node infrastructure/runtime-security/container-smoke.mjs whatsapp otziv-whatsapp-ci
node infrastructure/docker-observer/consumer-smoke.mjs otziv-observer-ci
node infrastructure/runtime-security/scan.mjs image otziv-worker-ci /secure/evidence/worker-vulnerabilities.json
node infrastructure/runtime-security/scan.mjs image otziv-whatsapp-ci /secure/evidence/whatsapp-vulnerabilities.json
node infrastructure/runtime-security/scan.mjs image otziv-observer-ci /secure/evidence/observer-vulnerabilities.json
# Run only after Maven verify has produced the current release jar.
node infrastructure/runtime-security/scan.mjs java backend/target /secure/evidence/maven-vulnerabilities.json
```

## Chromium sandbox prerequisites

Playwright defaults its Chromium sandbox off. Every worker launch explicitly sets `chromiumSandbox: true`; the readiness fixture inspects the **actual** browser command line through CDP and refuses `--no-sandbox`, `--disable-setuid-sandbox`, `--disable-seccomp-filter-sandbox` and `--disable-namespace-sandbox`. The WhatsApp compatibility fixture checks those same actual arguments. Checking only our argument array would miss library-added defaults.

`chromium-seccomp.json` derives from the [official Playwright v1.61.1 Docker profile](https://github.com/microsoft/playwright/blob/v1.61.1/utils/docker/seccomp_profile.json). The original downloaded bytes have SHA-256 `cc3e61cabda6bbc1e53e54d27ba4d55a9d3be829b6dd1a596f4a7b31b1cc7849`. It retains the deny-by-default baseline and the upstream user-namespace syscalls `clone`, `setns`, `unshare`. Our single additional unconditional syscall is `chroot`: Chromium needs it **inside its user namespace**, and the baseline's CAP_SYS_CHROOT conditional rule cannot match `cap_drop: ALL`. This does not grant CAP_SYS_CHROOT or CAP_SYS_ADMIN in the host namespace. The profile is versioned and checked for selected dangerous unconditional syscall additions.

The deployment host must support and permit unprivileged user namespaces, have a nonzero namespace limit and an LSM/AppArmor policy compatible with the sandbox. Verify the exact deployed image and this profile on each host using the commands above. A host policy that denies user namespaces needs a narrowly reviewed host policy change. Do not disable AppArmor globally, grant SYS_ADMIN, use an unconfined seccomp profile or disable the browser sandbox to make a failed probe green. The repository does not silently modify host kernel/LSM settings.

The smoke uses the release constraints: non-root image user, read-only root filesystem, all capabilities dropped, `no-new-privileges`, `/tmp` with `noexec,nosuid`, this seccomp profile and bounded memory/PIDs/shared memory. Worker OCR reads the pinned local language models with `--network none`. It then starts the real worker twice and checks healthy readiness, broken-Chromium readiness failure, authenticated API admission, and orderly exit. WhatsApp tests actual Puppeteer 25 + whatsapp-web.js local and remote lifecycle against intercepted fixture pages; QR login, a live provider session and real message delivery remain separate acceptance checks.

Worker Compose stop grace is 400s, longer than its validated maximum task/drain grace (370s). WhatsApp stop grace is 330s, longer than its maximum 300s drain. A forced timeout remains a failure: an abandoned WhatsApp claim is UNKNOWN on recovery and must not be blindly retried. Rollouts must preserve the durable WhatsApp auth/operation volume. Do not lower stop grace independently of task limits.

## Vulnerability gate and its limits

The [2026-09-07 override/advisory review](OVERRIDE_AND_ADVISORY_REVIEW_2026-09-07.md) maps all 22 current npm override declarations to actual parent ranges/resolved versions and fresh full-graph audit evidence. Its separate per-CVE index retains 49 unresolved CVEs across the latest three integration/publisher image reports, with proposed reviewer roles and **no approved owner assignment, acceptance or expiry**. Read the scope/timestamps before treating a prior image report as current release evidence.

The separate [observed production fleet registry](PUBLISHED_FLEET_2026-09-07.md) verifies all 13 actual containers / 12 image configurations and retains full scan/SBOM/triage evidence, plus static scheduler definitions extracted and hashed from the published JAR. The old deployed images contain 1001 HIGH/CRITICAL package rows (347 advisory IDs): 804 with fixes and 197 without a reported fix. No risk is accepted by this inventory. [The comparison with checked-in pins](DEPLOYED_AND_REPOSITORY_IMAGES_2026-09-07.md) distinguishes pending application releases from upstream image upgrades and rehearsals that still require implementation. Candidate image tests are not substituted for production digests; static annotations are not counted as registered runtime tasks.

`scan.mjs` pins Trivy 0.74.0 by digest, exports the local image to a fresh temporary directory and gives the scanner only that read-only export. The scanner never receives the Docker socket or application credentials. Maven mode copies only packaged jars and uses Trivy **rootfs** mode: filesystem mode deliberately ignores compiled JARs. Missing artifacts, missing Java results, failed database access, missing report and missing CycloneDX components fail closed. A cold Java scan downloads a large Java index (about 918 MiB compressed in the recorded run); provision several GiB of free temporary disk. Scanner scratch uses its own temporary disk directory, not the small container tmpfs, and is removed after the run.

The complete JSON report contains all severities, vendor statuses, fixed versions and the discovered package inventory (`--list-all-pkgs`). A matching `.sbom.cdx.json` is generated offline from that report. The `.triage.json` retains every HIGH/CRITICAL row with review context and unproven reachability; it grants no exception. Bounded scanner diagnostics are retained in `.scanner.log` on success or failure. There is no `--ignore-unfixed`, no CVE ignore list and no invented VEX claim. CI uploads these artifacts even when the vulnerability gate fails, for 14 days; archive release evidence externally for the retention period required by the actual organization.

The automatic fix-availability gate fails on HIGH/CRITICAL findings **with a fixed version**. Unfixed HIGH/CRITICAL findings remain in the report, count and `unresolvedRiskReview: REQUIRED` output. A successful automatic gate therefore does not mean zero vulnerabilities or approval for release. A risk owner must review unresolved findings against actual exposure and vendor status before release; any accepted exception needs an explicit owner, rationale, review/expiry date and tracked remediation. None is pre-approved here. Refresh the scanner database and scan the exact release image again: vendor fixes and CVE data change independently of source code.

The narrowly reviewed Grafana/Tempo pseudoversion case additionally produces `.adjudications.json`. The scanner resolves the image to an immutable local ID before export, extracts the actual Grafana executable from that same image without executing it, and uses a pinned, offline Go parser. Two exact Tempo module/version/CVE pairs can be classified as fixed code present only when the executable SHA-256, entire Go build-info hash, module h1 checksum, actual image rootfs/product/source labels, bundled upstream source hashes and complete official ancestry replies match the [review](adjudications/grafana-tempo/review.json). A changed binary requires another review. No image tag, user-provided verification flag, broad product match or semantic-version rewrite authorizes this decision. Inspection failure retains the original blockers.

Raw JSON, SBOM, triage and `blockingFixedHighOrCritical` remain unchanged. The scanner reports `adjudicatedFixedHighOrCritical` and `effectiveBlockingFixedHighOrCritical` separately; only the latter controls the exit code after this evidence check. A real additional fixed CVE still fails, and vendor-unfixed risks still require review. Run the actual path with `node infrastructure/runtime-security/scan.mjs image <immutable-image-id> <private-output.json>`; regression tests are in `grafana-tempo-adjudication.test.mjs`.

The [reviewed image manifest](reviewed-images.json) records portable source builds and the original immutable pins separately. Historical local image IDs and fixture proofs are not registry publication digests. Candidate publication must build the named component for `linux/amd64`, scan the resulting exact published manifest and retain its build provenance and SBOM. The original `sourceBeforeRef` stays an explicit upgrade/rollback proof input after default pins change. Publishing a candidate does not activate it, approve vendor-unfixed risks, or authorize opening existing database volumes with a new major release.

The runtime images use a verified Node 22.23.2 Debian Bookworm base digest and apply available distribution updates during build. npm/npx, Corepack and Yarn are removed after dependency installation; entrypoints and probes use `node` directly. Developer/CI `npm ci` and tests still run outside these final images. Apt repositories and vulnerability databases are intentionally current rather than historical snapshots, so equal source does not promise byte-identical rebuilds. Release by immutable built digest, retain SBOM/report and repeat smokes after rebuilding.

The packaged Maven scan covers shipped Java libraries. The mandatory CI security profile additionally scans resolved test/provided/system dependencies and build-plugin dependency graphs; authenticated Sonatype credentials and the other analyzer prerequisites must be provisioned. See the [Maven fixes, exact false-product corrections and remaining build/test findings](MAVEN_AUDIT_2026-09-07.md). Neither scanner proves runtime reachability or substitutes for code authorization tests. The integration matrix covers six actual built images: backend, web, worker, WhatsApp, observer and the signals publisher. A separate upstream-image inventory/gate covers checked-in dependency images; the [published fleet registry and exact-image reports](PUBLISHED_FLEET_2026-09-07.md) record the observed production artifacts. Each release must retain its own matching digest, report and review. Backend/web also receive bounded network-disabled runtime/configuration probes; application health against a real database is a separate acceptance step. These checks do not assert that the entire production fleet is vulnerability-free.

## External acceptance remains explicit

For bounded database query measurements with synthetic data, run `node infrastructure/runtime-security/queue-load-smoke.mjs /secure/evidence/queue-load.json`. It owns an isolated MySQL container/volume and never uses Compose or restored data. See [the measured plans, improvement and remaining limits](QUEUE_LOAD_2026-09-07.md). Completion is not a throughput or product SLO assertion.

The local recovery tests prove archive authentication, identity/manifest checks, negative cases and command boundaries. They do not prove a coordinated production MySQL/PostgreSQL/object-storage/secrets restore. Follow [the recovery runbook](../recovery/README.md), agree RPO/RTO, establish a real write fence and test the restored identity/session boundaries before public access.

The monitoring tests use only a local mock receiver and watchdog. A real independent host, selected contact/provider, observed production signals, receiver deduplication and recipient delivery/outage drills must be configured and evidenced according to [the monitoring runbook](../monitoring/README.md). Safe example configs intentionally fail until that information is supplied; no external recovery schedule or real alert delivery has been activated by these CI changes.
