# Observed runtime signals and TLS publication

Run `node infrastructure/monitoring/publisher.mjs /etc/otziv-monitor/publisher.json` using the example configuration as a schema, with actual source inventory and protected files. `otziv-signals-publisher.service` is the host-runner template. This component collects data; it never sends an alert or changes an application queue. The independent `watch.mjs` runner consumes its HTTPS URL and remains on another host.

Enable backend `OTZIV_MONITORING_ENABLED=true` and provide a distinct `OTZIV_MONITORING_SHARED_SECRET` of 32–512 characters. `GET /api/internal/monitoring/runtime` uses a dedicated exact-path, stateless Spring Security chain and constant-time `X-Otziv-Monitor-Token` authentication. No bearer/session fallback is accepted and all other methods are rejected. Supply that same value as the publisher's `BACKEND_MONITOR_TOKEN`. Existing worker/gateway shared secrets authenticate their scalar endpoints (`/api/internal/task-metrics`, `/internal/task-metrics`) via `X-Otziv-Internal-Token`; absent secrets never expose metrics anonymously.

The backend maintains a fixed-memory ten-minute histogram of actual servlet requests, including asynchronous completion and error/timeout outcomes. Health and monitoring requests are excluded so scrapes do not fabricate traffic. `latencyP95Ms` is the histogram bucket upper bound; overflow uses the observed maximum. An empty window is `NO_TRAFFIC`, zero observed samples and **null** latency/error rate. It is neither a 0-ms claim nor an unavailable process. Saturation is the maximum available measured JVM-heap, CPU and database-pool ratio, with individual unavailable components retained as null.

Queue families are explicit: lead, performer notifications, session revocations, common integration outbox and workload. Lead/performer/session metrics use their source observation timestamp; outbox and workload use public read-only projections sampled into a 30-second cache. HTTP publication never issues queue queries. Missing or stale snapshots fail collection. Disabled dispatch is metadata and does not hide real backlog, DEAD/blocked or UNKNOWN counts. `null` DEAD/UNKNOWN means the protocol has no such state, not a fabricated zero from a failed query. Capped outbox counts remain labelled lower bounds and cause `queue_counts_capped` rather than silently claiming exact counts. Lead due age uses `next_attempt_at` on due READY records, including records waiting behind FIFO blockers; it is not age since creation or a count of claimable rows.

Task sources must enumerate every deployed worker/gateway instance with a stable bounded alias; use `enabled=false` only for a contour that is actually disabled. Do not point one alias at a load balancer and assume it represents every replica. Task snapshots report actual running/cleanup occupancy, oldest cleanup age, timeout and fixed-reason rejection counters. An entirely disabled task inventory reports null cleanup with `DISABLED`, not synthetic healthy zero. Add each enabled WhatsApp instance explicitly.

Only HTTPS source URLs are accepted by default. Exact hostnames may be listed in `privateHttpHosts` for authenticated calls inside the deployment's private container network or loopback; this is an explicit operator allowlist, not proof of network isolation. Never allow a public plaintext hop. Use the existing network policy or an actual private TLS endpoint when the publisher runs outside that network. Redirects, arbitrary endpoint paths, credentials in URLs, oversized JSON and expired observations are rejected.

The publisher reads existing actual MySQL JSONL evidence and PostgreSQL receipts from read-only paths; missing files fail collection, empty receipts report unverified backup. Preserve source timestamps. The TLS key/certificate paths and environment secrets stay outside Git; a readable regular key with private permissions is required on Linux. Use a certificate valid for the exact configured hostname and a trusted CA; use `NODE_EXTRA_CA_CERTS` for a private CA. TLS verification must remain enabled. `MONITOR_SIGNALS_TOKEN` is a distinct 32–512-character bearer credential for the external monitor. The only published route is `GET /private/monitor-signals`, with no-store responses, request/header deadlines, a connection limit and cached bounded bodies. Startup, stale data or failed collection returns 503. Collection is single-flight; a hung source cannot spawn overlapping collectors or publish a late success past its deadline.

The container example binds all interfaces inside its container; `compose.monitoring.yaml` publishes its host port on loopback by default. For the host service, change `bindAddress` to loopback unless an exposed interface is intended. To expose a real HTTPS listener, configure its intended interface, private routing/firewall and DNS/certificate deliberately; do not publish application/internal worker ports as a workaround. Install the independent monitor only after selecting its owner/contact, receiver and dead-man service and agreed SLO/RPO thresholds. Tests exercise actual TLS and local source fixtures; no external notification route, real contact or provider is activated by source changes.

The opt-in Compose overlay joins only the existing application/review/messaging networks and enables the backend's separate monitoring endpoint. It has no Docker socket, database credentials, writable application volumes or notification credentials. Its config, TLS and actual receipt directories are read-only binds with automatic host-directory creation disabled. Mount the actual MySQL `otziv.backup.work-dir` evidence directory and the PostgreSQL recovery CLI evidence directory; adapt the filenames in the JSON config to those selected paths. Never replace missing receipts with a success fixture. TLS files must be readable by image UID 1000; the private key must remain mode 0600. Keep `MONITOR_SIGNALS_TOKEN` alone in the publisher env file; source tokens are forwarded separately by the overlay.

Required overlay variables are `SIGNALS_PUBLISHER_IMAGE`, `OTZIV_MONITORING_SHARED_SECRET`, `MONITOR_PUBLISHER_SECRETS_FILE`, `MONITOR_PUBLISHER_CONFIG_FILE`, `MONITOR_PUBLISHER_TLS_DIRECTORY`, `MYSQL_BACKUP_RECEIPTS_DIRECTORY`, and `POSTGRES_BACKUP_RECEIPTS_DIRECTORY`. The source inventory example matches the production `whatsapp_lika` and `whatsapp_vika` service names; prod-local has no gateway containers and must mark those contours disabled. A missing enabled worker/gateway makes the publisher unavailable. This publisher represents one explicit backend instance: use a separate publisher and monitor target per backend replica so a load balancer cannot hide an unavailable replica.

```sh
docker build -t otziv-signals-publisher:<release> infrastructure/monitoring
node infrastructure/monitoring/container-smoke.mjs otziv-signals-publisher:<release>
docker compose --env-file <selected-env> -f docker-compose.yaml -f compose.monitoring.yaml --profile monitor-signals config --quiet
# Deployment is a separate, reviewed operation after actual source/certificate/receipt configuration.
```

CI builds and scans this exact Dockerfile and tests its actual collector/TLS publisher inside a non-root, network-disabled, read-only container. Missing configuration and invalid TLS permissions fail startup. Source outages cause 503, not a fresh healthy snapshot. Existing dependency and image vulnerability policies still apply to this additional runtime.
