# External monitoring and notification drill

`watch.mjs` is a Node 22.12+ standalone one-shot monitor. Run it on a host independent of the application/Docker host. It does not rely on the application's Prometheus surviving to detect total host loss. No actual notification provider, recipient, schedule, SLO or RPO is selected by this repository.

```sh
node --test infrastructure/monitoring/*.test.mjs
node infrastructure/monitoring/watch.mjs /etc/otziv-monitor/config.json
node infrastructure/monitoring/export-signals.mjs /secure/runtime-metrics.json /secure/mysql-evidence.jsonl /secure/postgres-receipts.json
```

The example config fails closed until the owner/contact, endpoints, runbook, independent-host confirmation and every threshold are set. Store config and tokens outside Git. The environment supplies `MONITOR_ALERT_TOKEN`, `MONITOR_WATCHDOG_TOKEN`, `MONITOR_SIGNALS_TOKEN`; URLs may not embed credentials or query-string tokens. All production requests require HTTPS, reject redirects, use finite deadlines and bounded JSON bodies. Linux state directory mode is 0700; state/lock files 0600. Windows requires equivalent operator-managed ACLs. Do not put request bodies, user IDs or phone numbers into scalar metrics or alert labels.

The availability URL must return 2xx JSON `{ "status": "UP" }` only when ready. `collect.mjs` now obtains actual backend request/queue/resource samples and worker/gateway task snapshots; `publisher.mjs` publishes the combined `otziv-monitor-signals-v1` over authenticated HTTPS. Follow [publisher setup and source contracts](PUBLISHER.md). `export-signals.mjs` remains available for historical receipt tooling, but is no longer the only collection mechanism. No successful collection substitutes current time for stale source or backup timestamps. Missing/invalid/stale sources make the publisher unavailable and alert. Select windows and thresholds from agreed SLO/RPO; count thresholds of 1 detect any DEAD/UNKNOWN.

`runtime-metrics.json` format is `{ "schema":"otziv-runtime-metrics-v1", "measuredAt":"UTC ISO timestamp", "values":{...required scalar metrics...} }`. Receipt input accepts a JSON object/array or JSON Lines up to 20 MiB, so rotate/aggregate evidence explicitly. Export output contains no object keys or customer data. A verified remote object remains a valid backup even if later email or cleanup fails; these become separate conditions. A remote-verified receipt without a completion receipt is **not proof of successful cleanup**. The required `backupCompletionMaxAgeSeconds` threshold gives the bounded completion grace; after that age an absent matching completion receipt raises a separate completion-missing condition. Choose it from the actual maximum post-verification delivery/cleanup duration. Collector errors must stop updates so heartbeat age exposes them; do not emit fresh timestamps from a failed collection.

The alert receiver contract is an authenticated POST with an `Idempotency-Key` and JSON `{schema,eventId,service,owner,state,conditionCodes,observedAt,runbook}`. It must durably deduplicate that event ID and return 2xx only after accepting delivery responsibility. The monitor persists pending events before sending, retries the **same payload and ID** after an ambiguous failure, deduplicates unchanged conditions, repeats at the configured interval, and sends `resolved` after recovery. The local ledger cannot guarantee exactly-once human delivery if a selected provider ignores this contract. Add a small provider-specific receiver adapter if required; do not assume arbitrary webhook URLs implement it.

The watchdog URL belongs to an independent dead-man service, distinct from the app and alert provider hostnames. A successful run POSTs a heartbeat only **after** probes, durable state updates and required notification delivery succeed. Configure that service to notify the responsible contact when heartbeats stop; this catches a failed monitor process/host and an unavailable alert channel. Distinct hostnames and config confirmations alone do not prove infrastructure independence or real recipient delivery. A watchdog request failure exits nonzero; a dead-man service must actually be configured outside this monitor to detect missing pings.

Maintenance is optional `{startedAt,until,reasonReference}` and must fit the configured maximum duration. It suppresses new firing/resolution/repeat events only during that bounded interval and continues probes/watchdog pings. A previously persisted event is still delivered. On expiry, current conditions are evaluated normally. There is no indefinite mute. A stale `.lock` fails closed: first prove the owning process has exited, then remove that exact lock. Corrupt state needs a reviewed recovery; preserve the pending event if possible. Never run simultaneous monitors against the same state file or discard it during deployment.

The tests use a local HTTP fixture only: whole host outage produces one firing event, repeated runs deduplicate, recovery resolves, ambiguous alert acknowledgment retains the same event and suppresses watchdog, maintenance expires, backups age, missing metrics and broken state fail closed. No real user or provider receives these messages.

For production activation, choose contact/provider and policies, provision and test the receiver/dedup contract, external host, real signal collector and independent dead-man service, then install `otziv-monitor.service` with a completed `otziv-monitor.timer.example` after verifying the Node executable path. Set the cadence and dead-man grace from the agreed detection SLO and the maximum bounded run duration. Perform authorized drills for backend-only outage, entire Docker-host outage, stale backup/destination failure and notification-channel failure; obtain evidence of actual recipient delivery and resolution. Only that external test closes the operational acceptance gate.

Rollback preserves the durable state and the independent dead-man/availability check. Disable or tune the individual noisy metric rule using a reviewed config change; do not replace unknown/missing data with healthy values. If disabling this monitor, migrate watchdog ownership and alert coverage first so its silence is not mistaken for healthy service.
