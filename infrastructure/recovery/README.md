# PostgreSQL backup and paired recovery tools

Requires Node 22.12+ (built-ins only), AWS CLI v2, and `pg_dump` matching the configured PostgreSQL major. `postgres-drill` also needs a **local** Docker engine and the configured digest-pinned PostgreSQL image already present. Nothing here enables a timer, provisions storage or contacts a real endpoint merely by running tests.

```sh
node --test infrastructure/recovery/*.test.mjs
node infrastructure/recovery/cli.mjs preflight /etc/otziv-recovery/config.json
node infrastructure/recovery/cli.mjs backup /etc/otziv-recovery/config.json
node infrastructure/recovery/cli.mjs manifest /secure/pair-input.json /secure/manifest.json
node infrastructure/recovery/cli.mjs postgres-drill /etc/otziv-recovery/config.json /secure/manifest.json /secure/postgres.dump.enc
node infrastructure/recovery/cli.mjs compare-identities /secure/mysql-identities.json /secure/keycloak-identities.json
```

`config.example.json` deliberately fails validation until owner, immutable release, versions, storage, independence/privacy/versioning confirmations and agreed RPO/RTO are supplied. The checked-in image digest reflects the repository image; use the exact tested release image, never a floating tag. This preflight checks configuration and local tools; its output explicitly says `remoteVerification=NOT_RUN`. It does not prove storage access, independent retention or recoverability.

Keep real config, keys, receipts and dumps outside Git on restricted storage. Linux work directories must be mode 0700, password/CA files mode 0600, and the service account must own them. On Windows the operator must apply equivalent ACLs; Unix mode and directory-fsync guarantees do not apply there. Configure `RECOVERY_PGPASSFILE`, `RECOVERY_ENCRYPTION_KEY_BASE64` (independent random 32-byte Base64 key), `RECOVERY_S3_ACCESS_KEY`, `RECOVERY_S3_SECRET_KEY` and optionally `RECOVERY_S3_SESSION_TOKEN` in the protected environment. No key or database password is passed in process arguments. `keyId` is a safe recovery identifier, never the key itself. Keep recoverable key copies in a separate encrypted store. The source connection requires a local Unix socket or TLS with `verify-full` and an explicit trust root; no cleartext remote mode exists.

## Capture and remote verification

`pg_dump --format=custom` captures the complete configured **database**, with no schema/table filters. Its stdout is encrypted directly with AES-256-GCM and a random 96-bit nonce; there is no plaintext backup intermediate. `OTZIVPG1` is an 8-byte magic, 12-byte nonce, ciphertext, and final 16-byte authentication tag; the header is authenticated as AAD. Plaintext and ciphertext sizes are bounded. The current AWS `put-object` pipeline limits plaintext to below 4 GiB; larger databases require an explicitly implemented multipart/chunked extension, not removal of the bound. `pg_dump` failure or any stderr warning fails the capture and requires private operator diagnosis; child stderr is never printed in ordinary logs.

The dedicated S3 principal must have PutObject/GetObject/GetObjectVersion for its prefix, plus retention read/write if Object Lock is enabled. It does not need delete or public ACL permissions. Do not reuse the primary bucket/account. The tool strips ambient AWS profiles/role/session settings and uses only dedicated credentials. The endpoint requires verified HTTPS; redirects or custom shell commands are not used. Bucket versioning is mandatory. The exact upload version must pass HEAD byte count/SHA-256 metadata, optional SSE policy, optional provider-enforced retention, a version-bound download, ciphertext SHA-256 and complete GCM authentication. Missing/null/mismatched versions fail. Separate uploaded receipts include only object references, checksums, times, versions and key IDs.

A durable `<id>.remote-verified.json` receipt is written before checked local cleanup. A separate `<id>.completed.json` proves cleanup. Cleanup failure does not erase the remote verification receipt. A receipt-write failure after remote success may leave a valid unjournaled object; do not claim exactly-once uploads. No retention deletion is implemented. Existing encrypted MySQL backups and the R0 restore drill remain independent and unchanged.

`pg_dump` does not include cluster-wide roles or tablespaces. Recreate the standard database role/bootstrap from the pinned infrastructure and protected secret set; include any nonstandard cluster objects and their restoration procedure in that protected set before accepting a manifest. This tool is not a whole PostgreSQL cluster backup. [PostgreSQL pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html), [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html), [AWS put-object](https://docs.aws.amazon.com/cli/latest/reference/s3api/put-object.html), [version-bound get-object](https://docs.aws.amazon.com/cli/latest/reference/s3api/get-object.html).

## Pairing and isolated restore

`manifest` consumes a protected JSON object with:

- `mysql`: the existing R0 remote-verified/completed receipt; `postgres`: the new receipt. Both must contain verified HEAD/download/SHA-256/authenticated-envelope flags, matching release commits and captured interval metadata. The MySQL conservative capture interval is `timestampUtc - elapsedMillis` through `timestampUtc`.
- `fence`: safe `id`, `attestedBy`, `evidenceReference`, `startedAt`, `endedAt`, and exact scope `all-mysql-keycloak-and-business-object-writes`. Establish and observe this fence externally, including backend/jobs/Keycloak admin/API and business object writers. The tool verifies timestamp containment; **the receipt is an operator attestation, not automatic proof of a fence**. Independent daily snapshots are not automatically a consistent pair.
- `owner`, `releaseCommit`, `mysqlSchemaVersion`, `keycloakSchemaVersion`, `mysqlKeyId`, agreed `rpoSeconds`/`rtoSeconds`, and `recoverableKeyIds` containing both database key IDs.
- `components` entries `business-objects`, `secrets`, `android-signing`, `integration-state`, each with safe `recoveryReference`, immutable `versionId`, `sha256`, `owner`, and `independentCopyVerified=true`. Sensitive component archives require `encrypted=true`; business objects require a verified inventory of exact object versions and `versionedInventoryVerified=true`. Include application encryption keys, auth/session revocation state, OAuth/client secrets, signing material, database bootstrap/global objects, WhatsApp auth and operation-ledger state with its owning client identity as applicable. Never copy secret values into these fields.
- `sessionRecoveryPolicy`: `invalidate-all-sessions-and-rotate-signing-keys-before-public-access`. This identifies the required secure recovery gate; the manifest builder does not execute it. Coordinate forced reauthentication and current authoritative security generation restoration with the auth runbook before opening access.

The output contains a content checksum for accidental corruption detection, not a digital signature or proof of origin. Store it with the protected independent recovery set; a manifest from an untrusted source must not authorize restore. `ARTIFACT_SET_VALIDATED_FULL_SYSTEM_RESTORE_NOT_YET_PROVEN` is intentional. Secrets/object inventories have been attested, not fetched by this tool.

The PostgreSQL drill compares artifact checksum/size, image/major/Keycloak version/key identity, then authenticates the entire encrypted object into a mode-0600 temporary file **before invoking Docker**. It rejects `ssh://`/`tcp://` Docker endpoints and ambiguous contexts. It uses unique owner-labelled container/volume names, `--network none`, no ports, no host bind mounts, `--pull=never`, no application, and no outbound workers. It restores with `pg_restore --exit-on-error --no-owner --no-acl`, checks key Keycloak tables and migration/realm rows, then deletes only resources with the exact generated ownership label. The volume and plaintext temporary file exist only for the isolated drill. A process/host crash may interrupt cleanup: inspect exact `otziv-pg-drill-*` owner-labelled resources and restricted `otziv-pg-*` temporary directories; confirm no running drill before deleting those specific resources. Never use broad Docker cleanup or recursive deletion against a guessed path. Use an encrypted work filesystem because deletion is not secure erasure on SSDs/snapshots.

`compare-identities` accepts restricted normalized arrays of `{subject, realmId, roles:[businessRole,...]}` from the restored databases. It rejects orphan/duplicate links and role drift and prints counts only. Normalize **business roles** explicitly in the protected export query; do not silently compare arbitrary inherited Keycloak roles. Null local subjects represent intentionally unlinked accounts; at least one linked identity must be checked.

The full-system gate remains a separate isolated environment. The executable real fixture below proves the component restore path for generated fixture data. Production still requires MySQL via the [R0 drill](../../docs/R0_BACKUP_RESTORE_DRILL.md), the actual paired PostgreSQL source, exact object versions and secrets, and measured full RTO/recovery-point age against agreed policies. The PostgreSQL-only result continues to report `fullSystemRestore=NOT_PROVEN`.

## Real full-system fixture

```sh
node --test infrastructure/recovery/system-bundle.test.mjs
node infrastructure/recovery/full-system-fixture.mjs otziv-app:finalization-proof otziv-keycloak-security:local-proof /restricted/evidence/unique-run
```

This manual command requires cached images and a local Docker endpoint. Resolve the two application image references to the intended tested build; the command immediately freezes their immutable Docker image IDs and records all six runtime IDs. It starts only uniquely labelled disposable MySQL, PostgreSQL, Keycloak, MinIO, application and Node runner containers on one `--internal` network, with no published ports and no Docker socket inside a container. It does not call the stock database restore, contact a production source, or deploy a service. Its fixed resource ceilings total approximately 4.2 GiB; source services and their data are removed before allocating restored services. Messaging, payments, lead dispatch/receiver and unrelated jobs are disabled; physical network isolation provides the additional outbound fence. The issuer image must contain the generation SPI and the app must support enforced issuer generations. Realm provisioning creates a fixture password flow, a generation session-note mapper, explicit service-account permissions and a generated test user; it does not replace a production realm's flows.

The command mutates real application MySQL state, creates a real issuer user/roles/session, verifies login and refresh through `/api/me`, reveals an encrypted credential through the real application, and uploads an image through the real manager endpoint into versioned MinIO. Capture stops the actual app, issuer and object server and inspects their stopped state, verifies no application database sessions remain, and checks MySQL `super_read_only` and PostgreSQL transaction read-only controls. MySQL SQL, PostgreSQL custom dump, the stopped MinIO volume (including original object versions), and the actual generated secrets are independently encrypted and bound to one HMAC-authenticated manifest. The capture is performed while the technical fence remains in force, rather than trusting an operator checkbox. This is an offline, single-owner fixture: it does not claim a distributed snapshot protocol for a live fleet.

Restore authenticates every component and exact runtime image identity before allocating replacement data services. It restores real MySQL/Keycloak schemas and state, real versioned object data, and the original credential/application keys. With application ingress still absent it invalidates restored online and offline sessions and replaces the realm's RSA signing key. Only then does it start the restored app and prove old JWT/refresh rejection, fresh login/refresh acceptance, credential decryption, strict audit writing, and resolution of the database's original object URL to the exact original version and bytes. The fixture's policy invalidates all its restored sessions; a production cutover must inventory all affected realms and credentials before opening access.

`system-bundle.mjs` is a **bounded fixture format**, not a replacement for the streaming production PostgreSQL backup CLI: four fixed components, at most 64 MiB plaintext per component, AES-256-GCM with slot-bound AAD, ciphertext/plaintext hashes, and an HMAC over the full manifest. Wrong keys, altered manifests, swapped/missing components or incomplete fence evidence fail closed; partial plaintext outputs are removed. No production-sized dump support is implied. The separate environment variable `RECOVERY_ENCRYPTION_KEY_BASE64` may supply an independently held 32-byte key. If omitted, the fixture creates an ephemeral key and destroys it after verification; its encrypted evidence bundle then intentionally cannot be reused as a recoverable backup. The key is never included in the manifest or output. All generated passwords and tokens remain in private temporary files or encrypted secrets; Docker receives environment secrets by variable name, not credential-bearing process arguments.

Use a new restricted output directory for each run. `proof.json` records actual checks, cleanup and elapsed time; it explicitly distinguishes `PROVEN_FOR_THIS_REAL_ISOLATED_FIXTURE` from production independence and agreed business RPO/RTO. A local fixture cannot establish independent-account storage, remote retention, real production key custody, Android signing recovery or external messenger session recovery. Those actual recovery sources and a full production-sized paired drill remain operator inputs, not synthetic success fields. Plaintext scratch is removed and owner-labelled Docker resources are checked before deletion; interrupted runs require inspection of the exact `com.otziv.system-proof.owner` value and restricted `otziv-system-proof-*` scratch directory. Never use broad Docker pruning. Use an encrypted work filesystem and restricted Windows ACLs where applicable; deletion is not secure erasure.

If any component is missing/corrupt, the recovery key is unavailable, or the requested image IDs differ, stop before opening application access. Retrieve the exact authenticated component/version or recover the independently held key; do not create an empty replacement, mix another capture, disable authentication or silently retarget a different runtime. If the complete set cannot be recovered, preserve the failed evidence and retain the maintenance fence while the responsible owner chooses an explicit degraded-recovery procedure. The fixture does not authorize such a procedure automatically. An authentic manifest for a different runtime is a separate tested refusal case, independent of manifest corruption.

Install `otziv-postgres-backup.service` and a completed copy of `.timer.example` only after the external configuration and schedule are chosen and preflight/real isolated restore pass. The service runs alongside existing MySQL backup. Rollback disables only this new timer; preserve remote objects, receipts, keys and the existing MySQL schedule. Repeat an isolated drill on the exact rollback release.
