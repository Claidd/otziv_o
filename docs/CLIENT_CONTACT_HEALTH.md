# Контроль недоступных клиентских чатов

Владелец данных: `client_messages` (messaging). Таблица `client_contact_health` содержит только
свидетельство доступа к маршруту; компании, заказы, оплаты и журналы отправки не изменяются.

Компания **«На стопе» без действующих заказов и открытых заявок** при подтверждённой
недоступности/отсутствии привязки исключается из новых автоматических клиентских отправок. Вместо замечания
менеджеру она находится у ADMIN/OWNER: **Справочники → Мониторинг → Недоступные чаты компаний на стопе**.
В мобильном мониторинге есть одноимённый раздел. Компания не удаляется, квартальный цикл не сбрасывается.
Появление действующего заказа или открытой заявки немедленно меняет принадлежность проблемы:
исключение перестаёт действовать, недоступный контакт показывается менеджеру.

Состав действующих заказов и открытых заявок берётся из тех же настроек и условий, что у
`ArchiveCompanyMessageCandidateRepository`: по умолчанию завершённые статусы — «Оплачено,Архив,Бан»,
открытые заявки — PENDING/FAILED. Статус компании для этого административного исключения — «На стопе».

## Доказательства и ограничения

- Telegram: `getChat` + `getChatMember` **самого бота**, без отправки, вступления или автоматической
  миграции. Только явные 400/403 chat_not_found/blocked/removed/permission_denied или отсутствие
  членства/права отправки дают UNAVAILABLE. Это не утверждение, что группа удалена для всех.
- WhatsApp: актуальный доступный снимок групп с `not_member` либо ранее подтверждённый отказ
  доставки (ACK −1). `not_listed`, неполный/устаревший список, тайм-аут и `refused` дают UNKNOWN;
  `not_admin` означает невозможность получить приглашение, но не отсутствие членства.
- MAX: отсутствие привязки видно; без надёжного свидетельства провайдера доступ остаётся UNKNOWN.
- Участие клиента отдельно не отслеживается: выход произвольного участника не доказывает, что
  клиент перестал получать сообщения. Согласие/отказ от уведомлений остаются отдельной настройкой.
- UNKNOWN не создаёт новое исключение и не снимает уже подтверждённое. После изменения маршрута
  старое ограничение остаётся до положительной проверки нового чата. Квитанции доставки не подменяются.

Проверки ограничены 10 компаниями в минуту, повторный обход — через 6 часов. Отдельный поток
не блокирует очередь отправки. Ошибка попытки и изменение ссылки ставят вне транзакции
дополнительную проверку в ограниченную очередь; периодический обход страхует перезапуск процесса.
Конкурирующие проверки сравниваются по времени начала, старый ответ не затирает новый.

## Публичные контракты

| API | Владелец → потребитель | Авторизация и транзакции |
| --- | --- | --- |
| `TelegramChatAccess` | Telegram → client_messages | Только внутренние проверки текущего бота; сетевой вызов NOT_SUPPORTED, без мутаций/отправок. На локальном стенде выключенный транспорт возвращает UNKNOWN. |
| `WhatsAppChatAccess` | WhatsApp → client_messages | Только чтение снимка аккаунта и подтверждённых блокировок; не вступает в группы и не меняет приглашения. |
| `ClientContactHealth` | client_messages → manager_control | Результаты для текущего маршрута, текущих заказов и менеджера. Чтение не меняет бизнес-данные. `recheck` вне внешней транзакции сохраняет только собственное свидетельство. |

HTTP `/api/admin/client-messages/contacts` и `/{id}/recheck` доступны только ADMIN/OWNER.
Перепроверка не разрешает повтор UNKNOWN и не является отправкой. После доступного чата
обычный автоответчик снова проверяет master/pause/scenario, сроки, рабочие окна, лимиты и интервалы.
При удержании неготового предложения следующая проверка очереди назначается через сутки;
исторические PREPARED/UNKNOWN остаются в прежнем процессе сверки. Настройки автоответчика не обходятся.

При действующих заказах первая фактическая ошибка/UNKNOWN становится замечанием без ожидания
порога повторов. Ожидание рабочего окна, лимита, паузы, ручного контакта и живой транзакции ошибкой не считается.
Данные менеджерской панели обновляются существующей проекцией (обычно до 30 секунд).

## Проверка выпуска

18–19 ноября 2026: 205 профильных серверных тестов прошли, включая MySQL, авторизацию,
границы модулей, паузу/возобновление и ограничения автоответчика. Тест компонента проверяет
отмену без POST и ровно одну перепроверку после подтверждения. Веб и Android собраны.

На свежей копии БД VPS через `prod-like-smoke.ps1` и интерфейс проверены: отсутствие запроса
при отмене, UNKNOWN с сохранением ограничения, исчезновение компании из административного
списка при появлении заказа и конкретная карточка менеджера. Проверка повторена в платёжной
песочнице: сообщений, ссылок банка и документов — 0; историческая UNKNOWN-операция не изменилась.
Мобильный раздел проверен в обеих темах. Android 1.0.93 подписан и проверен штатным verifier.
