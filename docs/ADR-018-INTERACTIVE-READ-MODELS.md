# ADR-018: сохранение данных при ускорении заказов, команды и рейтинга

Дата: 2026-09-12. Продолжение ADR-017.

## Контекст

После предыдущего выпуска VPS ещё не обеспечивал P95 <100 мс: повторные
заказы около 119 мс, команда около 189 мс, рейтинг около 155 мс. Это оценки
серверной HTTP-гистограммы, а не времени загрузки браузера. Чтение исторических
событий команды занимало около 60 мс даже после прогрева. Повторялись запросы
сумм общих счетов, области доступа и финансовых агрегатов.

## Решение

Содержимое страниц, поля карточек, размеры страниц, фильтры и финансовые
правила сохраняются. Командные операции, авторизация и проверки безопасности
не заменяются результатами фоновых расчётов.

- Общие счета: один SQL возвращает идентификаторы страницы и оба счётчика.
  Предикаты карточек и связанных заказов остаются различными; пустая страница
  сохраняет счётчики, порядок имеет явное разрешение равных дат по id.
- Стоимость и статистика негативных отзывов рассчитываются одним текущим
  чтением. Карточки общих счетов сохраняют суммы статистики входящих заказов:
  повторное обогащение по синтетическому отрицательному id раньше могло их стереть.
- `TeamDirectoryReader` принадлежит модулю пользователей и возвращает все
  поля простой карточки, включая идентификатор изображения, без загрузки
  содержимого аватара и полной сущности. Пустая область менеджеров закрывает доступ.
  Расширенные OWNER-расчёты сохраняют существующий путь.
- Область повторного использования идентичности и отпечатка членства ограничена
  одной синхронной сборкой ответа. Следующий запрос читает актуальное членство;
  транзакция записи сбрасывает сохранённые значения, выход с исключением очищает область.
- Финансовая административная сводка читает четыре независимых агрегата одним
  `UNION ALL` без перемножения строк. Начальные балансы берутся из текущих профилей.
  LIVE/SHADOW, возвраты, резерв, фактический получатель и границы периода прежние.
  Кэша денежных сумм нет. Канонические дневные начисления суммируются по пользователю
  в SQL с сохранением семантики дневного количества записей.

Публичный API `TeamDirectoryReader` явно экспортируется владельцем `identity`.
Его потребители — `PersonalServiceImpl` для уже авторизованных страниц команды
и системная задача `TeamPatternSnapshotJob` для подготовки закрытых производных
фактов. `allActive` предназначен для существующего административного сценария
или системной задачи; `forManagers` принимает область, которую потребитель
получил через прежние проверки доступа. API не принимает SQL-фрагменты и не
возвращает сущности, пароли или содержимое изображений. Все методы выполняются
в read-only транзакции REQUIRED; внутри транзакции фонового пакета присоединяются
к ней. Экспорт ограничен этим классом, общий доступ к внутренностям identity
не расширяется.

## Исторические закономерности команды

Миграция 1.10.318 добавляет производную таблицу помесячных фактов каждого
специалиста: публикации, блокировки аккаунтов, восстановления, сетевые эпизоды
и их дневные значения. Денежных данных, полномочий и готового состава команды
в этой таблице нет. Корреляции, предупреждения и сравнения по-прежнему вычисляются
по текущему разрешённому составу команды.

Фоновая задача работает каждые 30 секунд на существующем отдельном планировщике.
Она использует аренду с fencing token, транзакцию на пакет до 25 специалистов,
атомарный контрольный указатель, до четырёх пакетов за запуск, ограничение времени
транзакции 20 секунд и прекращение новых пакетов через 15 секунд. Подготавливаются
текущий и предыдущий месяцы; более старые месяцы читаются исходным способом.
Для больших команд полный цикл может превысить срок свежести: это ухудшает
скорость через fallback, но не допускает чтение более старых фактов.

Чтение принимает только полный набор, соответствующий текущим worker/user id,
границам периода и времени базы данных от 0 до 60 секунд. Проверяются диапазоны
дней, отсутствие повторов, неотрицательные счётчики и совпадение месячных сумм
с дневными. Устаревшие, неполные, несовместимые или недоступные данные приводят
к каноническому расчёту. Внешний кэш страницы также проверяет время сводки,
чтобы его TTL не продлевал разрешённую задержку. Интерфейс показывает время
исторических данных в часовом поясе Иркутска.

Это явный компромисс свежести только для исторической аналитики: задержка
до 60 секунд. Пересчёт использует прежние запросы и прежние правила, включая
начало наблюдения сетевых событий. Обновление страницы не обходит этот срок.
Отключение: `otziv.projection.team-pattern.enabled=false` (Spring property);
задача прекращает обновления, новые сборки используют исходные запросы.
Старое приложение совместимо с добавленной таблицей; откат не требует её удаления.

## Проверки и эксплуатация

Реальные MySQL-тесты сравнивают старые и новые финансовые итоги, область
пользователей, сортировку и счётчики; отдельно проверяются срок свежести,
повреждённые строки и откат транзакции. Тест полного цикла сравнивает все
закономерности и показатели между каноническим расчётом и производной таблицей.
Используются существующие метрики `otziv.projection.*` с ограниченными тегами,
а также сегменты рейтинга `manager-performance`, `score-rows`, `financial-summary`
и `financial-facts`. В метках нет идентификаторов пользователей или платежей.

Приёмка скорости — одинаковые сценарии и ограничения ресурсов, отдельно первая
загрузка, повторные запросы и роли; P95, число выборок, ошибки и доля <=100 мс.
Успех локальных проверок не означает достижение SLO на VPS. Деплой выполняется
штатным корневым скриптом после обязательного CI, с резервной копией и проверкой
ревизии, миграции, состояния сервисов и повторными серверными замерами.
