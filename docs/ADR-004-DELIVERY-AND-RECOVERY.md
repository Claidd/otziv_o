# ADR-004. Исходящие операции, UNKNOWN и восстановление очередей

Статус: принято; включение каждого внешнего канала требует своей приёмки.
Дата: 2026-09-07. Владельцы: leads/performers/messaging. Пункты: P04/P05/P13–P16.

Изменение MySQL и отправка во внешнюю систему не образуют общую транзакцию.
Потерянный ответ может означать уже доставленное сообщение. Повтор с новым UUID
не сохраняет идентичность исходной бизнес-операции.

Сохраняем durable intent вместе с бизнес-изменением. Operation ID и содержимое
envelope определяются до отправки и сохраняются для последующих попыток. Relay
атомарно захватывает bounded due batch, освобождает claim-транзакцию перед сетью
и принимает результат только с действующим fencing token. Подтверждённый результат
повтора возвращается без новой отправки. Другой envelope с тем же ID отклоняется.

Различаем PENDING/RUNNING, подтверждённую доставку, определённый отказ и UNKNOWN.
Lease/timeout/disconnect не превращают UNKNOWN в доказанную неотправку. Telegram
и прочие адаптеры без сквозного receiver dedup не получают обещание exactly-once.
Операторское разрешение UNKNOWN сохраняет actor, причину и использованное evidence.
TTL предложения начинается от подтверждённой доставки, а не от создания intent.

Для legacy финансовых уведомлений общий счёт сохраняет идентификатор текущей
отправки и подтверждение в своей prepare-транзакции (V303). Изменение старых
UI timestamps после ошибки не создаёт новую операцию. Поздний finish сверяет ID;
замена реквизитов и режима оплаты блокируется до сверки незавершённого сообщения.
Подтверждённая начальная отправка повторно возвращает результат, а явное следующее
напоминание получает отдельную сохранённую occurrence.
Старый in-progress/UNKNOWN без сохранённого идентификатора не получает новый ID
после истечения таймера: требуется отдельная историческая сверка перед включением
отправок. Успех текущих операций не доказывает исход таких старых попыток.
Барьер действует и в общей stale-recovery функции: предшествующее чтение или
смена маршрута не может стереть неопределённость до следующей отправки.
Учитываются также сохранённые прежним кодом message_send_stale/route retry stale.

WhatsApp хранит неизменяемый зашифрованный envelope; повтор не меняет канал,
получателя и текст вслед за настройками компании. Для Telegram/MAX V304 хранит
хеш полного envelope, включая платёжную copy metadata, и постоянный барьер до
внешнего вызова. PREPARED/UNKNOWN после сбоя или перезапуска не допускает второй
POST. Receipt возвращается повторно; определённый отказ допускает только прежний
envelope. Оператор может подтвердить доставку точными token/hash/receipt и причиной,
которая сохраняется в аудите. Истечение времени не разрешает повтор.
Подробности: [client message fence](CLIENT_MESSAGE_OPERATION_FENCE.md).

Limiter удерживает permit до завершения фактической работы и cleanup. Поддерживаемая
отмена может остановить работу, но закрытие HTTP-сокета само по себе не освобождает
ресурсы и не определяет исход сообщения. Running/cleanup/timeout/rejected измеряются
без получателей, токенов и других меток высокой кардинальности.

Исторический payload нельзя реконструировать из текущего состояния сущности как
достоверное прежнее событие. Используем read-only classification, явные причины,
upper bound/cursor/checkpoint и фактические changed/conflict counters. Неизвестная
история сохраняется; ограниченная миграция не объявляет все старые сообщения SENT
или PENDING. Применённые Flyway scripts неизменны. Offline migration tooling требует
технического write fence, восстановления исходных значений и проверки незавершённой
maintenance перед запуском writers.

Legacy синхронные уведомления статуса заказа сохраняют прежнюю связь результата
отправки с переходом статуса. Отдельная фиксация reservation не превращает весь
этот сценарий в transactional outbox: внешняя доставка может предшествовать commit
вызывающей order-транзакции. Эта остающаяся семантика должна быть учтена при
отдельном переходе на асинхронную доставку; стабильный ID не является доказательством
атомарности денег/статуса и сети.

Общий R6 outbox подключается отдельно для event type после проверки lease/deadline,
receiver identity/order, retention, mixed-version handler и UNKNOWN policy. Для
неподходящего транспорта допустима отдельная domain state machine.
Опора: [R6](R6_TRANSACTIONAL_OUTBOX.md), [outbound protocol](../whatsapp/OUTBOUND_OPERATIONS.md),
[rollout](ARCHITECTURE_ROLLOUT.md).

`c_companies.api.MissingWhatsAppRoute` принадлежит companies и вызывается messaging
только для уже разрешённого автоматического уведомления. Скалярный snapshot читается
в короткой read-only транзакции; проверка точной invite-ссылки у выбранного WhatsApp
клиента выполняется вне неё. Companies сохраняет найденный groupId условной записью:
ссылка не изменилась, включая регистр invite-кода, привязка всё ещё пуста и компания
не заблокирована. Обычная очередь продолжает тот же business occurrence только до
первой фиксации transport envelope. Сохранённые операции, деньги, статусы заказа
и права интерактивных команд этот контракт не меняет.

`c_companies.api.CompanyChatLinkChanged` принадлежит companies и публикуется общим
сервисом после разрешённого сохранения ссылки из любого редактора. Старые ID всех
мессенджеров очищаются в транзакции правки. После commit messaging проверяет точную
новую WhatsApp-ссылку вне транзакции и условно сохраняет адрес; карточки с тем же
invite-кодом получают подтверждённый ID. До проверки V361 сохраняет признак ожидания:
название группы, входящее сообщение и ID другой карточки не подтверждают новую ссылку.
При недоступности шлюза проверка повторяется плановой синхронизацией. Отмена/rollback
не запускают проверку. Событие не разрешает отправку и не меняет уже сохранённые
transport envelopes, историю доставки и статусы заказов.

Отвергнуты: log-only retry, новый UUID на каждом повторе, новые producer-сценарии с отправкой до commit,
слепой replay UNKNOWN и изменение прошлых SQL ради зелёного Flyway.
Пересмотр нужен при изменении receiver guarantees или retry/retention horizon.

Дополнение владельца от 01.11.2026: для уведомления о полученной оплате и связи
по архивному заказу разрешено одно отдельное информационное уведомление с риском
дубля. Это новая occurrence, а не replay исходного UNKNOWN. `client_notification_followups`
хранит исходный ID, детерминированный ID повтора, версию разрешившей политики,
зашифрованный снимок источника/текста/получателя, результат и квитанцию. Старый
provider ledger не очищается и не объявляется «не отправлено».

Сначала проверяется история исходной операции и подтверждается точная invite-ссылка
у текущего WhatsApp-клиента. После первого сохранения намерения выдерживаются
15 минут (от наблюдения UNKNOWN, а не от даты старого платежа). Перед dispatch
повторно проверяются бизнес-контекст, настройки отправки и получатель. Глобальная
пауза между такими отправками — минута. Уникальный ключ и транзакционный claim
защищают от двух обработчиков; сеть выполняется вне транзакции. Известный отказ
до отправки допускает ту же occurrence, таймаут/потерянный ответ — только чтение
квитанции. Третьего автоматического сообщения для исходной операции нет.

Для оплаты отправляется только подтверждение уже полученной суммы: деньги,
банковские документы и следующие заказы не создаются. Возврат и изменение
исходного платежа блокируют отправку. Для архива повторно проверяются цикл
компании, активные заказы, ответ клиента и рабочее время; используется нейтральное
сообщение о связи по завершённому заказу. Квитанция повтора и применение результата
в бизнес-задаче фиксируются одной транзакцией. Исходный снимок остаётся в аудите.
Остальные финансовые команды и отправки документов не получают разрешение на
повтор из этой политики.
