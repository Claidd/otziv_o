# Одна рабочая версия проекта

Основной каталог на этом компьютере: `E:/Works/Projects/otziv`.
Рабочая и выпускаемая ветка: `main`. Все готовые изменения должны попасть сюда
до деплоя. `origin/main` — та же ветка на GitHub, а не отдельный набор функций.

«Группа 1/2/3» в проверках — параллельные части серверных тестов одной версии.
Их разделение ускоряет проверку и не разделяет изменения приложения.

## Обычный выпуск

1. Проверить `git status`, обновить сведения через `git fetch origin`, сопоставить
   локальные изменения и открытые PR с ожидаемым составом выпуска.
2. Сохранить и объединить все законченные доработки в основном каталоге. Не
   заменять этот шаг созданием чистого клона. Запустить проверки затронутых функций.
3. Зафиксировать изменения в локальном `main`. Для обязательных проверок GitHub
   использовать один PR всего выпуска, а не отдельные незавершённые ветки функций.
   Слияние с сохранением коммитов позволяет затем обновить локальный `main`
   командой `git merge --ff-only origin/main` без сброса локальной истории.
4. Дождаться успешных проверок итогового `main`, обновить основной каталог и
   запустить быстрый выпуск `./deploy.ps1 -Tag <название-выпуска> -ImageTransport Direct`
   из него. При явном указании
   `-ProjectFilesRoot` это каталог `E:/Works/Projects`, содержащий `otziv`.
5. Проверить на VPS установленную ревизию, состояние сервисов и каждую ожидаемую
   функцию. Наличие здоровых контейнеров само по себе не доказывает состав выпуска.

Проверка деплоя требует именно `<ProjectFilesRoot>/otziv`, чистый `main`, совпадение
с текущим `origin/main` и успешный CI этой версии. Чистая соседняя копия больше не
служит обходом незаписанных изменений основного проекта.

## Быстрый деплой — обязательный вариант по умолчанию

`deploy.ps1` по умолчанию выбирает прямую доставку (`Direct`) готовых проверенных
образов из CI на VPS. Неизменившиеся образы используются повторно; при установке
перезапускаются только сервисы с изменившимся образом или конфигурацией.
Для обычного исправления не нужно вручную пересобирать всё на компьютере или VPS,
запускать старые сценарии напрямую либо добавлять `-FullRollout`.

`-ImageTransport Local` оставлен для случая, когда прямая доставка недоступна.
Полный режим нужен только при обоснованной технической необходимости; если
автоматический анализ не может доказать безопасное сохранение сервисов, он
указывает причину перехода к полному перезапуску. Пользователю сообщается причина
такого отступления. Проверки CI, резервное копирование и проверка здоровья
сохраняются в быстром режиме.

## Отдельное проверенное обновление OpenSSL в PostgreSQL

Только для принятой пары C23 PostgreSQL и C23/C24 Keycloak доступен явный параметр
`-CoordinatedSslRefresh`. Он дополняет быстрый `Direct`: после обязательной
проверенной резервной копии основной БД под общей блокировкой выпуска сохраняется
дополнительная зашифрованная копия PostgreSQL на VPS, останавливается авторизация,
проверяются записи всех 102 таблиц и устанавливается образ с обновлённым OpenSSL.
При ошибке отдельного шага восстанавливается прежний образ на том же томе.
Версия PostgreSQL, схема и параметры запуска остаются прежними. Обычный запрет
замены образа БД поверх существующего тома сохраняется; параметр требует точного
успешного CI `main`, принятой пары образов и разрешения владельца на этот выпуск.
Данные авторизации с VPS не выгружаются на компьютер. Затем продолжается обычный
выборочный деплой сервисов, без `-FullRollout`.

C24 Keycloak наследует проверенное обновление OpenSSL C23 и заменяет только
Jackson Databind на исправленную 2.21.7 в сервере и административной утилите.
Полное сравнение файлов, содержимого и прав ZIP подтверждает сохранение остальных
классов. Допуск пары требует повторных проверок сохранения всех таблиц, входа,
ролей, восстановления и отката именно опубликованного C24 образа.

## Подготовка и измерение времени

`-CheckOnly` сохраняет прежний смысл: чтение GitHub CI без Docker и VPS.
`-PreflightOnly` дополнительно создаёт пакет из точного коммита, проверяет его
комплектность, настройки резервного копирования и доступное место на VPS.
Образы при этом не доставляются и установка не запускается. Обычный запуск
делает эту подготовку автоматически до больших загрузок и затем использует
тот же архив с проверкой SHA-256. Локальные игнорируемые файлы в пакет не входят.

Каталог evidence каждого выпуска содержит `timing.json` (проверка main,
подготовка, доставка, резервная копия, установка и проверка образов),
`ci-timing.json` (фактическое время CI, очередь и цепочка зависимостей) и
`verified-source.json`. Время параллельных заданий не складывается как общее
время выпуска. Для сопоставления PR и main можно выполнить:

```powershell
python -B infrastructure/scripts/prod/release_metrics.py --run-id <PR-run> --run-id <main-run> --output diagnostics/release-timing.json
```

Известные сценарии доставки запускают контракты выпуска; неизвестные пути и
изменения общих политик по-прежнему расширяют проверки до полного набора.
Конфигурации мониторинга проверяются на неизменяемых production-образах;
изменение Dockerfile выбирает сборку соответствующего кандидата. Сканирование
всех выпускаемых образов остаётся свежим. Кэши слоёв имеют отдельные ключи
компонентов, а runner проверок мониторинга собирается один раз на попытку CI.

Повторное использование образа сравнивает его реальные входы сборки и рецепт
Buildx. Изменение доставки не меняет байты образа; изменение политики требует
нового сканирования по текущим правилам. В отчёте отдельно записываются отпечатки
сборки, политики и доставки, а также причина новой сборки или повторного использования.

Серверные тесты распределяются целыми классами по длительности JUnit. Профиль
`backend-test-durations.json` содержит источник замеров; обновлять его следует
по успешному полному прогону. Новые классы получают детерминированную оценку,
проверка всех классов, вложенных тестов, пропусков и дублей сохраняется.

## Один координатор выпуска

Перед изменениями проверяйте `release_session.py status`. После фиксации кода
в чистом main координатор выполняет `begin --owner <задача>` и сохраняет token.
Остальные задачи откладывают запись файлов до завершения сессии. Это правило
сотрудничества; оно не является запретом файловой системы. Скрипт деплоя
дополнительно блокирует второй запуск технически, а VPS сохраняет свой отдельный lock.

Срок подготовительной сессии — четыре часа; продлить её может владелец через
`renew --token <token>`. После слияния PR выполняются обновление main и
`advance --token <token>`: допустим только новый коммит с тем же деревом файлов.
Выпуск запускается обычной командой с `-ReleaseSessionToken <token>`.
Сессия действующего процесса деплоя не истекает посреди установки; остановленный
процесс определяется по PID и времени его создания. Самостоятельный запуск
`deploy.ps1` создаёт сессию автоматически. Чужие сессии принудительно не закрывать.

## Перенос результатов тестов

Владелец разрешил включение проверяемого переноса 27.09.2026. Репозиторная
переменная `OTZIV_CI_TEST_REUSE_ACTIVE=true` включает его после успешного полного
сравнения; без этого значения работает `shadow` с обычным выполнением тестов.
Обязательные задания текущего main сохраняются. Сначала проверяется успешный
PR, слитый именно в этот main, затем каждое задание сравнивает фактически
установленные инструменты. Только при совпадении пропускаются повторные тяжёлые
шаги. Проверки npm/Maven, образов, секретов, SQL и миграций выполняются заново.

Доказательство связывает actual checkout и полное дерево Git, workflow,
поколение hosted runner, GitHub Actions check, исходный run/attempt и digest
артефакта. Дополнительно сравниваются реальные версии и байты Node/JDK, системные
пакеты, Maven и Docker, закреплённые образы БД, установленный Chromium и Android
SDK/Gradle для соответствующих проверок. Серверные группы используют точную
версию Java из предварительной проверки; каждый свежий shard сохраняет свою
среду. Смешанные среды не дают пригодного для переноса доказательства.
При отличиях или отсутствии результата выполняются обычные проверки.
Изменённые доказательства и неуспешная последняя попытка не заменяются старыми
зелёными результатами. Новые артефакты привязаны к точной попытке CI: после
частичного rerun без нужного отчёта следует выбрать **Re-run all jobs**.

Manifest содержит конечные решения всех восьми заданий текущей попытки после
сверки среды, а не предварительный список кандидатов. Перед деплоем повторно
проверяется, что исходный PR run не был перезапущен или отозван. Для отключения
оптимизации достаточно установить `OTZIV_CI_TEST_REUSE_ACTIVE=false`: следующий
полный запуск main выполнит обычные тесты с диагностическим сравнением.

Первая установка оптимизации требует полных проверок. Фактический выигрыш
сравнивается по следующим трём обычным выпускам, без искусственных production
деплоев. Цели 15–25 минут для UI и 20–35 минут для backend остаются ориентирами,
пока реальные замеры всего пути до проверенного VPS их не подтвердили.
