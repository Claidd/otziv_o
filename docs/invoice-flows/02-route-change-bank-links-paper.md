# Смена получателя и способа оплаты, банковские ссылки, бумажные счета
> Для ИИ-агентов. Состояние кода: рабочее дерево main на 2026-11-10.

Соглашения. Ссылки даны от корня репозитория как `путь:строка`. Ссылка без пути (двоеточие и номер строки в обратных кавычках) относится к тому же файлу, что и предыдущая ссылка в той же строке документа (пункт списка или строка таблицы); если в строке её нет — к файлу, объявленному выше словами «Файл раздела», «Файл» или «далее RW/PRW/BRC…». «Общий счёт» = `CommonInvoice`, «счёт заказа» = `PaymentLink`, «ref» = `CommonInvoicePaymentRef` (банковская попытка общего счёта). Ничего не запускалось: документ составлен чтением кода и тестов. Номера строк сняты с рабочего дерева (незакоммиченные правки + локальный коммит `24fd78296`) 2026-11-10 около 19:50 местного времени. В это время параллельная задача дописывала выдачу номера карты названному менеджером получателю, поэтому строки в затронутых ею файлах могут снова сдвинуться (список файлов — в разделе «Не проверено»).

## Коротко — 8–12 правил, которые нельзя нарушать

1. Смену запускает только сотрудник с ролью ADMIN/OWNER/MANAGER (`backend/src/main/java/com/hunt/otziv/common_billing/controller/CommonBillingAdminController.java:154-176`, `backend/src/main/java/com/hunt/otziv/payments/controller/ManagerPaymentController.java:45-65`). Клиент может только попросить менеджера; причина в журнале так и записывается: «…по просьбе клиента» (`backend/src/main/java/com/hunt/otziv/common_billing/service/CommonInvoicePaymentRouteWorkflow.java:319`).
2. Любая смена требует `confirmedUnpaid=true`; без него сервер отказывает (`backend/src/main/java/com/hunt/otziv/common_billing/service/CommonInvoicePaymentRouteWorkflow.java:242-244`, `backend/src/main/java/com/hunt/otziv/payments/dto/PaymentRouteChangeRequest.java:9`, `backend/src/main/java/com/hunt/otziv/paper_billing/PaperBillingService.java:106`).

Файл раздела: `backend/src/main/java/com/hunt/otziv/common_billing/service/CommonInvoicePaymentRouteWorkflow.java` (далее RW).

**Входы.** Все требуют роль и `requireCanMutateInvoice` (`backend/src/main/java/com/hunt/otziv/common_billing/controller/CommonBillingAdminController.java:401-403`).

**Шаги.**
1. Клиент читает контекст: `canChange`, `blockReason`, `paymentEvidenceToken`, `currentTarget`, `canReissueOwnerBank`, `ownerBankReissueBlockReason`, `ownerManualRoute`, `bankRecipientChangeAvailable` (RW `:159-193`). Если есть незавершённое задание банка, `blockReason` = его сообщение, а `bankRecipientChangeAvailable=false` (`:166-167`, `:192`).
2. Проверка запроса: цель должна быть одной из трёх, `differentRecipient` допустим только с `EMPLOYEE_REQUISITES` → иначе 400 «Для общего счёта можно выбрать реквизиты сотрудника, банковскую ссылку владельца или переиздать ее по актуальному профилю» (`:239-241`); нет подтверждения → 400 «Подтвердите, что клиент ещё не оплатил по прежнему способу» (`:242-244`); `recipientProfileId` с другой целью → 400 «Получателя выбирают только при выдаче номера карты» (`:245-247`).
3. Развилка для `EMPLOYEE_REQUISITES` (`backend/src/main/java/com/hunt/otziv/common_billing/service/BankRecipientChanges.java:90-106`): под блокировкой счёта сверяется токен (иначе 409 «Состояние общего счёта изменилось. Обновите карточку», `:96-97`), затем ищется привязанная неоплаченная банковская операция `bankRecipientRef` (RW `:387-412`). Она есть только если маршрут — банковская ссылка, нет удержаний, бумажного документа и признаков оплаты, последний ref в статусе CURRENT/INIT_PREPARED/безопасном конечном и совпадает с привязкой счёта. Нет операции → шаг 4; есть → задание банка (раздел «Банковская ссылка»), названный человек сохраняется в задании (`backend/src/main/java/com/hunt/otziv/common_billing/service/BankRecipientChanges.java:99`).
4. Прямая замена `replaceCommonInvoicePaymentRouteLocked` (RW `:261-374`), одна транзакция:
   - блокировка счёта и ref (`:263-265`); незавершённое задание → 423 (`:266-267`); токен (`:268-272`); причины блокировки (`:273-276`, таблица ниже);
   - `OWNER_TBANK` при уже банковском маршруте → `false`, ничего не меняется и сообщение не шлётся (`:283-285`, `:250`);
   - сумма маршрута должна равняться остатку, иначе 409 «Сумма общего счёта изменилась. Обновите счёт перед сменой способа оплаты» (`:292-297`);
   - блокировка менеджера (`:299`); для `OWNER_BANK_REISSUE` — проверки профиля (`:300-311`);
   - фильтр заданий: `ManualPaymentTaskRoutingFilter.NUMBER`, а при `differentRecipient` — `otherRecipient(прежний userId, прежнее задание)` (`:312-318`; `backend/src/main/java/com/hunt/otziv/payments/service/ManualPaymentTaskRoutingFilter.java:13-20`, `:26-32`);
   - освобождение старого: задание → `taskReceiptIntegrationService.release(invoice, "Способ оплаты общего счёта изменён по просьбе клиента")`, иначе живой резерв → `releaseCommonInvoiceRouteForReplacement(…, "LIVE_COMMON:ROUTE_REPLACED")` (`:319-324`). Резерв переводится в `CANCELED`; если он уже не `RESERVED`/`OWNER_FALLBACK` или по нему есть отметка клиента/подтверждённые деньги — 409 (`backend/src/main/java/com/hunt/otziv/contractor_payments/service/ContractorPaymentLiveRoutingService.java:627-673`);
   - очистка маршрута, статус `PARTIALLY_PAID` при `paidKopecks>0`, иначе `READY`; `sentAt`, `lastReminderAt`, `nextReminderAt`, `lastError` = null (`:325-330`; поля маршрута — `backend/src/main/java/com/hunt/otziv/common_billing/service/CommonInvoiceRouteState.java:19-41`). `invoicePaymentMode` счёта и аккаунта не меняется (в RW `:261-374` нет его установки);

Назвать можно только человека из круга счёта: специалисты его заказов, менеджер, специалисты, работавшие с теми же компаниями, команда менеджера (`:1229-1253`).
