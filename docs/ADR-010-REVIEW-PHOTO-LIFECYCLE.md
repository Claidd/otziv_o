# ADR-010: авторизация и жизненный цикл фотографий отзывов

Дата: 2026-09-08. Статус: реализуется, совместная приёмка в процессе.

Владелец сценария загрузки — storage, владелец принадлежности и ссылки отзыва — orders. Legacy MVC и manager API вызывают `s3.api.ReviewPhotoUploads`; storage обращается к `p_products.api.ReviewPhotoRecords`. API передаёт ID, URL и Authentication, не JPA entities. Это сохраняет существующее направление storage → orders; обратная зависимость orders → storage не вводится.

Перед обработкой изображения и S3 PUT короткая транзакция проверяет actor/scope. Storage регистрирует уникальный ключ в `s3_upload_registry` до PUT. Сам PUT имеет ограниченное время и выполняется без бизнес-транзакции. Следующая транзакция повторно проверяет принадлежность под штатными блокировками, получает актуальную прежнюю ссылку, записывает новую, переводит registry в ATTACHED и сохраняет cleanup intent прежнего ключа. Ошибка любого шага откатывает всю привязку. `enqueueRequired` присоединяется к этой транзакции и не подавляет ошибки.

Обработчик cleanup удаляет объект после commit. Orders держит постоянный запрет повторного назначения удаляемой ссылки (`review_photo_reference_guard`), совместимый с ручным редактором URL. Перед DELETE проверяются текущие ссылки. Если объект используется, удаление откладывается. Прежняя ссылка существующего отзыва остаётся читаемой. Фотография, уже выведенная из использования, может быть загружена заново с новым уникальным ключом.

URL fence и чтение текущих ссылок используют READ_COMMITTED. Сканирование исторических URL выполняется потоково только при фоновой очистке, без блокирования всех отзывов. Это совместимость с существующими вручную введёнными ссылками, включая регистр hostname, стандартный порт, percent encoding, query и fragment. Время сканирования подлежит измерению на восстановленной БД; при росте нагрузки нужен индекс канонических ссылок с полной миграцией всех writers.

UPLOADING/READY имеют срок привязки. После его окончания registry переводится в ABANDONED и создаёт повторяемое задание очистки. Позднее завершившийся PUT уже не может быть прикреплён. ABANDONED хранится как постоянный tombstone и повторно ставит DELETE раз в сутки: удалённый объект может появиться после завершения удалённого запроса даже при смерти исходного процесса. Простое удаление tombstone по времени не используется. ATTACHED сохраняется как история привязки; контроль роста registry относится к capacity-приёмке.

Миграция 308 добавляет таблицы, не переписывает применённые миграции и не очищает существующую S3 cleanup queue. Исторические orphan-объекты автоматически не удаляются: сначала нужна сверка владельца, ссылок и времени создания с отчётом. Старые generic upload-сценарии вне фотографий отзывов этим ADR не объявляются мигрированными.

Приёмка включает настоящий MVC security chain и причинные тесты MySQL: отказ до PUT; изменение владельца во время PUT; конкурентные замены; rollback записи cleanup; crash после PUT и до DELETE; поздний PUT после sweep; запрет повторного назначения удаляемого URL. Отдельно требуется запуск совместного приложения на свежей копии БД штатным `prod-like-smoke.ps1`.
