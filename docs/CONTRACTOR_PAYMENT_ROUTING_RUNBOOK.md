# Маршрутизация счетов в пользу самозанятых: shadow/live runbook

## Назначение и неизменяемые правила

Контур сопоставляет обязательства за фактически выполненную работу
самозанятого с новыми счетами клиентам. Постоянной сущностью является
**платёжный профиль**, а не ежемесячное задание. Месяц используется только как
срез статистики: остаток обязательства не обнуляется и переносится дальше
автоматически.

Для каждого нового счёта действует порядок:

1. текущий специалист карточки;
2. менеджер заказа (если его нет — менеджер компании);
3. действующий маршрут владельца: T-Bank, Альфа-Банк или ручное платёжное
   поручение.

Счёт назначается самозанятому только целиком. Частичного деления одного счёта
между несколькими получателями нет. После выбора получатель и реквизиты
фиксируются snapshot-ом; последующее редактирование профиля влияет только на
новые счета.

Персональный допуск настраивается в разделе «Пользователи» отдельно для каждой
роли пользователя. Выключенный допуск специалиста исключает его только из
выбора получателя нового счёта: система продолжает с менеджером заказа. Если
выключен допуск менеджера или его доступного остатка недостаточно, новый счёт
получает реквизиты владельца. При выключенных допусках обоих кандидатов счёт
сразу остаётся у владельца. Переключатель не удаляет существующий резерв, не
меняет уже зафиксированный snapshot и не влияет на начисления, подтверждения,
возвраты или статистику профиля.

Для общего счёта специалист допустим, только если у каждой входящей позиции
есть один и тот же специалист. Набор `специалист A + позиция без специалиста`
считается смешанным. Для смешанного счёта проверяется менеджер общего счёта,
затем владелец.

Все административные операции с общим счётом, которые читают реквизиты,
повторяют/отменяют маршрут или меняют его платёжное состояние, сначала
авторизуют **неизменяемого получателя allocation**, а уже затем загружают и
изменяют сам счёт. Для ограниченного `OWNER` общий счёт с привилегированным
получателем (`ADMIN`/`OWNER`) возвращает такой же скрывающий `404`, как
несуществующий идентификатор; журналы и списки отфильтровывают такие цели.
Текущий специалист карточки для этой проверки не используется.

## Расчёт доступной суммы

Для профиля рассчитываются независимо:

- начислено;
- зарезервировано отправленными счетами;
- клиент сообщил об оплате;
- подтверждено фактическое поступление;
- отменено или истекло;
- возвращено;
- доступно для новых счетов;
- переплата/кредит, если подтверждено больше актуального начисления.

Базовая формула (подтверждение учитывается за вычетом возвратов):

`доступно = max(0, начислено - net-подтверждено - активный резерв)`.

`RESERVED`, `CLIENT_REPORTED` и неподтверждённый остаток
`PARTIALLY_CONFIRMED` входят в активный резерв, но отображаются отдельно.
Переплата не увеличивает лимит новых счетов: она показывается отдельным
кредитом до появления новых начислений или ручной сверки.

Проверка остатка и создание резерва выполняются под блокировкой платёжного
профиля. Поэтому два параллельных счёта не могут оба использовать один остаток.
Отмена, истечение, перевод заказа/общего счёта в «Не оплачено» или подтверждение
отсутствия перевода освобождают резерв. Повторно подготовленный одиночный счёт
создаёт новый attempt и новый активный резерв. Для общего счёта повторная
попытка после отправки разрешена только при подтверждении, однозначно
привязанном к конкретному allocation/attempt; агрегатного признака оплаты всего
общего счёта недостаточно. При неоднозначности повторная маршрутизация
блокируется до ручной сверки.

Оплата, пришедшая после освобождения резерва, учитывается как позднее
поступление. Она уменьшает доступный остаток и может сформировать переплату;
это не позволяет назначить ту же сумму ещё раз.

Если общий счёт уже имеет хотя бы одну предыдущую платёжную попытку или
частичное поступление, он не назначается самозанятому. Агрегатная сумма общего
счёта не доказывает, какому получателю относился последующий возврат; до
появления recipient-bound payment ledger такой счёт целиком остаётся на
маршруте владельца.

## Начисления и перераспределение работы

Обязательство фиксируется после фактического завершения работы, до оплаты
клиентом. Клиентская оплата больше не создаёт это обязательство: она только
погашает выбранную часть и проходит стадии сообщения клиента и фактического
подтверждения. Дата начисления — подтверждённая дата выполнения в business-zone,
а не дата запуска repair или дата оплаты.

Каждый валидно классифицированный источник выполнения имеет идемпотентный ключ
и неизменяемый marker. Marker без денежной строки допустим только для источника,
который доказан, но по правилам не создаёт нового начисления: например, он уже
входит в opening balance или соответствующее вознаграждение отключено. Неполное
post-cutoff доказательство никогда не закрывается пустым marker.
Повторный callback или repair синхронизирует исходную атрибуцию и не читает
заново уже изменившегося менеджера, специалиста, коэффициент или состав работ.
Отмена выполненной на границе или после неё дополнительной работы оформляется
отдельным отрицательным начислением на дату отмены тем же получателям;
историческая строка месяца выполнения не удаляется и не переписывается. Для
работы до границы действует явная корректировка opening balance, описанная
ниже. Для неоднозначной исторической даты автоматический перенос запрещён —
нужен датированный импорт/корректировка.

После границы доказательства выполнения проверяются до записи любой строки или
marker. Число опубликованных результатов должно точно совпадать с объёмом
заказа; у каждого результата обязательны дата публикации и неизменяемый
исполнитель. У выполненной дополнительной задачи обязательны дата, положительная
сумма и исполнитель. Пропущенный исполнитель не заменяется текущим специалистом
карточки. Менеджер фиксируется единым resolver-ом: менеджер заказа, а при
синхронном завершении — текущий менеджер компании. Для исторического repair
менеджер компании не считается доказательством прошлого назначения, потому что
он мог смениться. Любая неполнота даёт конфликт, durable backoff и блокирует
LIVE-readiness без частичного начисления и без пустого marker.

### Неизменяемая граница нового учёта

Граница задаётся настройкой
`contractor-payments.completion-attribution-start-date` как календарная дата в
настроенной business-zone. Допустимо только **первое число расчётного месяца**,
не находящееся в будущем относительно business-date. При первом успешном
включении дата фиксируется в singleton-latch. После этого изменение настройки
на другую дату, пустое или некорректное значение и расхождение часов закрывают
attribution и LIVE-маршрутизацию fail-closed; перенос границы «задним числом»
запрещён.

Учёт по обе стороны границы не должен пересекаться:

- работа с подтверждённой датой **до** границы входит только в подписанный
  переходящий остаток по конкретному профилю и роли;
- работа с датой **на границе или позже** создаётся только как датированный
  immutable-источник в новом ledger;
- один и тот же источник нельзя одновременно включить в переходящий остаток и
  восстановить как новую ledger-строку; между двумя наборами также не должно
  быть пропуска.

Исторические строки начислений за фактически выполненную работу при отмене
клиентской оплаты сохраняются активными как первичное доказательство. Они не
конвертируются в новые completion-строки и не деактивируются вместе с оплатой:
для источников до границы обязательство уже учтено ровно один раз в
подписанном переходящем остатке. Система фиксирует логические completion-marker
и отменяет только платёжный факт, не факт выполненной работы.

Если выполненная дополнительная задача относится к периоду до границы, её
последующая отмена не может автоматически создать отрицательную ledger-строку
в текущем периоде. Операция блокируется до явной, датированной и аудируемой
корректировки переходящего остатка с причиной и повторной подписью сверки;
исторический факт выполнения при этом не переписывается.

При передаче заказа:

- уже опубликованные отзывы остаются за фактически выполнившим их
  специалистом;
- выполненные дополнительные задачи остаются за их исполнителем;
- незавершённые карточки и задачи переходят новому специалисту;
- при начислении сумма распределяется по сохранённым фактам выполненной работы;
- новый счёт проверяет специалиста, который ведёт карточку на момент первой
  подготовки счёта.

Таким образом, передача уже частично выполненного заказа не перемещает ранее
заработанную сумму, но следующий ещё не подготовленный счёт проверяет текущего
специалиста карточки. Изменение опубликованности, цены, состава или количества
уже зафиксированной работы без явной корректировки блокируется. Если по счёту
уже выданы реквизиты, изменение суммы/дополнительной задачи также блокируется;
для закрытого исторического счёта используется отдельный дополнительный счёт
или ручная сверка, а не молчаливый пересчёт старого получателя.

Для shadow-проверки этот исполнитель, менеджер, состав общего счёта, сумма и
generation сохраняются в той же транзакции, где впервые подготовлен счёт.
Отложенный обработчик и backfill используют только этот snapshot и не
восстанавливают историческое решение из уже изменившейся карточки.

Миграция V222 сохраняет отдельную границу
`contractor-payments.shadow-preparation-started-at` только после добавления
всех колонок snapshot. Строки старого binary без generation, созданные до этой
границы, считаются legacy и не реконструируются. Строка без generation после
границы считается ошибкой подготовки, остаётся в retry/health и требует
расследования. Это не позволяет бесконечной очереди старых строк скрыть новый
реальный сбой и не даёт назначить исторического получателя по изменившейся
карточке.

Миграция V228 приводит `shadow_route_generation` во всех четырёх рабочих и
архивных таблицах счетов и `source_generation_snapshot` allocation к
`utf8mb4_unicode_ci`. Это обязательный контракт: иначе native join очереди и
архивации между старой production-схемой и новыми таблицами завершается
`Illegal mix of collations`. Prod-like smoke исполняет эти join фактически, а
не только проверяет metadata.

Миграция V229 добавляет singleton `contractor_payment_rollout_state`. Он
отделяет необратимого владельца учёта (`LEGACY` или `COMPLETION`) от обратимой
паузы новых реквизитов, хранит immutable дату начала и optimistic revision.
Если до обновления уже существовал cutover или LIVE-фаза, миграция сохраняет
новый учёт активным и переводит финансовую фазу в LIVE; downgrade в legacy не
выполняется.

Если по заказу уже существует активный LIVE-резерв, ручная передача,
автоматическое выравнивание нагрузки и технический rollback передачи обязаны
остановиться. Аварийное выключение создания новых LIVE-маршрутов не снимает
эту блокировку с уже зафиксированного получателя.

## Жизненный цикл и сверка

Текущее состояние allocation — оперативная проекция. Каждое изменение также
пишется в неизменяемую историю с предыдущим/новым статусом, суммами, временем и
без открытых реквизитов.

Ключевые переходы:

- `RESERVED` — сумма зафиксирована за новым счётом;
- `CLIENT_REPORTED` — клиент сообщил о переводе, резерв остаётся занятым;
- `CONFIRMED` / `SIMULATED_PAID` — фактическое / shadow-поступление;
- `RELEASED_UNPAID`, `EXPIRED`, `CANCELED` — резерв освобождён;
- `LATE_PAYMENT_AFTER_RELEASE` — оплата обнаружена после освобождения;
- `PARTIALLY_RETURNED`, `RETURNED` — частичный / полный возврат;
- `RETURN_AMOUNT_PENDING` — провайдер сообщил частичный возврат, но не передал
  надёжную сумму; показатель не корректируется догадкой и требует ручной
  сверки.

Время подтверждения берётся из фактического `paidAt`/`manualConfirmedAt`, а не
из времени запуска фоновой задачи. Повторная обработка одного события
идемпотентна. Ошибки after-commit записи попадают в постоянную очередь повторов.
Сверка также повторно проверяет неоплаченные и изменившиеся источники, поэтому
падение между сменой статуса заказа и освобождением резерва не должно оставлять
вечный резерв. Зависшие элементы видны в административном журнале.

Completion-repair безопасен при одновременном запуске на нескольких узлах:
batch ограничен, каждый заказ обрабатывается в отдельной транзакции, строка
заказа служит межузловым mutex, а generated unique key остаётся последней
защитой от дубля. Конкуренция за строку retry-state не останавливает остальные
элементы batch; ошибка сохраняется только стабильным кодом без SQL/PII, получает
ограниченный exponential backoff и остаётся видимой в health. Такая схема
допускает повторную работу, но не двойное начисление и не потерю всей очереди
из-за одной poison-записи. Один bounded-проход выбирает неполный набор базовых
marker, выполненные дополнительные задачи без DONE-marker и отменённые после
выполнения задачи без CANCEL-marker. Последние восстанавливаются тем же
append-only отрицательным начислением; отмена pre-cutoff работы остаётся в
durable conflict до явной корректировки opening balance.

## Переключатели безопасности

Shadow включён по умолчанию:

- БД: `contractor-payments.shadow-enabled=true`;
- БД: `contractor-payments.live-routing-enabled=false`;
- БД: `contractor-payments.reward-attribution-live-enabled=false`;
- deployment: `otziv.contractor-payments.live-routing-master-enabled=false`;
- deployment: `otziv.contractor-payments.reward-attribution-master-enabled=false`.

LIVE-функция разрешена только при одновременном `true` у deployment master и
соответствующего свежего флага БД. Кроме того, LIVE-маршрутизация требует уже
включённой completion-attribution и отдельного операционного подтверждения
`contractor-payments.live-readiness-confirmed=true` после backfill и сверки.
Даже после подтверждения LIVE остаётся закрыт, пока существует хотя бы одна
запись completion repair-state или нарушен любой из точных инвариантов: у
каждого заказа в completion-статусе есть marker менеджера, специалиста и
продуктового вознаграждения; у каждой DONE-допзадачи есть
`BAD_REVIEW_DONE:<id>` независимо от cut-off; у CANCELED-допзадачи с прежним
DONE-marker или активным DONE-начислением есть `BAD_REVIEW_CANCEL:<id>`. Эта
проверка не входит в attribution gate:
attribution и repair должны работать при выключенной LIVE-маршрутизации, чтобы
очередь могла полностью очиститься.
Readiness разрешено подписать только после сверки переходящих остатков с
legacy-отчётом и подтверждения, что ни один источник не попал одновременно в
opening balance и новый ledger. Проверяется весь completion backlog, включая
future-backoff retry, а не только готовые сейчас повторы; ручной readiness-флаг
эту проверку не обходит. Ошибка чтения, отсутствующее/некорректное значение,
несовпавшая неизменяемая граница, нечистый completion backlog или выключенный
master дают `false`. В текущем тестовом запуске оба deployment master и
readiness должны оставаться `false`.

### Операционные лимиты маршрута

Дополнительно каждый кандидат проверяется по deployment-лимитам:

- `OTZIV_CONTRACTOR_PAYMENTS_ROUTING_LIMITS_MAX_SINGLE_INVOICE_KOPECKS` —
  максимум одного нового счёта, по умолчанию 5 000 000 копеек (50 000 рублей);
- `OTZIV_CONTRACTOR_PAYMENTS_ROUTING_LIMITS_MAX_DAILY_PROFILE_AMOUNT_KOPECKS` —
  максимум суммы новых счетов одному профилю за бизнес-день, по умолчанию
  15 000 000 копеек (150 000 рублей);
- `OTZIV_CONTRACTOR_PAYMENTS_ROUTING_LIMITS_MAX_DAILY_PROFILE_COUNT` — максимум
  числа новых счетов одному профилю за бизнес-день, по умолчанию 50.

Лимиты работают раздельно для `SHADOW` и `LIVE`. Для суточных ограничений
считаются все попытки маршрутизации `PAYMENT_LINK` и `COMMON_INVOICE`, включая
счета, которые позднее были отменены, просрочены, освобождены или возвращены.
Это ограничение операционного риска: отмена и повторное создание счёта не
обнуляют использованный суточный лимит. Прямые переводы владельца в него не
входят. Текущий день определяется по времени БД и настроенной business-zone,
чтобы расхождение часов web-узлов не давало разным узлам разные лимиты.

Если специалист не проходит лимит, проверяется менеджер. Если лимит не проходит
и менеджер, сохраняется `OWNER_FALLBACK`, и клиент получает действующие реквизиты
владельца. Нулевое, отрицательное, слишком большое или иным образом некорректное
значение лимита, а также некорректная бизнес-зона закрывают маршрутизацию
самозанятым (fail-closed). Ошибка записывается без открытых платёжных реквизитов.
Перед canary лимиты следует уменьшить под согласованный объём, а повышать только
после сверки shadow-журнала.

Каждое решение хранит стабильные коды без ФИО и реквизитов:

- `routing_decision_reason` — итог маршрута; у выбранного специалиста или
  менеджера это `SPECIALIST_SELECTED`/`MANAGER_SELECTED`, а у владельца —
  причина последнего решающего отказа менеджера;
- `specialist_rejection_reason` — почему счёт не был направлен специалисту;
- `manager_rejection_reason` — почему после специалиста не был выбран менеджер.

Поэтому при выборе менеджера причина отказа специалиста не теряется, а у
`OWNER_FALLBACK` видна вся цепочка. Для старых строк, где точную причину уже
нельзя восстановить, используется `LEGACY_UNCLASSIFIED`. Коды копируются в
события allocation и показываются в административном журнале. Это позволяет
считать причины fallback без анализа свободного текста:

```sql
SELECT mode, routing_decision_reason, COUNT(*) AS decisions
FROM contractor_payment_allocations
WHERE status = 'OWNER_FALLBACK'
GROUP BY mode, routing_decision_reason
ORDER BY mode, decisions DESC;
```

Для оперативного контроля отдельно группируются
`specialist_rejection_reason` и `manager_rejection_reason`. Рост
`INSUFFICIENT_AVAILABLE_BALANCE` обычно означает исчерпание доступного остатка,
а рост `LIMIT_*`, `PROFILE_*` или `RECIPIENT_DETAILS_INCOMPLETE` требует
проверки конфигурации/профилей до расширения canary.

Shadow-backfill тоже создаёт попытки маршрутизации в день своей обработки и
расходует лимит `SHADOW`. Поэтому большую очередь нельзя проверять как обычный
день canary: сначала фиксируются размер очереди и ожидаемые `OWNER_FALLBACK`, а
временное повышение лимита проводится только осознанно и не переносится в
`LIVE`-конфигурацию.

Есть и третий, персональный предохранитель: профиль должен быть одновременно
активен и отдельно разрешён для LIVE (`enabled=true`, `live_enabled=true`), а
пользователь не должен быть заблокирован. `enabled` разрешает shadow-расчёт,
но само по себе никогда не публикует реквизиты клиенту.

LIVE-маршрутизация и новый алгоритм распределения начислений включаются
раздельно. Сначала в изолированном staging включается только attribution,
проверяется completion → `zp` → ledger на копии данных и выполняется сверка.
Затем в production отдельным окном attribution включается при выключенной
маршрутизации, очередь полностью дренируется и сверяется. Только после этого
подтверждается readiness и отдельным релизом запускается canary счетов.

Режим финансовой статистики хранится отдельным singleton-состоянием
`SHADOW/LIVE`. Переход в `LIVE` выполняется под блокировкой при первом реально
разрешённом маршруте и необратим: аварийное выключение новых маршрутов не
возвращает отчёты к тестовым данным. Любая ручная операция передаёт ожидаемый
режим и при гонке cut-over получает конфликт вместо записи не в тот журнал.

## Прямой перевод владельца

Если у специалиста или менеджера остался долг, но подходящих новых счетов нет,
в профиле можно зафиксировать отдельный прямой перевод владельца. Это не
корректировка начисления: создаются неизменяемая запись доказательства,
allocation и событие подтверждения. Сумма проверяется под тем же mutex профиля
и не может превышать незарезервированный доступный остаток.

Операция требует дату, причину, непрозрачный идентификатор внутреннего
документа и ключ идемпотентности. Исправление или возврат оформляются только
новой дочерней записью; накопленный возврат не может превысить исходный
перевод. В `SHADOW` интерфейс явно называет такую запись тестовой симуляцией.
После ухода или смены роли исторический профиль остаётся видимым и доступным
для окончательной сверки, но включить его в новые счета нельзя.

Запись в системе не выполняет банковский перевод и не заменяет доказательство
банка. Перед LIVE должна действовать maker-checker процедура: один сотрудник
создаёт перевод в банке, другой сверяет получателя, сумму и внутренний документ
до отражения операции как фактической. Ежедневная независимая сверка выявляет
ошибочную или недобросовестную запись, а исправление делается только дочерней
корректировкой — исходная запись не удаляется.

## Проверка shadow-режима

Production shadow с выключенным attribution master безопасно проверяет выбор
получателя, резервы, статусы, очереди и fallback на уже существующем долге, но
**не является** end-to-end проверкой нового начисления по выполнению. Для E2E
используется только изолированная staging-копия БД: attribution deployment
master и DB-флаг включены, оба флага реальной маршрутизации выключены, shadow
включён. Так выполняется ровно production-цепочка completion → внутренний
реестр начислений → платёжный ledger → shadow routing, но реальные данные и
реквизиты клиентов не меняются.

На production attribution включается позже отдельным cut-over при выключенной
маршрутизации. До успешного staging E2E, сверки production backfill и пустого
repair backlog выставлять readiness запрещено. Создание второго «тестового»
финансового ledger на production намеренно не используется: две расходящиеся
реализации сделали бы проверку менее надёжной.

Перед включением реальных реквизитов проверить минимум полный расчётный месяц:

1. Для всех активных специалистов и менеджеров созданы профили; включены только
   профили с проверенными ФИО, номером и банком.
2. На дату cut-off выгружен legacy-остаток обязательств отдельно по каждому
   пользователю и роли. Миграция намеренно не считает старые строки `zp`
   автоматически: их итог заносится как переходящий остаток с причиной,
   агрегат сверяется с legacy-отчётом, повторный импорт идемпотентен.
   Cut-off выполняется только на границе расчётного месяца. Иначе переходящий
   остаток сохранит правильный общий долг, но месячный показатель «начислено»
   не включит часть старых строк. Если перенос на границе месяца невозможен,
   нужен отдельный помесячный импорт ledger с датой возникновения, а не одна
   недатированная корректировка.
   Настройка допускает только первое число уже начавшегося месяца. При первой
   effective-активации дата навсегда фиксируется singleton-строкой
   `contractor_completion_cutover_state`; последующее изменение настройки,
   будущая дата или дата внутри месяца выключают attribution fail-closed.
3. Начальный остаток каждого профиля подтверждён по аудиту, а итоговая сверка
   `до границы = opening balance`, `с границы = новый ledger` подписана
   ответственными за cut-over. Ошибка исправляется отдельной корректировкой с
   обязательной причиной; исходная запись истории не переписывается. Отмена
   или исправление старой работы, уже включённой в cut-off остаток,
   сопровождается такой же явной корректировкой: исторический источник не
   может автоматически изменить агрегированный стартовый остаток.
4. Для кнопки «Счёт» и автоответчика получаются одинаковые решения.
5. Нет oversubscription при параллельном создании счетов.
6. Смешанные общие счета не назначаются специалисту.
7. «Не оплачено», отмена и истечение освобождают резерв, а повторный счёт снова
   резервирует сумму.
8. Ручное сообщение клиента не считается фактическим поступлением до
   подтверждения.
9. Поздняя оплата, полный и частичный возврат правильно меняют остаток.
10. В личном кабинете сумма совпадает с административным журналом и ledger.
11. В одном административном health-срезе проверены все четыре независимых
    контура: (1) reconciliation allocation, (2) repair начислений/ledger,
    (3) shadow-backfill маршрутов и (4) completion-repair завершённой работы.
    Нет просроченных lease (`expiredClaims`), готовых, но не запущенных
    повторов (`dueRetries`), старых `nextRetryAt`, пропущенных источников и
    отрицательных неразобранных остатков. `activeClaims` первых трёх очередей
    сам по себе является нормальным рабочим состоянием. Для completion контура
    перед LIVE недостаточно отсутствия due-retry: durable retry-state должен
    быть полностью пуст, base-marker scan, DONE-task scan и CANCELED-task scan
    не должны вернуть ни одной строки. Future-backoff не обходится, потому что
    readiness сначала считает все repair-state независимо от срока повтора.
12. Передача нагрузки сохраняет выполненную работу за прежним исполнителем и
    блокируется после LIVE-фиксации.
13. В сообщениях и интерфейсе нет открытых реквизитов в логах и нет терминов
    трудовых отношений.
14. Архивация/восстановление заказов и начислений не удаляет финансовую историю
    и не блокируется внешними ключами нового контура.
15. Заблокированный пользователь и профиль без `live_enabled` никогда не
    выбираются для реального счёта.
16. У каждой поздней оплаты или возврата общего счёта есть доказательство,
    однозначно привязанное к attempt; неоднозначный случай останавливается.
17. Прямой перевод и его возврат повторяются с тем же idempotency key без
    дубля; гонка прямого перевода с последним доступным счётом допускает только
    одного потребителя остатка.
18. Передача карточки после подготовки, но до shadow callback не меняет
    snapshot получателя; следующий новый счёт использует уже нового
    специалиста.
19. На staging начисление появляется до клиентской оплаты; последующая оплата
    не создаёт дубликат legacy-источника.
20. Повторная публикация, repair и `PUBLIC -> CORRECTION -> PUBLIC` не меняют
    исходного получателя/месяц и не создают вторую строку; финансовое изменение
    требует отдельной корректировки.
21. Два заказа с обратными парами менеджер/специалист и две последние позиции
    одного общего счёта завершаются параллельно без deadlock и oversubscription.
22. Если профиль подключён в середине месяца, UI явно показывает дату начала
    покрытия и не выдаёт неполный срез за полный месячный итог.
23. Изменение выполненной дополнительной задачи не пересчитывает уже
    отправленный общий/одиночный счёт: операция получает конфликт, а сумма,
    allocation и реквизиты остаются прежними.
24. Отмена клиентской оплаты по историческому заказу не деактивирует и не
    конвертирует строки за выполненную работу; меняется только платёжное
    состояние, а итоговый долг остаётся равен подписанному opening balance
    плюс ledger начиная с границы.
25. Отмена выполненной до границы дополнительной задачи получает конфликт без
    явной корректировки opening balance; после корректировки история задачи и
    обе суммы сверяются без неявной отрицательной строки текущего месяца.
26. Для каждого mutation-endpoint общего счёта ограниченный `OWNER` проверяется
    по immutable allocation recipient до чтения/изменения счёта; запрещённая и
    отсутствующая цель неразличимы по ответу.

## Включение и аварийная остановка

Главный переключатель находится на сайте: **Справочники → Настройки → Новая
система расчётов по вознаграждениям**. Он управляет не набором независимых
`app_settings`, а singleton `contractor_payment_rollout_state` с ревизией и
необратимым владельцем учёта. Пока состояние `LEGACY`, DB-флаги сами по себе не
могут включить новый учёт.

Включение выполняется так:

1. сохранить резервную копию, проверить миграции и завершить staging E2E;
2. выбрать первое число уже начавшегося расчётного месяца, импортировать только
   обязательства до этой даты как opening balance и подписать исходную сверку;
3. отдельным релизом включить только deployment master нового учёта. Routing
   master можно оставить выключенным; оба DB-флага остаются выключенными;
4. OWNER открывает глобальную настройку, указывает согласованную дату и причину,
   вводит фразу `ВКЛЮЧИТЬ НОВУЮ СИСТЕМУ`. Одна транзакция фиксирует immutable
   cutover, переводит accounting authority и финансовую фазу в LIVE, включает
   completion-учёт, оставляет новые клиентские реквизиты на владельце и пишет
   обязательный бизнес-аудит;
5. обратного переключения в `LEGACY` после шага 4 нет. Выключение deployment
   master или DB-флага не должно и не может вернуть старый writer: при
   конфигурационной ошибке операция блокируется, чтобы не создать двойное
   начисление;
6. дождаться repair/backfill, проверить все четыре health-контура и сверить
   суммы, получателей и месяцы. Кнопка реквизитов не включится при непустом
   completion backlog;
7. включить routing deployment master и убедиться, что все web/worker pod-ы уже
   работают на одной новой версии. Смешанное окно со старым binary запрещено;
8. включить `live_enabled` только у проверенных canary-профилей;
9. OWNER нажимает «Включить реквизиты», указывает причину и вводит
   `ВКЛЮЧИТЬ РЕКВИЗИТЫ`. Сервер повторно проверяет masters, immutable cutover,
   repair readiness и ожидаемую ревизию, затем атомарно разрешает новые LIVE
   маршруты;
10. вручную проверить первые счета, подтвердить поступления и сопоставить
    журнал с банковскими выписками; расширять canary только при нулевых
    расхождениях.

Аварийная остановка выполняется на том же экране командой «Приостановить
реквизиты» и фразой `ПРИОСТАНОВИТЬ РЕКВИЗИТЫ`. Команда блокирует общий rollout
mutex вместе с созданием нового маршрута, поэтому после её commit новый LIVE
allocation уже не появится. Новые счета пойдут владельцу, но completion-учёт,
repair, ledger, прямые переводы и сверка ранее отправленных счетов продолжаются.
Уже отправленные счета сохраняют прежнего получателя. Их нельзя массово
переназначать: при необходимости счёт сначала явно отменяется и только затем
создаётся заново.

После появления хотя бы одного LIVE-маршрута аварийный rollback означает
выключение флага на текущей версии приложения, а не запуск старого binary.
Старый binary не знает новый тип источника реквизитов и может перестать читать
такие строки. Downgrade допустим только после отдельной проверки совместимости
данных и, при необходимости, специальной миграции.

## Обязательные условия перед production

Техническая готовность не заменяет юридическую и операционную проверку. До
production должны быть письменно согласованы:

- договорная модель, при которой платёж клиента самозанятому погашает
  обязательство платформы, и порядок споров/возвратов;
- проверка статуса плательщика НПД, обязанность сформировать чек самозанятого,
  сроки передачи чека клиенту и порядок чеков коррекции/возврата;
- правовое основание и согласие на показ клиенту ФИО, телефона и банка
  получателя;
- кто и по какому доказательству подтверждает поступление на счёт самозанятого:
  сообщение клиента не равно банковскому подтверждению;
- лимиты на один счёт, профиль и сутки, банковские antifraud-ограничения,
  процедура ошибочного перевода/возврата и контакт ответственного;
- сроки хранения, ротация ключей шифрования, резервное копирование и тест
  восстановления финансовой истории;
- сверка стартовых остатков и всех отрицательных корректировок начислений. Если
  уже отправленные счета превысили уменьшенное обязательство, дальнейшая
  маршрутизация профиля блокируется до ручного решения;
- порядок прямого закрытия остатка специалисту/менеджеру, у которого больше нет
  новых заказов. Система не должна искусственно назначать ему чужой счёт только
  ради погашения остатка.

### Остающиеся production-gates

Тестовый контур не закрывает следующие обязательные условия; каждое из них
является отдельным блокером LIVE:

1. **Датированный исторический импорт.** Нужен идемпотентный инструмент и
   подписанный dry-run для источников с неоднозначной датой, помесячной истории
   и исключений cut-off. Автоматически подставлять дату запуска repair или
   сворачивать такую историю в недатированную текущую корректировку нельзя.
2. **Maker-checker.** Для прямого перевода и фактического подтверждения нужны
   раздельные серверные полномочия создателя и подтверждающего, запрет
   self-approval и привязка к банковскому доказательству. Одна описанная
   операционная инструкция четырёх глаз недостаточна.
3. **Закрытые расчётные периоды.** После подписания месяца требуется
   технический запрет задних изменений суммы, получателя и даты. Исправление —
   только append-only в открытом периоде либо через явно аудируемое повторное
   открытие и новую версию отчёта.
4. **Свободный текст и PII.** Шифрование комментария защищает хранение, но не
   оправдывает сбор лишних данных. Нужны правила допустимого содержания,
   минимизация/срок хранения, маскирование в выгрузках и поддержке, проверка
   логов и процесс удаления по утверждённой политике.
5. **Юридическая готовность.** Должны быть утверждены договорная модель,
   статус НПД, чеки и чеки коррекции, согласия на раскрытие реквизитов,
   возвраты, споры и налоговая ответственность каждой стороны.
6. **Банковское подтверждение и сверка.** Нужен согласованный источник истины
   (API или подписанная выписка), устойчивое сопоставление получателя/суммы/
   attempt, ежедневная сверка, обработка поздних переводов и возвратов; слова
   клиента не заменяют банковский факт.
7. **Нагрузка и эксплуатация.** На production-like объёме измеряются оба пути
   выставления счёта, массовый completion-repair, contention mutex/phase,
   дешифрование snapshot, latency и нагрузка на БД; до LIVE задаются SLO,
   capacity, dashboard и alerts для всех четырёх health-контуров.
8. **MySQL/Flyway и окно миграции.** Версия production MySQL должна входить в
   явно поддерживаемый текущим Flyway диапазон. Полная цепочка миграций
   репетируется на свежей production-копии с замером metadata locks, времени и
   места, а backup/restore и восстановление после частичного DDL проверяются
   без автоматического `flyway repair`.

Production остаётся запрещённым, пока не завершены полный shadow-период,
миграционный и архивный тест на копии БД, UAT обоих способов выставления счёта,
сверка с выписками и юридическое согласование. Значения deployment master в
репозитории и шаблонах окружения должны оставаться `false`.

Уже применённые Flyway-миграции неизменяемы. В частности, checksum `V217`
должен совпадать с применённым ресурсом; расширения схемы выпускаются только
следующими версиями. `flyway repair` не используется для маскировки
расхождения checksum. Проверяется и чистая установка, и обновление копии БД с
последней применённой production-версии.

`V218`-`V229` содержат цепочки MySQL DDL над крупными рабочими и архивными
таблицами. До окна обслуживания на восстановленной копии production измеряются
длительность `ALTER`, свободное место и ожидание metadata lock; затем целиком
проходятся Flyway `V217 -> latest`, archive/restore и smoke приложения. В
`V220` удаление и повторное создание `orders.order_worker` намеренно разделены
на два `ALTER TABLE`: объединённый вариант воспроизводимо завершался ошибкой
дублирования FK на MySQL. Для частично выполненного DDL заранее репетируется
восстановление из backup: повторный запуск или `repair` без анализа фактической
схемы запрещён.

07.08.2026 полный путь `V217 -> V229` успешно отрепетирован штатным
`prod-like-smoke.ps1 -RestoreProdDb` на заново скачанной копии актуальной БД с
VPS. Сценарий проверил checksum дампа, удалил временный plaintext-дамп,
санитизировал реквизиты получателей нового контура до старта приложения и не
импортировал production-ключ шифрования. Flyway проверил 321 миграцию и поднял
схему до `1.10.228`; прошли health приложения, публичные маршруты, Keycloak,
frontend, T-Bank TEST, workload SHADOW и отдельный contractor-payment SHADOW
smoke. Через дополнительный интервал фоновых задач не обнаружены ошибки
collation, routing backfill или completion repair; оба deployment master
остались `false`.

Репетиция обнаружила две реальные проблемы до выпуска: отсутствие локального
ключа шифрования после восстановления и несовместимые collation старых и новых
таблиц в generation-join. Первая устранена созданием защищённого стабильного
локального ключа вне репозитория, вторая — новой миграцией `V228` с явным
выравниванием collation. Уже применённые миграции не редактировались, `flyway
repair` не использовался. Локальный сервер MySQL 9.0 новее диапазона, с которым
эта версия Flyway была официально проверена (до 8.1), поэтому версия production,
время/место для DDL и metadata locks всё равно остаются обязательными release
gate перед окном обслуживания.

## Основные риски и меры

| Риск | Защита |
|---|---|
| Двойное использование остатка | блокировка профиля, уникальный источник, optimistic version |
| Устаревший snapshot БД после ожидания mutex | capacity читается locking/current-read после блокировки профиля |
| Повторная отправка одного счёта | идемпотентный allocation и неизменяемый snapshot маршрута |
| Массовая или ошибочная маршрутизация одному получателю | fail-closed лимит одного счёта, суточной суммы и числа попыток; далее менеджер/владелец |
| Обход суточного лимита отменами и повторными счетами | в суточный объём входят все попытки, независимо от их последующего статуса |
| Разные сутки на параллельных web-узлах | единое текущее время БД и явная business-zone; TZ приложения и БД проверяется перед canary |
| Двойное начисление одним событием на разных узлах | блокировка исходного заказа, immutable marker и generated unique key `(order, source, role, profession)` |
| Сбой после commit | постоянная очередь повторов и backfill, включая завершённые `Оплачено`/`Напоминание`/`Не оплачено` |
| Poison-запись блокирует очередь | durable retry state, экспоненциальный backoff, ограниченный batch и видимый health-срез |
| Несколько узлов одновременно берут один completion-repair | межузловая блокировка заказа и unique key делают повтор идемпотентным; гонка retry-state сохраняется как безопасная диагностика и не обрывает batch |
| Два completion-потока берут профили в обратном порядке | единый canonical batch: ID источника начисления ASC, затем ID профиля ASC; MySQL concurrency regression |
| Две последние позиции общего счёта завершаются одновременно | финализация только после commit в новой транзакции; все member Order блокируются id ASC до account/invoice |
| Старый общий счёт при refresh получает сегодняшнюю дату начисления | routing/repair использует опубликованную дату или statusChangedAt; `now` допустим только в синхронном факте выполнения |
| Исправление уже выполненной работы меняет историческую сумму/получателя | immutable marker и 409 для неявной мутации; отмена/коррекция только append-only отрицательной строкой |
| Поздняя оплата после освобождения | отдельный статус, учёт полной экспозиции и переплаты |
| Неизвестная сумма частичного возврата | fail-closed `RETURN_AMOUNT_PENDING`, ручная сумма и аудит |
| Повторное подтверждение той же суммы возврата | pending закрывается явным идемпотентным переходом, уменьшение итога запрещено |
| Изменение реквизитов после отправки | snapshot в счёте/allocation; старый счёт не переписывается |
| Передача карточки после фиксации | единый guard во всех ручных и автоматических путях |
| Гонка переноса и создания счёта | каноническая блокировка заказов до повторного LIVE-guard |
| Ошибка стартового остатка | отдельная аудируемая корректировка, подписанная opening/ledger-сверка до canary |
| Изменение cut-off создаёт overlap или gap | дата только первого числа не будущего business-месяца навсегда фиксируется singleton-latch; любое расхождение выключает attribution/LIVE fail-closed |
| Отмена клиентской оплаты удаляет исторически заработанное | legacy earned-строки остаются активными и не конвертируются; completion-marker фиксирует факт работы, а меняется только платёжное состояние |
| Отмена выполненной до cut-off дополнительной задачи | операция блокируется до явной датированной корректировки opening balance и повторной подписанной сверки; исторический факт не переписывается |
| Исторический источник не имеет достоверной даты | автоматический repair запрещён; до LIVE требуется идемпотентный датированный импорт и ручная сверка исключения |
| Утечка ФИО/телефона/комментария | шифрование этих полей в профиле и allocation snapshot, ролевой доступ, запрет PII в логах; startup backfill повторно шифрует plaintext/старый key id |
| Дублирование реквизитов в legacy-полях счёта | `V224` очищает phone/name/comment/instruction четырёх рабочих/архивных таблиц и ставит enforced CHECK; клиентский ответ строится по `allocationId` из зашифрованного immutable snapshot; owner/manual строки сохраняют совместимое чтение |
| Аномально большой счёт или всплеск за сутки | fail-closed лимиты суммы одного счёта, суммы и количества на профиль/сутки, ограничение стартовой корректировки; при превышении — маршрут владельца, аудит и alert |
| Случайное включение production | routing требует оба deployment master, оба свежих DB-флага, отдельный readiness sign-off и персональный `live_enabled`; всё fail-closed |
| Production shadow создаёт ложную уверенность в completion-based начислении | production shadow при attribution=false считается только тестом routing на legacy debt; полный E2E обязателен на изолированной staging-копии с routing=false |
| Binary downgrade после первого LIVE-счёта | аварийно выключается флаг на новой версии; старый binary без data-compatibility проверки не запускается |
| Mixed-version rollout при включении LIVE | DB-флаг меняется только после проверки version/health всех web и worker экземпляров; rolling deployment сначала полностью завершается с выключенным флагом |
| Несовпадение общей и одиночной цепочки | общий сервис выбора и интеграционные тесты обоих входов |
| Удаление/коррекция исходного начисления | исходная строка неизменяема; только append-only корректировка, повторная синхронизация ledger и отображение кредита |
| Архивация удаляет исходный заказ/начисление | финансовая история хранит логические ID без удаляющих source-FK, archive/restore regression test |
| Архив откатывает впервые обнаруженный неопределённый возврат | preflight-сверка коммитит факт в отдельной транзакции; под архивными блокировками выполняется повторная strict-сверка |
| Удаление специалиста каскадно удаляет активный заказ | FK `orders.order_worker` использует `ON DELETE RESTRICT`; удаление возможно только после штатного завершения/архивации зависимостей |
| Процесс умер после claim, но до записи retry | health отдельно показывает просроченный lease с оставшимся token (`expiredClaims`) и готовые повторы (`dueRetries`) |
| Поздняя оплата старой попытки общего счёта | attempt-bound evidence; при отсутствии — запрет автоматического reissue и ручная сверка |
| Нет доступа к счёту самозанятого | подтверждение только по согласованному доказательству, периодическая сверка с выпиской |
| Ошибка ключа или потеря encrypted-полей | fail-closed запуск, резервная копия и проверенная ротация/восстановление ключа |
| Production-копия требует боевой ключ либо раскрывает реквизиты локально | restore-сценарий никогда не импортирует production-ключ: создаёт защищённый локальный ключ вне репозитория и до старта приложения очищает contractor profile/allocation recipient PII, сохраняя финансовые суммы и статусы |
| Старые и новые таблицы имеют разные collation | `V228` явно выравнивает generation-поля; prod-like smoke выполняет реальные одиночные/общие/claim join и затем проверяет фоновые логи |
| Ошибка фонового repair не видна синхронному smoke | после функциональных запросов выдерживается интервал scheduler и проверяются health/логи на backfill, completion repair, scheduled-task и collation ошибки |
| Исправление найденной миграционной ошибки меняет checksum применённой миграции | применённые ресурсы неизменяемы; исправление выпускается только следующей версией (`V228`), validation checksum обязателен, автоматический `flyway repair` запрещён |
| Старый тестовый binary оставил частичный набор completion marker | LIVE-readiness проверяет три базовых marker и каждую DONE-задачу; bounded repair дополняет набор, а перед sign-off отдельно сверяются marker ↔ исходное начисление ↔ ledger и неоднозначные строки изолируются |
| Callback отмены выполненной допзадачи потерян | readiness ищет CANCELED с прежним DONE-evidence без CANCEL-marker, repair создаёт append-only коррекцию; pre-cutoff случай fail-closed требует явной корректировки opening balance |
| Частично применённая цепочка MySQL DDL | upgrade rehearsal на production-копии, оценка места/metadata locks, maintenance window и проверенная процедура восстановления; без автоматического repair |
| Исполнитель ушёл и не получает новых заказов | профиль не подставляется в чужие заказы; остаток закрывается отдельным подтверждённым переводом владельца |
| Гонка первого LIVE-счёта и тестовой ручной операции | отдельная необратимая accounting phase, общий mutex и обязательный `expectedMode` |
| Возврат старого платежа частично оплаченного общего счёта | любой общий счёт с prior payment/ref остаётся на реквизитах владельца до recipient-bound ledger |
| Передача карточки до выполнения shadow callback | durable preparation snapshot/generation; mutable карточка не используется для исторического решения |
| Старый общий счёт не проходит строгую проверку snapshot/generation | реквизиты самозанятого fail-closed скрываются; нужен alert и операционная кнопка явной отмены/перевыпуска, без молчаливой подмены получателя |
| Mutation общего счёта обходит ограничения целевого пользователя | common-invoice target-policy проверяет immutable allocation recipient до lookup/decrypt/mutation; запрещённый target скрывается тем же 404 и исключается из списков |
| Свободный комментарий содержит реквизиты или иные PII | комментарий шифруется в профиле/snapshot и не дублируется в legacy invoice-поля; до LIVE всё равно нужны минимизация, правила содержания, маскирование и срок хранения |
| Профиль подключён в середине месяца | API возвращает `trackingStartedAt/currentMonthCoverageComplete`, UI помечает неполное покрытие и сохраняет legacy-срез вместо ложного полного итога |
| Restricted OWNER проверяет чужой финансовый ID как existence oracle | target-policy вызывается до lookup/financial locks; privileged target скрывается тем же 404, что отсутствующий ресурс |
| Дополнительные lookup зашифрованного snapshot создают N+1/latency | замер обоих публичных путей на production-like объёме, метрика latency и при необходимости batch/cache только с сохранением строгой проверки поколения |
| Глобальная строка accounting phase становится точкой конкуренции | нагрузочный тест параллельного создания счетов и прямых переводов до LIVE; при росте contention меняется гранулярность блокировки без ослабления first-LIVE fence |
| Maker-checker существует только как операция, а не техническое правило | до LIVE назначаются раздельные роли создателя и подтверждающего; при невозможности гарантировать процесс добавляется двухэтапное серверное утверждение |
| Задняя корректировка меняет уже подписанный месяц | до LIVE вводится техническое закрытие периода; исправления только append-only в открытом месяце либо через аудируемое reopening и новую версию отчёта |
| Исчерпан суточный лимит корректного профиля | безопасная деградация на менеджера/владельца, отдельная метрика причины fallback и alert для отличия antifraud-срабатывания от нехватки остатка |
