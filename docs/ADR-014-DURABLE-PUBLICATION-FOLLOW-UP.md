# ADR-014: устойчивое продолжение публикации после коммита

Дата: 8 сентября 2026. Дополнительная волна после локальной проверки архитектурных исправлений.

## Решение и граница

`OrderServiceImpl.changeStatusAndOrderCounter` раньше сохранял публикацию, затем регистрировал callback с отправкой прогресса и завершением заказа. Аварийный выход между коммитом и callback терял обе операции. Новый `OrderPublicationOutbox` сохраняет намерение **в той же бизнес-транзакции**, после существующей проверки actor/назначения и изменения review/counter. Ошибка сериализации или INSERT откатывает публикацию. Callback больше не является источником истины для этого сценария.

Миграция **V1_10_310** добавляет только `order_publication_client_updates`. Она не переигрывает старые публикации, не меняет прежние occurrence/operation UUID и не сбрасывает UNKNOWN. Уникальные ограничения задают одну запись на `(order_id, publication_occurrence)` и один operation ID. Повтор с несовпадающим снимком отклоняется. Публикации, сделанные старой версией во время смешанного развёртывания, не получают новой гарантии задним числом: все экземпляры, обрабатывающие публикацию, должны перейти на этот пакет.

Существующий generic integration outbox рассмотрен: его relay по умолчанию выключен, handler возвращает void/SUCCEEDED, превышение attempts переводит в DEAD, а DEAD блокирует aggregate FIFO. Для publication progress требуются UNKNOWN/receipt-only и независимое продолжение completion. Изменять эти условия у всех generic handlers ради одного сценария не требуется. Используется узкая очередь владельца orders, с обязательным polling и прежними send flags. Новая очередь не зависит от `integration.outbox.relay.enabled`.

## Три независимые фазы

1. **Completion.** Worker в новой транзакции берёт настоящий `OrderRepository.findByIdForCounterUpdate` lock, затем строку очереди, вызывает fresh проверку counter, settled evidence и recovery. Frozen счётчик сообщения не определяет завершение заказа. Все уже закоммиченные pending completion данного Order отмечаются в той же транзакции: накопленные 1/3, 2/3, 3/3 не запускают счёт заново после его отправки. При активном recovery completion остаётся pending с backoff; снятие блокировки повторно проверяется без UI. Для отложенного сценария допустимы только текущие «Публикация», «Опубликовано», «Ожидает общего счета»; более поздние ручные статусы не отменяются. Новый `scheduleInitialInvoiceIfAbsent` создаёт отсутствующий прежний invoice target key, сохраняя существующий ACTIVE/PAUSED/DONE и его delivery identity. Поведение других callers `checkAndMarkOrderCompleted` и обычного explicit reschedule сохранено.
2. **Общий счёт.** `billing_done=false` сохраняется после completion. Отдельная фаза вызывает public owner API `common_billing.api.PublicationInvoiceCompletion` вне транзакции отдельного Order. API с `NEVER` получает scalar current membership, затем использует существующие `writeTransaction` и `lockedInvoice`: все Orders по возрастанию → account → invoice, повторная проверка membership. Старый быстрый callback и durable recovery делегируют одному idempotent телу. Только актуальный COLLECTING может стать READY либо применить подтверждённую PREPAID через прежний financial owner. READY, PARTIALLY_PAID, уже отправленные/terminal/attention состояния не переоткрываются. Новое ручное закрытие member также не отменяется. Недостаточная готовность/recovery сохраняет pending; marker пишется после успешного owner commit. Потеря marker приводит к безопасному повтору.
3. **Прогресс.** Producer сохраняет scalar Order/Company/route/client/group, исходный отформатированный текст и признак первой кнопки, recipients для существующих auth alerts, неизменяемые occurrence/UUID. Последний review и выключенные при публикации отчёты сохраняют SKIPPED progress, но не подавляют completion. Workers соблюдают FIFO progress внутри Order; UNKNOWN блокирует более поздний progress этого Order, но не его completion/billing и не другие Orders.

За новым billing переходом существующие READY/PARTIALLY_PAID, enabled account, `sentAt=null`, возраст ≥5 минут и допустимый `lastError` являются durable источником для `CommonBillingReminderScheduler`/`sendUnsentActionInvoices`, если потерян быстрый invoice-send callback. Прежний `auto_send_disabled` намеренно не выбирается этим scheduler: данное изменение не вводит автоматическую отправку старых отключённых счетов после включения флага. Банковские вычисления, распределение/начисления и собственные payment recovery state machines остаются у прежних владельцев.

## Send boundary и неопределённость

Claim коммитит DISPATCHING/token до provider I/O. Вызов sender выполняется под `NOT_SUPPORTED`, без lazy entities и удержания Order/outbox transaction. Непосредственно перед sender повторно читаются свежая company preference и оба глобальных флага через fail-closed settings API. При запрете/ошибке чтения провайдер не вызывается, а ещё доказанно не начатая попытка возвращается в READY с тем же envelope/UUID.

Перед новой отправкой выполняется свежая проверка существования Order. Физическое удаление переводит только доказанно не начатый progress в SKIPPED с token guard; ошибка чтения сохраняет READY для возобновления. Receipt-only recovery выполняется до этой проверки и сохраняет возможность подтвердить прежнюю отправку удалённого заказа. Проверка не удерживает Order lock во время I/O и не обещает атомарность удаления с уже начавшимся provider вызовом.

Истёкший DISPATCHING никогда не даёт разрешения отправлять снова: worker переходит только к `recordedOutcome(originalOperationId)`. Отсутствие receipt, timeout, неизвестная ошибка и потерянный finalize остаются UNKNOWN без TTL-сброса. Только существующий точный allowlist validation/admission errors допускает READY retry после известного отказа до отправки. Положительный provider receipt подтверждает occurrence и SENT в одной транзакции; token guard не позволяет старому worker перезаписать новую попытку. Receipt recovery работает и при выключенных send flags, без нового POST.

Снимок progress содержит исходный текст и controls; deterministic Telegram hint/callback/button по-прежнему формирует messaging owner. При первой реальной попытке существующий transport fence фиксирует полный canonical wire envelope/hash, включая keyboard. Изменение шаблона/маршрута в БД не перегенерирует очередь; несовпадение canonical envelope после обновления программного formatter не разрешает новый UUID или автоматический повтор сомнительной отправки. Это сохраняет прежний транспортный fence, а не заявляет, что все provider payload bytes уже лежат в publication JSON до первой попытки.

## Проверка границ по ADR-001

Внешние возможности worker ограничены уже экспортированным `client_messages.api.ClientMessageDelivery` и новым узким API внутри уже экспортированного `common_billing.api`. Доступ к чужим repositories не добавлен. Существующие module edges orders→messaging/billing сохраняются, новые cyclic edges не требуются.

В internals baseline добавлено ровно одно reviewed read dependency: `p_products.status.service.OrderPublicationOutboxWorker → config.settings.service.AppSettingService`. Это прежняя permission-to-send проверка `OrderServiceImpl`, перенесённая также на финальную границу I/O; source owner orders, actor scope прежней публикации, только fresh fail-closed чтение двух настроек. Старый OrderServiceImpl→settings остаётся для initial eligibility/formatting; поэтому это **+1 retained read dependency**, а не фиктивное уменьшение долга. Blanket observed baseline не применяется.

## Причинные проверки и пределы

- `PublicationClientUpdatesMySqlIntegrationTest`: реальные migrations/JDBC queue/fence, actual publication/checker/invoice scheduler через Spring advice; JDBC repository fixtures, mocked provider и unrelated owners. Проверяются бизнес-rollback/ошибка enqueue, restart до отправки, полный Telegram text/button/route, отсутствие provider TX/удержанных business locks, параллельный FIFO, потеря finalize после receipt, UNKNOWN без resend, fresh kill-switch/opt-out/read failure, неизменяемый known-unsent retry, stale token, конфликт envelope, backlog и ранее SENT invoice, current terminal statuses, recovery release, отдельный billing ACK crash.
- `CommonInvoicePublicationFinalizationTest`: actual membership orchestration и явный mocked settlement boundary проверяют fresh locking entry, потерянный callback/повтор после owner commit, COLLECTING/PREPAID dispatch order, recovery/membership/terminal guards, сохранение disabled-send policy. Эти проверки не подменяют MySQL transaction suites и существующие реальные financial workflows тесты, включая `CommonBillingServiceTest`.
- Новый `durablePublicationRecoveryUsesActualCanonicalTransactionAndCommittedCollectingTransitionIsIdempotent` в `CommonInvoiceAccountArchiveTransactionMySqlIntegrationTest` использует actual Membership/Settlement, Spring advice и JDBC adapters: закоммиченные ready flags без callback, запрет вызова под outer TX, rollback owner save, canonical Orders→account→invoice, persisted COLLECTING→READY и повтор после потери ACK без повторного sender. Денежные providers здесь не вызываются.
- Регрессии: `OrderServiceImplTest`, `OrderStatusCheckerServiceImplTest`, `PaymentInvoiceRetrySchedulerTest`, `OrderNotificationOccurrencesMySqlIntegrationTest`, `ClientMessageOperationFenceMySqlIntegrationTest`, `SharedReviewPublicationMySqlIntegrationTest`, common billing transaction suites и architecture gates. Итоговые результаты Maven/fresh DB фиксируются отдельно в отчёте исполнения; данный ADR не выдаёт ещё не выполненный прогон за PASS.

Нет автоматического удаления publication records/UNKNOWN, backfill старых уведомлений, нового банковского POST либо изменения денежных сумм. Журнал операций и последующий retention требуют сохранения referenced identities; этот append-only cutover ничего не очищает.
