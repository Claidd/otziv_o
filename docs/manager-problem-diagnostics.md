# Диагностика замечаний и проверка ответов по фактам

Карточка менеджера и аудит используют версионированные снимки одной проблемы.
Завершение аудита подтверждает ответ на вопросы; устранение причины проверяется
отдельно существующим процессом закрытия карточки.

## Модель

По умолчанию используется `deepseek-flash`. На 22.10.2026 официальный API
сопоставляет это имя с **DeepSeek-V4.1-Flash-1017**:
[таблица моделей DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/).
Alias может измениться у поставщика. Перед выпуском проверяют актуальную версию
и действующее значение `DEEPSEEK_MODEL`: явное старое значение окружения VPS
имеет приоритет над новым значением по умолчанию.

Диагностика сохраняет настроенное имя модели, протокол
`manager-problem-evidence-v2`, версию фактов и расход токенов. Имя alias само по
себе не является идентификатором неизменных весов модели. Протокол проверки
ответов — `evidence-v1`; вопросы и ответы имеют отдельные бюджеты и таймауты.

## Сбор и разбор проблемы

После сохранения карточки событие фиксирует снимок по завершении транзакции.
Событие `ClientMessageAttemptRecorded` сразу обновляет существующие карточки
состояния автоматической отправки и связанных счетов после записи попытки.
DeepSeek вызывается отдельным фоновым обработчиком. Периодический обход подбирает
открытые карточки по 25 записей за проход; это страховка, а не гарантия обработки
всех старых карточек за одну минуту.

Случай связывает менеджера и рабочую сущность. Дневные копии используют актуальное
состояние сущности; повторное открытие после закрытия начинает новый эпизод.
Изменение фактов создаёт новую версию. Очередь использует аренду задания и
проверяет версию при записи: старый ответ модели не заменит свежий снимок.

Подробно собираются общие счета, их позиции, связанные состояния автоматической
отправки и последние попытки доставки. Сбор ограничен первыми 100 позициями счёта,
40 связанными состояниями отправки и 5 последними попытками каждого состояния.
Для замечаний клиентского чата сохраняются состояние проверки, исходное сообщение,
зарегистрированный ответ и их метаданные. Цитата подтверждает, что текст был
записан; истинность содержащихся в нём утверждений требует отдельного подтверждения.
Для остальных типов сохраняется контекст карточки с указанием ограниченного
покрытия. Полные файлы журналов, переписки, окружение VPS и платёжные ссылки не
выгружаются. Дополнительные источники требуют своего сборщика. Поля выбираются
разрешённым списком; типовые секреты, ссылки, телефоны и email маскируются перед
сохранением и внешним запросом.

Валидатор проверяет структуру ответа, допустимые действия и ссылки на факты.
Подтверждённый факт дословно совпадает с серверным представлением значения.
Тексты ошибок и комментариев — наблюдения; их смысл не становится автоматически
подтверждённой первопричиной. Причины без доказательств остаются гипотезами.

В ответе модель выбирает до 10 существенных подтверждённых фактов и краткое
объяснение. Полный собранный снимок хранится отдельно; переписывать сотни строк
истории в вывод не требуется. Проверка модели включает большой синтетический
случай с 432 фактами, без данных реальных клиентов.
Бюджет диагностики по умолчанию — 8000 выходных токенов, включая размышление
модели: проверка большого случая обнаружила обрезку на прежнем лимите 5000.
Обрезанный ответ не принимается; очередь сохраняет безопасный код ошибки,
причину завершения и расход токенов, без тела ответа провайдера.

Карточка показывает время снимка, подтверждённые факты, возможные причины,
недостающие данные, следующие действия, ответственного и проверку результата.
Версия и исходные ссылки доступны в раскрываемом блоке. Всё отображается как
текст. Модель не создаёт исполняемые команды, не получает дополнительные права,
не запускает ремонт, повторную отправку или новый платёж самостоятельно.
Известные поля и статусы показаны русскими подписями; технические ссылки остаются
в раскрываемых доказательствах. Незнакомое значение отображается как текст без
предположения о его смысле.

## Проверка аудита

Перед вопросами и оценкой ответа обновляются связанные факты. Исторический снимок
сохраняется; текущие статусы получают отдельные ссылки и время. Историческое
действие оценивается по сведениям, доступным менеджеру в тот момент.

При повторной проверке сохранённого ответа после сбоя используется его исходный
снимок, связанный с номером вопроса, временем отправки и SHA-256 текста ответа.
Свежесть фактов и относительные сроки проверяются на момент отправки. Если
точный снимок недоступен, требуется контекст: новое состояние задачи не может
задним числом сделать старый ответ ошибочным. Актуальное состояние отдельно
используется для закрытия замечания и проверки обещаний.

Для каждого критерия и существенного утверждения модель возвращает цитату ответа,
ссылки и статус проверки. Сервер проверяет полноту схемы, принадлежность цитат,
существование ссылок и структурированные значения. Для одиночного счёта отдельно
сверяются явные утверждения о статусе и количестве позиций. Общий балл не заменяет
эти проверки. Ответ менеджера и вывод диагностической модели не становятся
исходными доказательствами.

Попытки могут дополнять друг друга; явная поправка отменяет отозванное утверждение.
Длина, опечатки, скорость и слово «частично» сами по себе не доказывают нарушение.
Менеджеру показываются направление уточнения и безопасная причина; скрытые
критерии, готовый правильный ответ и внутренний вывод не копируются в подсказку.

Владелец и администратор видят сохранённые попытки в разделе «Ознакомление с
аудитом»: полный текст ответа, время, решение, критерии, проверенные утверждения,
цитаты и ссылки на факты. `GET /api/admin/manager-daily-summary/review-sessions`
возвращает добавочный список `answerAttempts`; для старых записей прямо указано,
что подробный разбор не сохранялся. Это чтение истории, а не повторная оценка.
Распознаваемые значения учётных данных маскируются при выдаче; ответы отображаются
текстом. Большие снимки доказательств и отдельные попытки раскрываются по запросу.
Исторические счётчики скорости не означают доказанного нарушения.

| Решение | Смысл |
|---|---|
| `ACCEPTED` | Критерии подтверждены |
| `NEEDS_CLARIFICATION` | Ответ неполон или есть подтверждённое противоречие |
| `NEEDS_CONTEXT` | Недостаёт или устарели существенные факты |
| `UNAVAILABLE` | Модель или формат ответа недоступны |

Ожидание контекста и сбой модели не считаются доказательством плохой работы.
Обещание сохраняется отдельно: действие, ответственный, срок, зависимости и
проверка. Срок и способ проверки должны опираться на цитаты ответа. Обещание не
закрывает карточку. По наступлении срока аудит спрашивает результат и подтверждение.
В самой карточке отдельно показаны действие, ответственный, срок и способ
проверки. Статус `CASE_RESOLVED` означает закрытие исходной проблемы; он не
доказывает выполнение обещанного действия именно менеджером.

## Постепенное включение диагностики

Владелец или администратор управляет режимами в «Справочники → Настройки аудита».
Пилоты диагностики и проверки ответов выбираются независимо из списка менеджеров.
Пустой пилот и неизвестный менеджер не сохраняются. Там же доступны отдельные
лимиты, таймауты и режим рассуждения для диагностики, вопросов и ответов.

Существующий `GET/PUT /api/admin/settings/manager-report-review` возвращает и
принимает блок `evidence`. Для изменения через API берут полный результат GET,
меняют нужные поля и отправляют PUT без списка `managers`. Пропуск `evidence`
в запросе старого клиента сохраняет текущие режимы. Старые JSON-поля длины,
скорости, сходства и проходного балла оставлены для совместимости; они больше
не управляют проверкой и не показаны как действующие настройки.

Параметры `AppSettingService`:

| Настройка | По умолчанию |
|---|---|
| `manager-control.diagnostics.mode` | `SHADOW` |
| `manager-control.diagnostics.pilot-manager-ids` | пусто, ID через запятую |
| `manager-control.diagnostics.max-requests-per-hour` | 60 на процесс |
| `manager-control.diagnostics.max-output-tokens` | 8000 |
| `manager-control.diagnostics.timeout-seconds` | 45 |
| `manager-control.diagnostics.thinking-enabled` | true |

`SHADOW` собирает факты и результаты, скрывая рекомендации от менеджера. `PILOT`
показывает их выбранным менеджерам. `ENFORCE` показывает всем; этот режим не
разрешает автоматическое выполнение предложений. `OFF` останавливает новые
задания. Эти параметры управляют диагностикой карточек; они не заменяют
отдельное управление проверкой прохождения аудита.

Проверка аудита имеет собственные настройки:
`manager.report-review.evidence-mode=SHADOW` и
`manager.report-review.evidence-pilot-manager-ids` (ID через запятую). В `SHADOW`
оценка сохраняется для сверки владельцем, ответ остаётся ожидающим проверки,
автоматического прохождения и ограничения рабочего доступа нет. `PILOT`
применяет решения к выбранным менеджерам, `ENFORCE` — ко всем. Тестовые аудиты
проверяются полностью независимо от режима. Теневой режим нельзя оставлять как
постоянный способ прохождения рабочего аудита: нужен завершённый контроль качества
и последующее включение проверенной схемы.

Spring properties с префиксом `manager-control.diagnostics.`:
`scan-delay-ms=60000`, `worker-delay-ms=15000`, `initial-delay-ms=45000`.
Интервалы не заменяют лимит запросов и не гарантируют время ответа модели.

## Проверки и выпуск

### Контракты модулей

`config.settings.api.ManagerProblemDiagnosticSettings` принадлежит платформенной
конфигурации. Диагностика и политика аудита читают только режим, список менеджеров
пилота и лимиты запросов; интерфейс не меняет настройки и не даёт полномочий
на карточки. Вызов не требует бизнес-транзакции.

`reputationai.api.ProblemDiagnosticModel` принадлежит модулю исследований.
Фоновая диагностика передаёт только разрешённый снимок без секретов и получает
текст и сведения о расходе. Сетевой запрос выполняется после сохранения снимка,
за пределами транзакции источника; интерфейс не получает ORM-объекты или доступ
к базе менеджеров. Проверка схемы и допустимых действий остаётся в диагностике.

Событие `client_messages.api.ClientMessageAttemptRecorded` принадлежит модулю
сообщений и содержит только ID состояния. Оно публикуется при записи попытки.
Обработчик диагностики после фиксации транзакции обновляет существующие связанные
карточки, проверяя принадлежность менеджеру через сохранённые источники. Событие
не разрешает повторную отправку и не создаёт платежи.

Доступ к диагностике и обещаниям идёт через существующую авторизованную выдачу
карточек. Отдельного публичного чтения произвольного sourceTaskId нет.

1. Прогнать тесты парсера, сверки фактов, версий, повторных заданий, обещаний и UI;
   выполнить production-сборку frontend.
2. Прогнать размеченный набор на живой модели. Ошибка API, неполная схема или
   расхождение с меткой блокируют этот шлюз.
3. Начать с `SHADOW`, вручную проверить реальные обезличенные примеры с владельцем.
   Затем выбрать менеджеров пилота и расширять показ по результатам проверки.
   Новые ограничения прохождения аудита требуют проверки именно этой функции
   и её отдельного режима.
4. Выпускать по `UNIFIED_MAIN_WORKFLOW.md`: общий main, проверка состава,
   координатор выпуска, успешный CI точной версии, резервная копия,
   `deploy.ps1 -ImageTransport Direct`. На VPS проверить модель, миграции,
   очередь, свежую карточку и ответы на контрольные сценарии.

Набор `backend/src/test/resources/manager-audit-evaluation/victoria-regressions.json`
содержит вымышленные примеры по типам найденных ошибок: шаблоны с неверным
статусом/причиной, верные ответы своими словами, длинный ответ, обещание вместо
действия, выдуманная отправка, неизвестная доставка, поздняя поправка, внедрение
инструкций, исторические/устаревшие данные, отсутствующий источник и обязательство.

Из `backend`:

```powershell
./mvnw.cmd -Dtest=ManagerReportReviewLiveEvaluationTest test
```

Без флага проверяется только структура набора. Для платного живого прогона
безопасно передать в окружение процесса `DEEPSEEK_API_KEY`,
`DEEPSEEK_MODEL=deepseek-flash`, `RUN_MANAGER_AUDIT_LIVE_EVAL=1`, затем повторить
команду. Ключ не сохранять в репозитории или командной строке. Тест использует
production-сервис оценки, его настоящий промпт, парсер и провайдер; данные VPS
не читает. Синтетические факты получают тот же конверт версии/источника, что и
рабочие снимки.

Отчёт — `backend/target/manager-audit-evaluation/report.json`: метки/вердикты,
ошибки приёма и отклонения, ожидание контекста, токены, время. Ожидаемый
`NEEDS_CONTEXT` считается правильным результатом; сбой API не засчитывается как
успешный отказ. Успех маленького набора не измеряет частоту ошибок на реальных
менеджерах и не гарантирует отсутствие обмана.

## Наблюдение

Micrometer: `manager.problem.diagnostics.captured`, `completed`, `stale`, `retried`,
`tokens` (тег `direction=input|output`); timer `manager.problem.diagnostics.latency`.
`captured` считает обращения к фиксации снимка, поэтому не равен числу уникальных
проблем. Стоимость рассчитывают по действующему тарифу отдельно: одних токенов
недостаточно для учёта кэша и времени суток.

На размеченной выборке отдельно считать неверно принятые ответы, неверно
отклонённые и ожидание контекста. Эффект для менеджеров оценивать по времени до
подтверждённого устранения, повторным проблемам, числу уточнений и просроченным
обещаниям. Счётчики очереди не измеряют эти показатели. Рост ошибок или расходов —
основание вернуть рекомендации в `SHADOW`, сохранив факты для разбора.
