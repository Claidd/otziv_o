# Счёт и акт Точки: первая версия

Функция выпускает документы по выполненному неоплаченному заказу или готовому общему счёту. До выпуска менеджер подтверждает отсутствие оплаты по прежним реквизитам. Прежний маршрут закрывается существующим механизмом проверки банковских платежей и освобождения резерва.

При активном восстановлении отзыва выпуск счёта и акта отклоняется до завершения работ, даже если старый счётчик заказа уже заполнен.

## Реквизиты заказчика

Менеджер вводит ИНН. DaData возвращает действующую организацию или ИП, полное юридическое наименование, КПП и адрес организации. При нескольких подразделениях нужно выбрать нужное. Для ИП адрес регистрации не раскрывается этим API, поэтому адрес остаётся необязательным. ИНН проверяется по длине и контрольным разрядам, тип плательщика должен соответствовать ИНН. Предусмотрен ручной ввод при недоступности справочника.

Реквизиты сохраняются у компании отдельно от торгового названия; изменения записываются в аудит. Для счёта Точки расчётный счёт покупателя не обязателен, поэтому вводить его, БИК и корреспондентский счёт покупателя не нужно. Реквизиты получателя банк берёт из выбранного счёта продавца.

## Документы и доставка

После подтверждения сохраняется неизменяемый снимок плательщика, суммы, состава общего счёта, счёта продавца, описания услуги, НДС и группы заказчика. Фоновый процесс создаёт счёт и связанный акт, получает PDF и отправляет оба файла в привязанную группу WhatsApp, Telegram или MAX.

На один заказ или общий счёт создаётся один комплект. Повторное нажатие показывает существующий комплект. Если результат POST в банк неизвестен, автоматический повтор создания запрещён. Неопределённая доставка также требует сверки. Документы доступны для скачивания только пользователю с доступом к соответствующему заказу или компании.

PDF акта не означает подписание заказчиком. Электронное подписание, печать и добавление изображения подписи в этой версии не реализованы.

## Подтверждение оплаты

Входящий webhook проверяется по подписи RS256 с фиксированным публичным ключом Точки. Дополнительно поступления восстанавливаются из банковской выписки. Обе проверки используют один уникальный идентификатор банковского платежа.

Автоматическое закрытие выполняется, когда совпали подключение банка, счёт получателя, ИНН плательщика, уникальный номер счёта в назначении и точная сумма в рублях. Принимается один перевод на всю сумму. Недоплата, переплата, несколько разных переводов, другой плательщик или изменение состава заказа требуют сверки. Частичные поступления автоматически не суммируются. Повторное уведомление о том же переводе не создаёт повторную оплату.

Закрытие использует существующие финансовые сервисы проекта. Следующий заказ создаётся штатной очередью автоповтора; повторный заказ сохраняет бумажный режим оплаты. Для общего счёта действует существующая настройка автоповтора его аккаунта.

После создания банковского документа смена маршрута и ручное подтверждение оплаты блокируются. Это предотвращает повторное закрытие по другой форме оплаты.

## Настройки

По умолчанию функция выключена; старый ручной сценарий продолжает работать.

| Переменная | Назначение |
| --- | --- |
| `PAPER_INVOICES_ENABLED` | Новая форма и процесс документов |
| `PAPER_INVOICES_BANK_OPERATIONS_ENABLED` | Создание документов и сверка поступлений |
| `PAPER_INVOICES_DELIVERY_ENABLED` | Отправка PDF в группу |
| `PAPER_INVOICES_ACCOUNT_LAST4` | `4287`, выбран владельцем; совпадение среди активных рублёвых счетов должно быть единственным |
| `PAPER_INVOICES_DADATA_KEY` | Обычный API-ключ DaData; только сервер, не Git и не браузер |

Используется существующее подключение Точки: `OTZIV_PAYMENTS_TOCHKA_JWT_TOKEN` и его customerCode. Для текущего подключения чтением проверены действующие права `ManageInvoiceData`, `ManageWebhookData`, `ReadAccountsBasic`, `ReadAccountsDetail`, `ReadStatements`, `ReadCustomerData`. Перевыпуск ключа не требуется.

Перед будущим включением на VPS нужно добавить `incomingPayment` к существующей подписке webhook, сохранив `acquiringInternetPayment` и действующий адрес. Подписка банка не менялась. После проверки с имитацией по отдельной просьбе владельца выполнен изолированный запуск настоящего банковского клиента в локальном Docker: один счёт и связанный акт на 1 000 рублей по ИНН владельца, без клиентских рассылок и без деплоя. Подробности — в `docs/TOCHKA_PAPER_INVOICES_LOCAL_VERIFICATION.md`.

Локальный скрипт `infrastructure/scripts/local/connect-paper-dadata.ps1` переносит только API-ключ из указанного владельцем файла в локальный env. Его нужно запускать от владельца защищённого env-файла. Скрипт сохраняет ACL и не печатает секрет.

## Локальная проверка

Базовый стенд запускается штатным `infrastructure/scripts/local/prod-like-smoke.ps1` с `-RestoreProdDb`. Скрипт получает свежую БД VPS, очищает внешние подключения и отключает настоящие операции.

Для проверки финансового сценария поверх этого стенда применяется `infrastructure/scripts/local/paper-invoice-fixture/compose.yaml`. Локальный сервис имитирует Точку и доставку файлов; API создания, подписанное уведомление и выписка проходят через те же прикладные обработчики. Сервис доступен только из локальной сети Docker и на `127.0.0.1:8099`.

Профиль `paper-invoice-fixture` допускает только фиксированный адрес имитации и пустой банковский JWT. С настоящим JWT приложение отказывается использовать имитацию. При наличии ключа DaData поиск идёт в настоящий справочник, без него работает тестовый ответ для ИНН `7707083893`.

Управляющие флаги оплаты в тестовой БД включаются только для изолированного сценария. Внешние сообщения, настоящие токены банков и ботов остаются выключены. После теста флаги оплаты возвращаются в безопасное состояние.

Для неизвестного результата создания документа или доставки автоматическое повторное создание/отправка не выполняется.
