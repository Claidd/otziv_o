# Координированное обновление MySQL C30 → C37

Обновление исправляет `openssl-libs` для CVE-2026-84782. Версия сервера
остаётся MySQL 9.7.3, а том `docker_mysql_data` сохраняется. Обычный деплой
с другим образом базы отклоняется `database_image_guard.py`; переход выполняет
только `coordinated_mysql_refresh.py` внутри защищённого выпуска.

Репетиция опубликованного digest —
`infrastructure/runtime-security/proofs/c37-mysql/rehearsal.json`, SHA-256

Сценарий сверяет этот файл, исполнявшийся исходный скрипт, запись активации,
манифест публикации и точный локально загруженный образ. Локальная
предварительная сборка не заменяет доказательство опубликованного digest.
В deploy-пакет входят только привязанные хэшами манифест, сводки публикации
и анонимной загрузки, итоговая репетиция, её исполнявшийся скрипт и запись
исходной активации. Полные сырые OCI-доказательства проверяет CI для точного
коммита; сценарий на VPS повторяет проверку их итоговых привязанных результатов,
а не скачивает весь архив публикации повторно.

## Порядок выпуска

1. Завершить проверки PR для точного коммита `main`, убедиться, что активная
   запись MySQL указывает на C37, и проверить `release_session.py status`.
2. Запустить штатный `deploy.ps1` из основного каталога с
   `-Tag <название> -ImageTransport Direct -CoordinatedMysqlRefresh
   -CoordinatedSslRefresh -ReleaseSessionToken <token>`. Оба флага нужны в
   этом выпуске: на VPS исходно MySQL C30 и PostgreSQL C23, а новый Compose
   содержит C37 и C36 соответственно. Самостоятельно вызывать Python-сценарий
   вне deploy lock нельзя.
3. Внутри выпуска обязательная зашифрованная копия MySQL создаётся до
   синхронизации файлов. После синхронизации отдельный C37-сценарий сверяет
   старые образы через `checked_override`, останавливает известных писателей,
   включает `super_read_only`, создаёт и проверяет **ещё одну** зашифрованную
   копию, затем пересоздаёт только контейнер MySQL с тем же томом.
4. Сценарий ждёт здорового состояния, сравнивает состав таблиц, контрольные
   суммы их строк через `CHECKSUM TABLE ... EXTENDED`, схему, историю Flyway
   и учётные записи. Затем запускает ранее работавшие сервисы.
   Только после этого выполняется отдельный переход PostgreSQL C23 → C36,
   общий guard и остальная часть быстрого выпуска.
5. Проверить закрытие выпуска и файл
   `.deploy-backups/mysql-c37-cutover-<lock-token>/cutover.json` на VPS:
   `result=PASS`, обе identity образов, `volume=docker_mysql_data`,
   одинаковые `before`/`after` и путь дополнительной зашифрованной копии.
   Этот файл содержит хэши, а не строки базы.

## Если проверка не прошла

Сценарий сначала останавливает всех ранее запущенных писателей, затем
пересоздаёт MySQL с C30 **на том же томе**, сравнивает контрольные отпечатки
до и после отката и возвращает писателей. При успехе остаётся
`rollback.json`, а внешний выпуск завершается ошибкой и восстанавливает
штатный таймер по своей процедуре.

Если появляется `manual-recovery-required`, автоматический откат не доказан.
Нужно оставить deploy lock и таймер самовосстановления выключенными,
проверить `my-mysql`, том и журнал Docker, затем использовать проверенную
зашифрованную копию. `restore-clean` заменяет данные базы и применяется
только как отдельное восстановление после анализа фактического состояния;
он не является продолжением автоматического перехода.

Нельзя удалять старый образ, том или зашифрованную копию до проверки
работы приложения и архива выпуска. Не редактируйте исторический сценарий
C30: его хэши и предпосылки относятся к другому переходу.
