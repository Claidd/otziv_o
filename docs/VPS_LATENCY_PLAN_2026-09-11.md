# План снижения задержки API до 80–100 мс

Дата: 11.09.2026. Проверка VPS: примерно 19:11–19:13 Asia/Irkutsk. Локальный исходный код: `10a53131`. На VPS выполнены только диагностические чтения; приложение, настройки, БД и контейнеры не изменялись. Нагрузочные тесты production не запускались.

**Вывод:** главные кандидаты — дорогие расчёты на промахах кэша, последовательная сборка данных по менеджерам и тяжёлый SQL. Постоянное насыщение VPS и нехватка JDBC-соединений не подтверждены. Достижение 100 мс требует ограничить работу каждого интерактивного запроса; одним увеличением TTL или числа потоков задачу надёжно не решить.

## 2. Конкретные кандидаты в коде

1. **Профиль менеджера собирает общий рейтинг.** `ApiCabinetController.java:969` вызывает `managerPerformanceService.score(selectedDate)`, затем выбирает одного пользователя. В `ManagerPerformanceService.java:79` при miss загружаются все менеджеры и их месячные controls/items/concreteItems; дальше идут группировки. У рейтинга уже есть двухминутный кэш, поэтому дорогой расчёт выполняется не на каждом вызове. Однако он хранит одну дату, и чередование дат может вытеснять полезный результат. Предложение: scoped query для одного менеджера либо готовая проекция рейтинга с чтением нужной строки, без изменения формулы оценки.
2. **Today делает серию расчётов на каждого менеджера.** `ManagerControlBoardWorkflow.java:103` последовательно вызывает `managerControl`. В `ManagerControlDailySnapshotWorkflow.java:167` тот собирает статусы, прогресс работников, просрочки, риски, automation issues (лимит 10 000), финансовую диагностику. Пакетное получение по набору разрешённых managerId и summary projections сократит повторную работу. Сам цикл виден в коде; число SQL в production пока не измерено.
3. **Profile/team совмещают много блоков.** `ApiCabinetController.java:125, 257, 709, 997`: профиль, заработок/статистика, рейтинг, дневной прогресс команды; team также дневной/месячный прогресс, нарушения и patterns. Нужны segment spans и измерение каждого блока, затем пакетные запросы и предрасчёт наиболее тяжёлых блоков.
4. **Кэш уже не примитивный.** `cached` на строке 466 использует `cache.get(key, loader)`; Caffeine поддерживает совместную загрузку одного ключа. Не нужно повторно «внедрять single-flight» для этого пути. `refresh=true` явно evict-ит ключ: измерить долю таких запросов и источники invalidation. Prod default TTL уже 3 часа (`application-prod.properties:23`), фактическое значение VPS не считывалось. Увеличивать его без политики свежести опасно и недостаточно.
5. **Сегментные метрики не покрывают медленные пути.** В Prometheus соответствующая шестичасовая выборка пуста; в локальном коде recordSegment вызывается для score/analyse. Из имеющихся графиков нельзя разложить задержку профиля на SQL/CPU/сериализацию.

## 3. Цель и бюджет

Предлагаемый SLO для согласованного набора интерактивных GET: **P95 ≤100 мс на серверной HTTP-границе**, внутренний инженерный ориентир ≤80 мс, P99 ≤200 мс как первоначальный дополнительный предел. 80 мс — запас, а не нижняя граница. Это предложение, не достигнутый результат и не универсальный мировой норматив. SLO задаётся на маршрут, роли, размеры данных, допустимую свежесть и нагрузку. Практика определения SLI/SLO: [Google SRE](https://sre.google/workbook/implementing-slos/).

Бюджет одного запроса для проектирования: очередь/proxy 5 мс + security 10 + получение соединения/SQL 35 + сборка DTO 15 + сериализация/отправка на сервере 15 + резерв 20 = 100 мс. Эти значения — гипотеза бюджета, не замеры; складывать независимые P95 компонентов и считать это P95 запроса нельзя.

Время в браузере измерять отдельно с реальной географией, RTT, TLS и размером ответа. При большом RTT серверные 100 мс не обеспечат 100 мс у пользователя. Команды синхронизации и ожидание внешних сервисов имеют отдельную семантику/SLO; нельзя считать быстрый 202 завершением операции.

Для SQL начать с `EXPLAIN FORMAT=JSON`; `EXPLAIN ANALYZE` действительно исполняет запрос, поэтому тяжёлые планы исследовать на изолированной копии с реалистичными объёмами. Индексы добавлять по WHERE/JOIN/ORDER BY и планам, проверяя стоимость записи, блокировки DDL и место. Источник: [MySQL 9.7 EXPLAIN](https://dev.mysql.com/doc/refman/9.7/en/explain.html?ff=nopfpls).

Из существующих архитектурных границ сохранять controller → application/workflow → domain services/repositories. Проекции и batch API принадлежат своему модулю; не переносить SQL в контроллеры и не дублировать правила расчёта зарплаты/рейтинга. GET today уже отделён от syncToday — сохранить это разделение. Если менять sync API на асинхронный, обновить контракт и клиентов: durable operation ID, status, ошибка, идемпотентность и повторная авторизация.

## 5. Безопасность и свежесть

Проверять права на каждом запросе, включая cache hit. Для profile ключ сейчас включает principal/date/aggregate flag, но не версию прав. До усиления кэширования проверить отзыв роли, блокировку пользователя и изменение состава команды: одна авторизация на этапе загрузки DTO недостаточна для долгоживущего кэша. Это рекомендация аудита, не доказательство существующей утечки. Источник: [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

Не ослаблять JWT issuer/audience/expiry, TLS, проверки принадлежности объектов, CSRF там, где он применим, rate limits, транзакционные гарантии и денежный аудит. Не уменьшать durability MySQL ради более быстрых commit. Финансовые команды всегда проверяют актуальное состояние в своей транзакции; экранный агрегат не становится источником истины для записи.

Для статистики определить max age и возвращать updatedAt; не включать stale-while-revalidate для всех данных автоматически. При недоступности проекции применять явно определённый fallback, ограниченный по стоимости, либо честное состояние недоступности. Для нескольких app replicas потребуются согласованная invalidation/версионирование; Redis добавлять только при доказанной необходимости.

В tracing не писать токены, cookies, сообщения, персональные данные и SQL bind values; route templates вместо идентификаторов в metric labels. Ограничить sampling/retention и доступ к telemetry. Источник: [OpenTelemetry: sensitive data](https://opentelemetry.io/docs/security/handling-sensitive-data/).

Не увеличивать Hikari «до 100» или запускать все запросы параллельно: текущий пул не выглядит bottleneck, а дополнительная конкуренция способна ухудшить хвост. Источник: [HikariCP Pool Sizing](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing).

## 6. Как доказать достижение цели

1. Исправить подписи Grafana, добавить точные classic histogram buckets 0.08 и 0.10 секунды и отдельный latency SLI: доля допустимых запросов ≤100 мс; рядом N, P50/P95/P99 и success/error. При малом N показывать недостаточную выборку, а не убедительный P99. Histogram quantile — оценка внутри buckets: [Prometheus](https://prometheus.io/docs/practices/histograms/).
2. Расширить имеющийся isolated MySQL benchmark именно маршрутами cabinet.profile, cabinet.team, today и manager.board. Текущий FinancialScenarioBenchmark проверяет CommonBillingService.managerBoardPage — это другой сценарий, не доказательство скорости manager.board. Документированные бюджеты 128/46/58 SQL фиксируют регрессии, а не желаемую эффективность.
3. HTTP-тестировать авторизованные роли на синтетических данных реалистичного масштаба: разные пользователи/даты, маленькие и большие команды, hit/miss, explicit refresh, конкурентная invalidation, после перезапуска и при работающих фоновых jobs. Проверять JSON и бизнес-результат, а не только статус 200.
4. Нагрузка open model с фиксированной интенсивностью, чтобы замедление сервера не уменьшало незаметно частоту запросов. Подобрать интенсивность по реальному пику и прогнозу; отдельно ступенчатый поиск предела. Контролировать dropped_iterations, насыщение генератора и ошибки. Источники: [k6 arrival rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/), [thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/).
5. Для устойчивой оценки хвостов получить тысячи запросов на ключевой маршрут/режим, повторить прогоны и оценить разброс. Показать отдельно cold-start и cache-miss; быстрые отказы не засчитывать как успешное выполнение. Принятие: P95≤100 мс при заданной нагрузке, отсутствие роста ошибок, соблюдение max age, неизменность расчётов и проверки доступа при смене ролей/команд.
6. Выпускать небольшими изменениями: измерения → SQL → проекции → кэш → ресурсы. Критерии отката: нарушение доступа, расхождение финансовых результатов, необработанные jobs, превышение max age, рост ошибок/latency. Миграции делать совместимыми с предыдущей версией, чтобы откат чтения не требовал удаления данных.

Первый практический пакет: instrumentation профиля/today + baseline + анализ CTE completions. Затем scoped rating и batch today. Покупку более мощного VPS решать после сопоставления задержек с CPU throttling/PSI/I/O: текущая диагностика такой необходимости ещё не доказала.
