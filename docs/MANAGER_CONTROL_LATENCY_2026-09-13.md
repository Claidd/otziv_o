## Изменения

1. Для `ACKNOWLEDGED` сервер сначала авторизует доступ и читает снимок исходного
   сообщения в короткой транзакции. Вызов DeepSeek выполняется после завершения
   чтения, до транзакции изменения карточки. При сохранении доступ проверяется
   повторно, исходное сообщение читается с блокировкой и сверяется по идентификатору,
   тексту, времени и принадлежности менеджеру. Изменившееся или переданное
   другому менеджеру сообщение требует новой проверки. Доказательство
   проверки создаёт только сервер; HTTP-запрос не может передать готовое одобрение.
2. Проверенные решения DeepSeek объединяются для конкурентных запросов одного
   точного текста и кешируются на пять минут, максимум 512 записей. Ключ содержит
   SHA-256 полного текста и порог уверенности. Недоступность провайдера и ошибки
   ответа не кешируются как решения. Перед использованием проверяются доступность
   DeepSeek и текущий порог. Жёсткие правила запрета закрытия вопросов, проблем и
   поручений, контроль частых закрытий и журналирование решения сохранены.
3. Рейтинг читает проекцию из пяти полей клиентских сообщений вместо полных
   сущностей с текстами переписки. Условия выбора, границы периода, принадлежность
   менеджеру, все строки и формулы остаются прежними. Страницы переписки продолжают
   получать полные данные через существующие запросы.
4. Детали контроля загружают сохранённые карточки для всех пунктов одним запросом.
   Для синхронизации сохраняется `FOR UPDATE` с порядком по идентификатору.
   Обновление устаревших карточек, актуальные примеры и все поля ответа сохранены.
5. Сверка очереди обычных заказов и повторных счетов читает существующие состояния
   пакетами до 500 записей вместо запроса на каждый заказ. Обе ветки используют
   прежнюю функцию перехода состояния: сохраняются запреты повторной отправки,
   восстановление допустимых задач, даты, попытки и сведения о доставке.
6. Синхронизация менеджера проверяет доступ до запуска общей сверки сообщений
   в отдельной короткой транзакции. Повторная проверка и чтение деталей происходят
   после сверки, чтобы снимок MySQL REPEATABLE READ видел её результаты.

## Проверка и ограничения

Контракт межмодульного API: владелец `client_chat_control` предоставляет
`ClientChatNoResponseReviews` модулю контроля. Вызывающая сторона сначала
авторизует карточку; владелец проверяет принадлежность сообщения тому же менеджеру
и возвращает неизменяемое серверное доказательство `PreparedNoResponseReview`.
Чтение использует короткую read-only REQUIRED транзакцию, AI-проверка — NOT_SUPPORTED.
Доказательство включает только скалярный снимок и неизменяемое решение AI, без ORM.
При записи владелец повторно проверяет снимок под блокировкой. HTTP не принимает
и не возвращает этот контракт. `ClientChatPerformanceSample` — read-only DTO для
reporting; он не предоставляет записи или доступа к переписке. В публичном API
экспортированы только эти три типа, новые обходы repository и циклы запрещены.

Целевые тесты проверяют совпадение старой и новой JPQL-выборки на MySQL, границы
периода и разделение менеджеров, сохранение процентилей ответа и backlog,
отсутствие чтения текстовых столбцов при расчёте рейтинга, изменение сообщения
во время проверки, недоступность AI и изменение порога уверенности. Отдельно
проверяются транзакционная граница и запреты повторного запуска доставок.

Новая проверка DeepSeek по-прежнему занимает время внешнего сервиса. Ответ HTTP
считается завершённым только после принятия или отклонения решения, а не после
постановки задачи в фон. Поэтому универсальные <100 мс для первого AI-действия
этими изменениями не обещаются. Новые данные не удаляются и не скрываются ради
достижения показателей; глобальная сверка сообщений не пропускается.

После проверки CI требуется обычный выпуск из чистого `main` и замеры на новой
ревизии. Действия над реальными карточками и отправки клиентам не используются
как искусственная нагрузка. Контроллерные и полные HTTP-таймеры сравниваются
отдельно, с указанием выборки, прогрева и времени запуска backend.
