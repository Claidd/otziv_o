# ADR-016: повторяемая задержка интерактивных чтений

Дата: 12 сентября 2026. Продолжает ADR-015 и план VPS_LATENCY_PLAN_2026-09-11.

## Границы решения

Сохраняется модульный монолит: контроллер вызывает прикладной сервис, чтение принадлежит
своему модулю, команды сохраняют транзакции, блокировки и аудит. Цель приёмки — серверный
P95 успешных интерактивных GET ≤100 мс при явно указанной нагрузке; 80 мс оставляет запас.
Это выбранный SLO продукта, а не универсальный отраслевой норматив. Внешняя сеть, первое
TLS-соединение и неизвестный IP требуют отдельного измерения. Нельзя засчитывать быстрый
отказ доступа как успешное выполнение страницы.

## Данные и запросы

Зарплатная аналитика использует актуальное SQL-представление ежедневных итогов. Сначала
каждая из трёх канонических ветвей агрегируется по пользователю/дате, затем результаты
объединяются. Правила приоритета ledger → live → archive сохранены, включая неактивную
ledger-запись и пересечение архива с восстановленной live-записью. DISTINCT исходного
начисления считается внутри ветви; множества исходных начислений между ветвями не
пересекаются. Общий междневной COUNT DISTINCT остаётся на прежнем каноническом view.
Два покрывающих индекса начинаются с user/active/date. Миграция совместима с предыдущим
приложением и использует INPLACE/LOCK=NONE, но краткие metadata locks всё равно возможны.

Сводка начислений читает ledger, события расчётов и непогашенные резервы пакетно по
профилям. Начальный баланс, выбранный месяц, LIVE/SHADOW и возвраты учитываются той же
арифметикой, что и личная сводка. Финансовые суммы не кэшируются. Интеграционная проверка
на MySQL сравнивает пакетные результаты с прежними отдельными запросами, включая
отрицательные суммы, границы месяца и немедленную видимость изменения начального баланса.

Активность команды загружается сразу по разрешённому набору менеджеров. Из сообщений
выбираются только времена STAFF-событий, из посещений — времена и типы. Расчёт пересекающихся
интервалов и фильтрация по автору сохраняются; текст сообщений для статистики не загружается.

Отдельный асинхронный финансовый итог здесь не вводится: неполная invalidation среди
многочисленных writers давала бы неверные суммы. Триггеры потребовали бы дополнительных
привилегий при существующей политике binlog. Live-view сохраняет видимость commit и
rollback без новых привилегий. Успешный пустой запрос зарплаты возвращает нулевую статистику;
ошибки БД продолжают распространяться и не превращаются в нули.

Два видимых счётчика специалиста используют отдельные индексные диапазоны vigul=true/false.
Общий CASE-агрегат оказался медленнее в повторном нагрузочном тесте и исключён. Различие
manager scope для публикации и нагула сохранено. Неиспользуемый счётчик отзывов по статусу
больше не вычисляется в обычной сборке board. Соединения страницы только to-one, поэтому
GROUP BY и COUNT DISTINCT идентификаторов на этом пути не нужны.

Заказы показывают сохранённое состояние клиентских сообщений после одной пакетной выборки.
GET больше не выполняет команду восстановления для каждой отсутствующей записи. Ремонт
сохраняется в существующем leased reconciliation worker, который сканирует канонические
заказы; обычный интервал полной сверки — пять минут. Прямые producers после изменения
заказа сохраняются. Если worker выключен или приостановлен, GET не обходит это решение.
Интерфейс честно показывает отсутствие состояния до восстановления.

Для карточек общих счетов два запроса на каждый счёт (наличие факта распределения и сумма
предоплаты) заменены двумя пакетными запросами на страницу. Результаты существуют только
в текущей транзакции сборки board. Условия evidenceId IS NULL, источник COMMON_INVOICE и
статус PREPAID сохранены. Команды подтверждения/закрытия и последующие внутренние
пересчёты продолжают читать свои актуальные данные; их блокировки и аудит не меняются.

## Холодные и фоновые пути

Worker access хранит только успешное наблюдение провайдера IP, включая отрицательную
классификацию риска. Ключ — SHA-256 версии формата, provider URL и нормализованного IP.
Это внутренний псевдоним, не гарантия анонимности. Полный IP не попадает в эту таблицу и
в диагностические метрики. Проверки пользователя, устройства, текущей политики и доступ
к разделу выполняются при каждом обращении; разрешение доступа не кэшируется.

Исходные observed/expires сохраняются в UTC epoch milliseconds. Перезапуск и попадание в
кэш не продлевают TTL. Более строгий текущий TTL также проверяется, запоздалая запись не
заменяет новое наблюдение. Ошибка кэша возвращает существующий путь проверки провайдера;
неизвестная сеть обрабатывается прежней политикой. Запись optional cache использует
отдельную транзакцию. Память ограничена 10 000 записями; SQL cleanup удаляет до 1 000
просроченных и до 1 000 лишних записей за tick, стремясь к 10 000, без обещания жёсткого
мгновенного ограничения размера таблицы.

На незащищённой вкладке аутентифицированного worker-only запускается предварительное
наблюдение сети: один поток, очередь 64, дедупликация и singleflight с обычным lookup.
Запросы при полной очереди пропускаются. SecurityContext не передаётся фоновому потоку.
Первый прямой вход на защищённую вкладку с неизвестным IP всё ещё может ждать провайдера.
Ослабление этой проверки ради 100 мс не допускается.

Manager snapshot завершает проход в последней реальной партии, без дополнительного tick
для обнаружения конца. Предел — 25 менеджеров, один поток, прежний бюджет начала партий
20 секунд и timeout транзакции 45 секунд. Cursor/lease fencing/commit остаются общими с
результатом партии. Причины fallback измеряются отдельно: absent, invalidated, scope, expired.

## Интерфейс и измерения

Manager/worker board отменяют прежнюю HTTP-подписку при новой загрузке и уходе со страницы.
Проверка последовательности ответов остаётся. Это прекращает ненужное ожидание в браузере;
уже начавшийся SQL на сервере не обязательно отменяется вместе с HTTP.

Кабинет браузера сохраняет singleflight, но TTL сокращён с трёх часов до 30 секунд.
Ключ включает subject, login session и роли. Ошибка старой загрузки не удаляет результат
более нового refresh. Два последовательных кэша по 30 секунд могут суммарно дать до
60 секунд старения экранных данных; финансовые команды всё равно читают актуальную БД.
Возраст прогресса в ADR-015 проверяется при построении DTO: к его серверному пределу
150 секунд браузер может добавить ещё 30 секунд до следующего чтения. Это не таймер
автоматического обновления уже открытой страницы.

HTTP observation охватывает security → controller → serialization, связывает вложенные
service observations. Отдельно измеряются получение соединения, execute и ResultSet.next;
последняя метрика не претендует на полное время всех JDBC getters. Фазы controller и его
окружения не складывают с вложенными SQL/service segments. Медленный лог содержит только
фиксированные имена, классы статуса, количества и времена, не более одного события/сек.
Токены, IP, SQL, bind values, пользовательские данные и тексты исключений туда не попадают.

Grafana открывает полные HTTP-метрики и отделяет process runtime. Текущие P95/P99 используют
instant query, конечное значение и минимальную выборку 100/1 000 за пять минут. Отдельно
показаны накопленный N процесса и возраст последнего запроса: increase/rate могут не
видеть обращения до первого scrape. Отсутствие новых данных не маскируется последним
старым P95. Исторические controller timers доступны отдельно.

## Приёмка и выпуск

Проверить эквивалентность финансовых источников на MySQL, отзыв scope/rollback/lease,
сроки и failures IP cache, роли/непустые страницы, concurrent UI requests и обновление
после TTL. Сравнить старый и новый image на одинаковых CPU/RAM и БД, отдельно холодные
запросы и открытый поток arrivals. N, доля ≤100 мс, P95/P99, ошибки и dropped iterations
обязательны. Низкий N production не даёт основания заявить устойчивый P95.

Выпуск проходит обычные CI, архитектурные/security gates, backup и release lineage.
Откат приложения совместим с добавленными таблицей/view/индексами; удаление финансовых
данных, отключение защиты или обход deployment gates не являются способом ускорения.

Основы: [Google SRE SLO](https://sre.google/workbook/implementing-slos/),
[Prometheus histograms](https://prometheus.io/docs/practices/histograms/),
[OWASP authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html),
[k6 constant arrival rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/).
