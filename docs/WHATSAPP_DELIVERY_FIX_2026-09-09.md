# Подтверждения WhatsApp и фоновые уведомления — 9 сентября 2026

WhatsApp Web изменил MsgKey: `id._serialized` исчез, хотя сообщение может быть
успешно принято сервером. Это превращало успешные отправки в UNKNOWN и ломало
идентификацию входящих сообщений и выборку истории в whatsapp-web.js 1.34.7.

## Совместимость и сверка

Адаптер устанавливается после внедрения WWebJS и до обработчиков событий/READY,
в том числе после повторного подключения. Он восстанавливает доступ библиотеки
к MsgKey через `toString()` и собственное поле сериализованного результата.
JSON-объекты дополнительно распознаются по компонентам ключа. Привязки к
минифицированному имени `$1` нет; идентификатор и ключ бизнес-операции сохраняются.

Внутренний `POST /operations/:operationId/reconcile` принимает только `messageId`.
Содержимое, адресат, время и подтверждение ACK читаются из авторизованной сессии
WhatsApp. Проверяются идентификатор, направление, ACK >= 1, интервал выполнения
и полный хеш исходного конверта. Только после этого UNKNOWN становится SUCCEEDED.
Запрос защищён существующей аутентификацией шлюза и ограничителем задач.
Подтверждённый ID также сохраняется как исходящее сообщение приложения для inbox.

Повторная отправка при сверке отсутствует. Неоднозначные и отсутствующие
доказательства сохраняют UNKNOWN. Перед восстановлением накопленных подтверждений
нужны резервные копии журналов и положительная сверка каждого сообщения. Известные
ID исходящих сообщений приложения должны быть отмечены до возобновления входящей
истории, чтобы они не были ошибочно классифицированы как ручные сообщения.

## Фоновые автоматические уведомления

Подтверждение оплаты и завершение задачи по плохому отзыву больше не выполняют
отправку в потоке HTTP/afterCommit. После commit они будят отдельный ограниченный
пул: 2 потока, очередь 128, без CallerRunsPolicy. Данные остаются в прежних
постоянных очередях владельцев: retry-флаг оплаты и ScheduledClientMessageState.
Существующие планировщики подхватывают работу после потери или отказа wakeup;
claim, неизменяемый operation ID и проверка результата защищают от повторов.

Отдельный HTTP-клиент WhatsApp использует `whatsapp.http-client.connect-timeout`
(по умолчанию 5 секунд) и `whatsapp.http-client.read-timeout` (30 секунд).
Общий таймаут приложения 150 секунд больше не увеличивает ожидание WhatsApp.
Таймаут сохраняет неоднозначный результат: он не разрешает повторную отправку.

Это изменение автоматических уведомлений; ручные команды отправки в manager
control, общих счетах и выключенном legacy MVC сохраняют свои существующие
контракты ответа. Оно не объявляет все API приложения асинхронными.

## Проверка

Регрессии проверяют старый и текущий формат ID, сериализацию и повторную инъекцию,
положительную сверку без отправки, отказы для чужого содержимого/адресата/времени,
отсутствующего ACK, rollback, заполнение пула и возврат управления при заблокированном
провайдере. Проверки MySQL сохраняют требования коротких транзакций и единого claim.
Локальная интеграционная приёмка использует штатный prod-like smoke со свежим
восстановлением БД и отключёнными внешними отправками. Эксплуатационные квитанции,
резервные копии и доказательства сообщений хранятся вне Git.
