1. Перенести замену в application service. До PUT зарегистрировать уникальный object key в постоянном upload registry; PUT выполнять вне блокировки бизнес-строки.
2. В короткой транзакции проверить права и версию/lock владельца, прочитать актуальную старую ссылку, привязать новый объект, отметить registry ATTACHED и создать cleanup intent для вытесненного объекта.
3. Запись cleanup intent должна участвовать в той же транзакции и гарантированно откатывать её при ошибке. Существующий best-effort enqueue в REQUIRES_NEW не обеспечивает эту гарантию.
4. Выполнять delete после commit отдельным обработчиком с идемпотентным завершением. Восстанавливать незавершённые uploads через registry; состояние/lease загрузки и переходы attach/cleanup должны исключать удаление ещё привязываемого объекта. После cleanup claim привязка запрещена; позднее завершение медленного PUT обязано повторно попадать в cleanup, даже если предыдущий delete видел отсутствие объекта.
5. Для исторических orphan-объектов сначала получить отчёт сверки ссылок и принадлежности. Удалять только доказанно неиспользуемые объекты после защитного интервала.

Приёмка: crash после PUT, после commit до delete и после delete до завершения задания оставляет восстанавливаемое состояние. Два upload сохраняют актуальное фото и учитывают все вытесненные объекты; rollback не удаляет прежнее фото; sweep не удаляет живую ссылку. Медленный PUT одновременно со sweep не оставляет поздний объект без задания. План миграции сохраняет существующую очередь cleanup.

**Правила изменений данных и выпуска**
