# Обычный деплой с проверкой CI

Запускайте из основной рабочей папки `otziv`, в PowerShell 7:

```powershell
git switch main
git pull --ff-only origin main
& .\deploy.ps1 -Tag '30.00'
```

Тег — новое имя выпуска; скрипт сам добавляет SHA коммита. Буква диска не
закреплена: SSH-ключ, `known_hosts` и env берутся из соседних `.ssh` и
`.otziv/env` относительно основной папки проекта. Для другой структуры передайте
`-ProjectFilesRoot` или явные пути. Нужны Git с входом в GitHub через Credential
Manager, Python 3, Docker Desktop и SSH. PowerShell 7 запускается командой `pwsh`.
Из Windows PowerShell 5 скрипт сам запускает установленный PowerShell 7: использует
PATH, путь из соседнего `otziv-deploy/powershell.path` или стандартную папку установки.
Если политика Windows блокирует запуск, разрешите его только для отдельного
процесса: `pwsh -NoProfile -ExecutionPolicy Bypass -File .\deploy.ps1 -Tag '30.00'`.

Для проверки CI без запуска Docker и без изменений VPS:

```powershell
& .\deploy.ps1 -CheckOnly
```

Команда допускает только чистую `main`, совпадающую с `origin/main`. Она проверяет
последние push-запуски четырёх обязательных workflows на этом SHA, все 20 заданий,
их принадлежность GitHub Actions, текущую попытку и дополнительные внешние
проверки безопасности. Старый успешный запуск не заменяет новый неудачный. При
отсутствии связи с GitHub, незавершённой проверке или результате старше семи дней
деплой не начинается. Перезапустите проверки **main** в Actions и дождитесь их
завершения. CI выполняется для каждого изменения, а выкладка начинается только
после запуска команды пользователем.

Образы собираются, проверяются и сканируются в CI. Проверка парного восстановления
использует тот же образ backend из артефакта, без отдельной сборки. Установщик
скачивает маленький манифест успешного push-запуска `main`, проверяет SSH, здоровье сервисов,
отсутствие другого деплоя, работу self-heal и запас места на VPS. Расчёт учитывает
слои новых образов, уже имеющиеся слои, временную распаковку, резервную копию БД
и свободный резерв 1 ГиБ. Эта проверка выполняется **до скачивания больших архивов
и подготовки транспорта**. Сборок на компьютере оператора и VPS больше нет.
Проверки кода в GitHub выполняются независимо от доступности production.

Затем установщик скачивает неизменяемые артефакты CI и проверяет их GitHub ID,
SHA256, исходный коммит, конфигурацию и слои образов. При упаковке Docker-образа
в OCI сохраняются исходная конфигурация и проверенные несжатые слои; при передаче
в закрытый реестр уже сохраняется и OCI manifest digest. Повторной сборки нет.
Временный реестр доступен только через loopback и SSH-туннель. Доступ на запись
в Docker Hub не требуется. Перед установкой реестр переводится в режим чтения,
CI проверяется повторно, а штатный `deploy-prod.ps1` сохраняет проверки целостности
БД, повторные проверки места, создание и проверку зашифрованной резервной копии,
обновление и проверки сервисов. При
ошибке выполнение останавливается с диагностикой; обхода этих проверок в обычной
команде нет. Контейнер передачи останавливается, туннель закрывается, локальные
образы и том сохраняются для восстановления. Не удаляйте образы рабочего и
резервного выпусков на VPS: адрес временного реестра доступен только во время
передачи. Для повторной установки используйте новый запуск команды.

Действующий `.env` сервера сохраняется. Локальный `.otziv/env/prod.env` должен
содержать совпадающий ключ проверки резервной копии. Изменения конфигурации
инфраструктуры требуют отдельной проверки совместимости. Установленный APK
сохраняется; новый подписанный APK можно передать через `-MobileApkPath`.

Локальные отчёты CI, состояние реестра и резервная копия сохраняются вне Git в
`~/otziv-deploy/releases/<тег>-<идентификатор>/` в домашней папке оператора с
закрытыми правами доступа. Старую команду с
`-SkipAutoSnapshotValidation` для обычных выпусков использовать не следует.

Для локального исследования изменений бизнес-логики есть
`infrastructure/scripts/local/prod-like-smoke.ps1`: по умолчанию он восстанавливает
свежую копию production-БД только в локальном Docker и блокирует внешние рассылки.
Штатный релиз не повторяет уже успешные тесты CI локально.

## Какие проверки запускаются

- Для рабочей ветки запускается PR-проверка; дублирующего push-запуска нет.
  После слияния `main` проверяется отдельно: это источник устанавливаемого релиза.
- Компонентные тесты выбираются по полному diff. Общие библиотеки расширяют
  набор потребителей; удалённые и переименованные файлы учитываются.
  Неизвестный путь, изменение CI/общей инфраструктуры или недоступная история Git
  включают полный набор. Ручной запуск также включает полный набор.
- Пересборка инфраструктурных кандидатов и репетиции обновлений хранилищ
  запускаются при изменениях инфраструктуры. Правка интерфейса или бизнес-логики
  больше не пересобирает Grafana, Alloy, Loki, Tempo и Prometheus.
- В `main` все релизные образы проходят сборку с сохранённым BuildKit-кешем,
  smoke-проверки и свежий скан; неизменившиеся слои берутся из кеша. Проверка
  закреплённых upstream-образов также сохраняется. Кеш из PR не заменяет кеш `main`.
- Обязательные 20 имён проверок сохраняются. Незатронутый компонент явно
  отчитывается об отсутствии изменений; ошибка выбора проверок блокирует gate.
  Секреты, миграции, политика безопасности и контракты репозитория проверяются всегда.

## Ежедневное сканирование установленного релиза

После успешной установки команда сверяет конфигурации реально запущенных
контейнеров с CI и закреплёнными инфраструктурными образами. Их идентификаторы
сохраняются в GitHub Deployments; секретов и содержимого `.env` в записи нет.
Для записи нужны права GitHub на deployments (обычный вход владельца через GCM).

Workflow **Production image security** запускается ежедневно в 04:23 UTC и вручную.
Он сканирует образы из последней подтверждённой записи production, используя
свежую базу уязвимостей. Отчёты, SBOM и диагностика доступны в Actions. Ошибки
сканера и исправляемые HIGH/CRITICAL дают красный результат; suppressions не добавлены.
Проверка не подключается к VPS и не получает его SSH-ключ. Она не блокирует
публикацию исправленного образа находками в старом работающем релизе.

Изменения образов вручную, в обход установщика, требуют повторной сверки и
регистрации production: ежедневный скан не является удалённым опросом Docker.
Если установка завершилась, но регистрация не удалась, повторите только
`production_images.py record` с сохранённым `ci-release.json` и теми же параметрами SSH;
повторно выкладывать приложение для этого не нужно.

Артефакты образов и манифест хранятся 90 дней, отчёты ежедневного скана — 30 дней.
При удалении/истечении артефакта скан и установка останавливаются с ошибкой;
автоматической подмены локальной сборкой нет. До истечения срока выполните новый
проверенный выпуск. После частичного перезапуска CI сборщик манифеста использует
последние успешные квитанции компонентов этого же коммита и запуска.

Первый запуск после изменения самого CI выполняет полный набор и наполняет кеши.
Обычные изменения после этого обходятся без повторных локальных сборок и тяжёлых
репетиций инфраструктуры. Время тестов затронутого компонента и проверки новых
уязвимостей сохраняется.
