# Keyed Telegram/MAX delivery and manual receipt reconciliation

`ClientMessageOperationFence` owns a durable local barrier for keyed non-WhatsApp financial sends. The sender supplies an operation ID, platform, destination and a canonical JSON payload containing `[message, copyButton.text, copyButton.copyText]`, including null entries. V304 stores only destination/envelope hashes, platform, state, token and result metadata; message/recipient plaintext is absent. The administrator resolution audit records actor, receipt and reason in the same short transaction as the resolution.

The public orchestrator suspends any caller transaction. A separate proxied store commits PREPARED and an exclusive random attempt token before the provider callback. The callback runs outside a database transaction. Only a validated Telegram/MAX receipt becomes SUCCEEDED. Provider errors, absent receipts, commit failure and restart leave UNKNOWN/PREPARED barriers; no lease expiry or restart permits automatic replay. A successful receipt is replayed locally before checking mutable current routing, so it cannot trigger another primary message or optional copy.

Known pre-dispatch refusals may retry only the exact platform, destination and complete payload hashes. Every such attempt receives a new token; a late result from a previous token cannot overwrite it. Changed bank-copy data is a changed envelope. The lookup before current platform selection prevents an unresolved Telegram/MAX occurrence from becoming a new WhatsApp send. WhatsApp uses its separate durable operation protocol.

For an actual OWNER/ADMIN, `GET /api/admin/client-message-operations/{operationId}` returns state, hashes, attempt token and any receipt. `POST /api/admin/client-message-operations/{operationId}/confirm-delivered` accepts `expectedClaimToken`, `expectedEnvelopeHash`, `providerMessageId`, and a 12–1000-character `reason`. Verify the exact operation against the message visible in the provider's interface before submitting this attestation. Receipt syntax must match the recorded platform. Preserve the receipt/evidence reference in the audit reason; do not include credentials or copy message content into it. A mismatched token/hash/receipt rejects the command. A failed audit write rolls back the resolution. Repeating the same confirmation is idempotent.

This endpoint permits **delivered confirmation only**. A missing receipt, timeout or absence from a partial history is not proof of non-delivery and cannot reset UNKNOWN to unsent. Keep the occurrence quarantined when delivery cannot be established. The operation ID comes from the initiating business record: `payment-success:<paymentLinkId>` or the invoice's persisted message operation ID. The UI/caller should expose that identifier with its unresolved result without exposing message text. No garbage-collection/TTL policy removes these barriers; retention must remain compatible with the business operation's retry lifetime.

`ClientMessageOperationFenceMySqlIntegrationTest` exercises the production V304 schema and actual Spring transaction proxies on independent MySQL connections: caller rollback, provider outside TX, concurrent claim, restart UNKNOWN, exact-envelope retry, receipt replay, failed final commit, stale token, explicit administrator authorization, atomic audit failure and the real controller HTTP route. All provider calls are fixtures; these tests send no Telegram/MAX messages.
