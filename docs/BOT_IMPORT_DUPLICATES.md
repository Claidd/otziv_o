# Источники аккаунтов и повторные поставки

В справочнике «Аккаунты» после импорта CSV, TSV, XLS или XLSX показывается отчёт о дублях:

- логин и строка в проверяемом файле;
- ID оригинала, дата первого импорта, название исходного файла и строка оригинала;
- причина: аккаунт уже добавлялся или повторяется внутри текущего файла.

Кнопка «Скачать дубли CSV» выгружает все совпадения. В таблице отображаются первые 100 строк.
Скачайте отчёт до закрытия окна импорта. Пароли в отчёт не включаются.

Если найдены дубли, автоматически формируется TXT с готовым обращением к поставщику:
название текущего файла и дата проверки, количество новых и повторных строк, затем полный список
совпадений с логинами, ID оригиналов, датами первого добавления, исходными файлами и номерами строк.
Отчёт включает все совпадения, в том числе за пределами первых 100 строк интерфейса.

TXT отправляется администратору через Telegram. Получатели берутся из `telegram.admin.chat-ids`;
если список пуст, используются привязанные Telegram-чаты активных пользователей с `ROLE_ADMIN`.
Повторяющиеся чаты не получают несколько копий. В интерфейсе показывается постановка в очередь,
а не неподтверждённое сообщение об успешной доставке.

Содержимое отчёта попадает в таблицу `bot_duplicate_report_delivery` в одной транзакции с импортом
(миграция `V1_10_322`). После отката импорта ничего не отправляется. Отправка выполняется в фоне
после фиксации транзакции, по умолчанию проверка очереди идёт каждые 30 секунд.

Само TXT-вложение формируется в памяти, без временного файла на диске. После подтверждения
доставки каждому получателю вся временная запись, включая текст отчёта, удаляется из БД.
При ошибке, отсутствии адресата или выключенной отправке документ сохраняется для повторной
попытки. Интервал повторов растёт от 30 секунд до часа. После частичной доставки повтор получают
только адресаты без сохранённого подтверждения. Перезапуск приложения не теряет очередь.
При обрыве связи после фактической отправки, но до получения или сохранения подтверждения,
Telegram может получить повторную копию; номер отчёта и имя файла при этом остаются прежними.

Флаг `telegram.bot.sending-enabled=false` останавливает отправку и сохраняет ожидающие отчёты.
Параметры `otziv.bot-import.reports.fixed-delay-ms` и `initial-delay-ms` задают период проверки
и начальную задержку планировщика (по умолчанию 30000 и 60000 мс).

Повтор определяется по логину без учёта регистра и пробелов по краям. Пароль, имя файла,
город и статус аккаунта не меняют результат проверки. Новый аккаунт сохраняется один раз;
повторные загрузки не перезаписывают первоначальный источник. Реестр источников сохраняется
и после удаления аккаунта. Сведения об аккаунтах, удалённых до появления реестра, не восстанавливаются.

Для старых аккаунтов миграция `V1_10_321` восстанавливает дату только из явного события
первоначального импорта в бизнес-аудите. Имена файлов раньше не записывались: вместо отсутствующих
сведений показывается «Не сохранено». Аккаунты, созданные вручную, также распознаются;
если сведений об импорте нет, дата и файл остаются неизвестными.

Реестр и новые аккаунты записываются в одной транзакции. Параллельные импорты сериализуются
блокировкой в БД, чтобы оба файла не приняли один и тот же аккаунт за новый. Блокировка действует
на файловый импорт; ручное создание аккаунтов использует существующий механизм сохранения.

Изменение требует обновления backend и frontend с применением миграции Flyway.

Граница модулей: владелец messaging предоставляет `TelegramAdminDocuments` фоновой
очереди administration. API возвращает только ID чатов администраторов и подтверждение
одной попытки отправки; ORM и транспортные объекты наружу не передаются. Отчёт создаётся
только штатным импортом с его проверкой прав, а сетевой вызов выполняется после завершения
транзакции захвата. Очередь владеет повторами и удаляет содержимое после подтверждений.
