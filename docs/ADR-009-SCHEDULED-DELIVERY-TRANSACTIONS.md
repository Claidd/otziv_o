# ADR-009: короткие транзакции фоновой отправки клиенту

Дата: 8 сентября 2026. Исправление A04.

## Решение

`ScheduledClientMessageService` исполняет обычные клиентские сценарии через prepare → commit → send → finalize. Подготовка блокирует заказ, состояние и общий бюджет именно в этом порядке, повторно проверяет право текущего claim и условия сценария. В БД сохраняется JSON-снимок только из скалярных значений: адресаты и канал, точный текст и денежный payload, copy-button, прежний business operation ID, token, поколение заказа и необходимые результаты успешной отправки. JPA-объекты и lazy-коллекции не пересекают границу отправки.

Вызов Telegram/WhatsApp/MAX выполняется после commit без активной бизнес-транзакции. Финализация открывает новую транзакцию, проверяет token, scenario, targetKey и активное состояние. Устаревший результат не меняет новую задачу. Сохраняются переход платежного напоминания, подтверждение order notification occurrence, переход статуса после повторной доставки счёта/проверки и отметка об уведомлении по восстановлению отзывов. Менеджерские fallback/auth-уведомления работают после этой транзакции с отдельной скалярной проекцией получателей.

Глобальный live-выключатель читается через `getBooleanFreshFailClosed` при подготовке и непосредственно перед provider call, включая отдельный BAD_REVIEW_INVOICE. OFF, некорректное значение и ошибка чтения запрещают provider I/O независимо от кеша экземпляра. Выключение после commit snapshot фиксируется как доказанно неотправленный SKIPPED/dry-run с `RETRYABLE`, прежними envelope/token/operation ID и без manager fallback. Включение возобновляет тот же payload через существующий механизм release dry-run. Для BAD сохранён отдельный сериализованный scalar snapshot, исключённый из ordinary recovery; его прежняя ручная сверка не заменяется новым протоколом.

Повторы `REVIEW_CHECK_DELIVERY_RETRY` и `PAYMENT_INVOICE_RETRY` используют `OrderStatusNotificationService.prepareAction/dispatchPreparedAction/applyPreparedAction`: сохраняется прежний ключ `OrderNotificationOccurrences`, а поздний успешный receipt не перезаписывает изменившееся поколение или статус заказа. Существующий отдельный протокол `BAD_REVIEW_INVOICE` сохраняется; его transport snapshot также стал скалярным.

## Отказы и восстановление

Новый claim помечается `CLAIMED`, и только истёкший claim с такой меткой можно автоматически вернуть в очередь до внешнего I/O. Миграция 309 не переинтерпретирует старые неопределённые записи. После подготовки `PREPARED` блокирует повторную отправку. Подтверждённый отказ до dispatch переводит запись в `RETRYABLE`, сохраняя идентичные ключ, адресата, текст и платёжные реквизиты. Неопределённый результат, исключение или незавершённый commit удерживает `PREPARED/UNKNOWN`.

Восстановление запрашивает только receipt для прежнего operation ID. Для WhatsApp требуется совпадение ID, состояния SUCCEEDED, hash замороженного envelope и непустой message ID. Telegram/MAX используют локальный durable fence. NOT_FOUND, недоступный ledger и UNKNOWN не доказывают отсутствие отправки и не разрешают resend. Ручная сверка локального fence по-прежнему возможна через существующий административный механизм.

Recovery ограничен 20 записями за проход с отдельным временем последней сверки. Старые UNKNOWN и повреждённые снимки не блокируют обработку следующих записей: barrier/backoff фиксируются до JSON decode. Система сознательно допускает задержку/ручную сверку для crash в окне между commit снимка и первым provider call; автоматическая доставка «ровно один раз» через неидемпотентный внешний канал не заявляется.

## Конкуренция и миграция

Миграция `V1_10_309` добавляет snapshot/channel/recovery timestamp и одноэлементную таблицу блокировки бюджета. PREPARED/UNKNOWN учитываются вместе с SENT при проверке дневного лимита, а их dispatch reservation timestamp — при интервалах канала. Подготовка использует READ COMMITTED: после ожидания общего guard она должна видеть reservation, зафиксированную другим экземпляром, независимо от раннего чтения в этой же транзакции. Guard удерживается только на подготовке/финализации, без provider I/O.

После PREPARED→SENT интервал опирается на persisted last-sent timestamp, прочитанный через `getStringFresh` под тем же budget guard. Очистка reservation не открывает окно отправки через старый пятиминутный settings cache другого JVM. Ошибка свежего чтения не разрешает отправку.

Перед выкладкой требуется успешная миграция 309; откат старого бинарника не должен сопровождаться автоматическим сбросом PREPARED/UNKNOWN. Снимок содержит тот же чувствительный текст сообщения/получателя, который ранее записывался в attempts: доступ к БД и срок хранения должны соответствовать действующей политике проекта. Новых module exports и исключений architecture baseline это решение не добавляет.

## Проверка

`ScheduledClientMessageServiceTest` сохраняет проверки содержимого и результатов всех существующих сценариев. `ScheduledDeliveryProtocolTest`, `ScheduledDeliveryReceiptTest`, `OrderStatusPreparedActionTest` проверяют frozen payload, границы транзакций, UNKNOWN, receipt identity и защиту от поздних результатов. `ScheduledDeliveryTransactionMySqlIntegrationTest` использует настоящие mappings и независимые MySQL-соединения: committed snapshot виден при остановленном provider, order/state locks доступны другой транзакции, restart выполняет receipt-only recovery, общий бюджет видит предыдущий commit, новый pre-dispatch claim отличается от legacy uncertainty.

Дополнительные причинные проверки используют две настоящие `AppSettingService` с независимыми прогретыми кешами и MySQL commit: OFF другого экземпляра между подготовкой и отправкой, re-enable с тем же snapshot и отказ следующему сообщению по gap после подтверждённого SENT при уже очищенной reservation. Unit-сценарии отдельно проверяют fail-closed ошибку чтения и BAD pause/resume без изменения суммы, адресата и ключа.
