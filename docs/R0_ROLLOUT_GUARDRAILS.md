# R0: совместимый rollout и неизменяемые публичные контракты

Этот документ фиксирует ограничения для этапов R0–R11. Они являются условиями
приёмки, а не временными рекомендациями.

## Публичные capability-ссылки

`/api/review-check/**` остаётся доступным без регистрации и без пользовательской
сессии любому владельцу ссылки. Владелец ссылки должен иметь возможность:

- открыть проверку;
- изменить текст отзыва и ответ;
- сохранить поле коррекции и остальные доступные на странице изменения;
- разрешить публикацию;
- отправить материалы на коррекцию.

`/api/payments/public/**`, включая общий счёт, остаётся доступным без регистрации:
ссылку можно открыть и инициировать оплату.

Нельзя вводить или включать флаги, которые переводят эти сценарии в read-only,
требуют входа либо запрещают approve. В частности, значения
`review-check.legacy-uuid-write-enabled=false` и
`review-check.public-approve-enabled=false` противоречат продуктовому контракту.
Будущая замена UUID на capability token выполняется через совместимое чтение двух
форматов и не урезает действия владельца ссылки.

Автотест `PublicCapabilitySecurityContractTest` является обязательным regression
gate для security-chain. Контроллерные тесты дополнительно проверяют изменение
текста/ответа, коррекцию и approve анонимным владельцем ссылки.

## Правила feature flags

- Новый read/write path сначала добавляется выключенным либо в shadow/dual-write
  режиме; существующий path остаётся рабочим.
- Флаг не должен менять права существующих ролей без отдельного теста матрицы
  доступа.
- Kill switch внешнего побочного эффекта останавливает только внешний вызов; он не
  должен повреждать уже сохранённые данные.
- Удаление старого path или флага допускается только после измеренного нулевого
  использования и отдельного этапа R11.
- `otziv.legacy.enabled` управляет старым MVC-интерфейсом и не является флагом
  публичных review-check/payment capability-ссылок.

## Порядок безопасного выпуска

1. Снять backup и успешно выполнить изолированный restore drill.
2. Прогнать публичные capability-тесты и полную backend-регрессию.
3. Включить только observability/shadow-режимы, проверить метрики и логи без PII.
4. Выпускать enforcement отдельно, с возможностью немедленно вернуть shadow path.
5. После каждого этапа проверить сценарии ADMIN, OWNER, MANAGER, WORKER, OPERATOR,
   MARKETOLOG, PERFORMER, а также анонимные review-check/payment ссылки.

Мгновенный отзыв уже выданных JWT реализуется на этапе R4 (auth epoch), а
атомарные побочные эффекты Keycloak/S3/payment — на этапе R6 (outbox). До этих
этапов rollout не должен заявлять гарантии, которых текущая архитектура ещё не
обеспечивает.
