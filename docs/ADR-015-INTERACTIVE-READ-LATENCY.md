# ADR-015: ограничение работы интерактивных чтений

Дата: 11 сентября 2026. Связан с [планом измерений](VPS_LATENCY_PLAN_2026-09-11.md).

## Решение

Профиль читает рейтинг выбранного менеджера через `ManagerPerformanceService.scoreForUser`.
Формула общая с рейтингом всех менеджеров; события повторного открытия собираются одним
запросом. Кэш разделён по дате, пользователю и версии расчёта. В транзакции записи он
обходится, область доступа входит и в ключ рейтинга, а invalidation выполняется после commit. Поздний loader старой версии не
может снова сделать её текущей.

Дневной и месячный прогресс профиля/команды читается из существующих таблиц статистики.
GET не запускает их перестроение. Неизвестный либо старше двух минут текущий прогресс
помечается `updating`; `calculatedAt` передаётся как UTC Instant. Существующая проверка
свежести workload projection сохраняется. При агрегировании используется наиболее ранняя
дата расчёта, а неизвестная дата не заменяется текущим временем. Проверка двух минут
выполняется при загрузке DTO; внешний TTL 30 секунд даёт суммарную границу 150 секунд
для отметки свежести profile/team. Прямые board-чтения проверяют возраст на каждом запросе.
Интерфейс показывает дату
в подсказке прогресса. Исторические строки читаются с их реальной датой расчёта.

Management владеет `manager_control_read_snapshots`: JSON существующего экранного DTO,
manager/date, версия invalidation, версия области доступа и время расчёта. Today сначала
определяет разрешённых менеджеров существующим `ManagerControlAccessPolicy`, затем
загружает их свежие снимки одной выборкой. Максимальный возраст — 60 секунд. При отсутствии
снимка используется прежний расчёт. Такой fallback может не уложиться в SLO; он измеряется
отдельно и не выдаётся за быстрый готовый снимок. GET и явная команда sync сохраняют
прежние разные контракты. Финансовые команды не используют экранный JSON для принятия решений.

## Устойчивое обновление

Две фоновые задачи используют отдельный scheduler с одним потоком. Worker progress
обрабатывает до 25 работников в транзакции и до четырёх партий за tick; manager control —
по одному менеджеру и до десяти за tick. Начало следующей партии ограничено бюджетом
20 секунд, timeout транзакции — 45 секунд. Значения задают верхний предел конкуренции,
а не гарантию полного прохода по произвольно большой базе за 30 секунд.

Обе задачи читают закоммиченные исходные данные повторным идемпотентным проходом.
Существующий `SchedulerLeaseService` расширен блокировкой строки lease внутри транзакции:
владелец и fencing token проверяются перед записью, новый владелец не пересекает ещё
открытую транзакцию старого. Checkpoint и результаты партии фиксируются одной транзакцией.
После ошибки или перезапуска следующий tick продолжает с закоммиченной позиции; конец
прохода возвращает cursor к нулю. Месячные агрегаты обновляются один раз после полного
прохода работников. Поэтому потеря callback не теряет пересчёт; новая очередь отправки
сообщений для этих производных данных не нужна.

Invalidation карточки management увеличивает generation в той же транзакции команды.
Снимок, рассчитанный с предыдущей generation, не может воскреснуть после команды.
Отзыв ролей/назначений дополнительно закрыт областью доступа. Ошибки и время последнего
полного прохода доступны в Prometheus; превышение возраста вызывает alert. В нескольких
репликах оценивать успех выбранного lease-владельца, а не требовать обновления локального
счётчика каждого невыбранного экземпляра.

## Область доступа и кэш

Identity публикует `u_users.api.CabinetCacheScope`. Он возвращает только SHA-256 от
упорядоченного набора версий пользователей, активности, режима контроля владельца,
определений/назначений ролей и связей owner/manager/worker/operator/marketolog.
Пароли, токены, имена и контакты не входят в выборку. Один запрос с UNION ALL избегает
декартова произведения коллекций и ограничения длины GROUP_CONCAT. Цена этого подхода
зависит от размера справочника identity; при его существенном росте потребуется отдельная
транзакционная версия изменений с проверкой всех writers.

Fingerprint не выдаёт прав. Аутентификация, текущие роли, принадлежность объектов и
проверки мобильной/сетевой сессии выполняются прежними владельцами на каждом запросе.
Ключи profile/team и метрик manager board учитывают fingerprint и авторизованного
пользователя. Profile/team имеют максимум 2 000 записей и TTL 30 секунд; Caffeine
сохраняет совместную загрузку одного ключа. Явный refresh остаётся явным refresh.
Очистка кэшей после Keycloak provisioning перенесена за commit. Между репликами отзыв
доступа отражается изменением fingerprint, без локального события как единственного
источника invalidation.

## SQL и финансы

`BoardIdentityReadScope` объединяет повторные чтения пользователя и его manager/worker
в пределах одной синхронной сборки manager/worker board, после HTTP-авторизации.
Типизированные lookup принадлежат identity; максимум 64 записи, scope закрывается
через try-with-resources при любом исходе. Между запросами, потоками и в фоновых задачах
значения не сохраняются. В транзакции записи lookup выполняется заново и локальные
значения очищаются. Финансовые данные, результаты permission/risk gates и составы
команд этим механизмом не кэшируются; следующий запрос повторно читает identity.

Completions сначала выделяет DISTINCT опубликованные review за нужный временной
интервал; обе анти-выборки используют этот компактный CTE. Reconciliation attempts
ограничивается подходящими будущими ACTIVE states до группировки. Индексы не добавлялись:
на MySQL 9.7.3 использованы существующие индексы, а результаты сравнивались на копии.

Для выбранной страницы общих счетов `BadReviewTaskService.getPayableSums` пакетно читает
доплаты и вызывает ту же проверяемую формулу, что одиночный путь. Некорректная сумма не
подменяется нулём: отсутствующая запись проходит прежний строгий одиночный расчёт и
обработку ошибки. Ошибка самой пакетной выборки прерывает операцию. Сводки плохих отзывов
также читаются для всей страницы. Эти входы живут только в текущем вызове/транзакции,
не попадают в кэш. Recovery gate читает PLANNED-задачи OPEN-партий для выбранных заказов
одним запросом в транзакции страницы, с теми же предикатами, что одиночная проверка.
Проверки recovery в командах, нормализация дублей, блокировки, применение
платежей и финансовый аудит сохраняют прежние пути.

## Архитектурные границы и наблюдаемость

Новые публичные возможности: identity fingerprint, платформенный `PerformanceMetrics`
и существующий платформенный `SchedulerLeaseService`. Репозитории identity не
экспортируются потребителям. Снимками management владеет management, прогрессом —
worker performance. Новые циклы и разрешения на доступ к чужим внутренним классам
не добавляются. Для публичных платформенных возможностей удалены соответствующие
устаревшие строки списка внутренних зависимостей; это не автоматическая регенерация baseline.

Servlet filter измеряет security → controller → сериализацию синхронных ответов и
учитывает ошибки отдельно. Очередь до servlet, proxy и RTT клиента измеряются снаружи.
В интерактивный SLI входят только GET: OPTIONS/preflight и HEAD не увеличивают N
и не улучшают latency выполненных чтений страницы.
JDBC instrumentation хранит только число execute и длительность; SQL, параметры и
ответы в telemetry не записываются. Spans имеют фиксированные имена; исключения новых
spans очищаются до имени класса без message/cause/stack. Cgroup v2 счётчики читаются
непривилегированно; отсутствие поддержки не отображается как нулевая нагрузка.
Объекты файлов cgroup удерживаются самим singleton binder: FunctionCounter
Micrometer хранит только слабую ссылку и иначе после GC оставляет последнее
значение. Штатный deploy пересоздаёт Prometheus с сохранением TSDB volume,
чтобы заменённые при доставке inode файлов конфигурации и правил попали в mount.
Сегмент `worker.board/cellular-access` отдельно измеряет прежнюю проверку сети,
включая запись нарушения: её нельзя исключать из HTTP-измерения защищённых вкладок.
Проверка IP объединяет одновременные промахи одного IP через существующий Caffeine
loader. TTL успешного результата и минутный TTL ошибки сохранены; ошибка не попадает
в длительный кэш. Запись каждого нарушения по-прежнему выполняется отдельно, но
читает только ID пользователя существующей scalar-выборкой. Сегменты
`worker.network/ip-intelligence` и `worker.network/violation-write` отделяют провайдера
от записи. IP, имя пользователя и содержимое нарушения не попадают в эти метрики/spans.

## Проверки и выпуск

Проверяются реальные InnoDB rollback/checkpoint/fencing/generation, смена области доступа,
паритет сумм и рейтинга, страницы с синтетическими данными, обычный OIDC-вход в локальный
стенд и фиксированная интенсивность HTTP. Конкретные результаты и ограничения записываются
в отчёт исполнения; этот ADR сам по себе не означает прохождения проверок.

Миграция V1_10_314 добавляет две таблицы. Предыдущая версия может работать после миграции,
не используя их. Штатный выпуск требует проверенного commit/CI, immutable images,
резервной копии и проверок после обновления. Откат возвращает предыдущие образы;
удалять новые таблицы ради отката приложения не требуется.
